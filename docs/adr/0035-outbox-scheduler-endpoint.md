# ADR-0035: outbox の処理を Cloud Scheduler の OIDC 認証付き内部エンドポイントで起動し、行ごとのトランザクションで排他する

- ステータス: Accepted
- 日付: 2026-10-18
- 関連: #217, ADR-0016, ADR-0031, ADR-0032, #213, #216

## コンテキストと課題

ADR-0032 の決定事項 2 で、通知メール（outbox）の送信は常駐ワーカーをやめ、Cloud Scheduler の定期呼び出しで起動すると決めた。
Cloud Run のリクエスト課金では、レスポンスを返した後の goroutine に CPU が割り当てられず、インスタンスも 0 台になりうるため。
実装にあたり、次の 3 点を決める必要があった。

1. 内部エンドポイントを、Cloud Scheduler 以外から呼べないようにする認証方式。
   API は `--allow-unauthenticated` で公開するため、Cloud Run の IAM 認証は使えない。
2. 複数の呼び出しが同時に走っても、同じ通知を二重に送らない排他方式。
   Cloud Scheduler の呼び出しが重なる、リトライされる、最大インスタンス数が 1 を超える、のいずれでも起こりうる。
3. 本番では常駐ワーカーと `Wake()` を使わない。ローカル開発での起動方法。

## 決定

1. **認証**: `POST /internal/outbox/process` は、Cloud Scheduler が付ける OIDC トークンを検証して受け付ける。
   - 署名は Google の JWKS（`https://www.googleapis.com/oauth2/v3/certs`）で検証する。
   - `iss` が Google（`https://accounts.google.com` または `accounts.google.com`）であること、`aud` が `SCHEDULER_OIDC_AUDIENCE` と一致すること、`exp` があり期限内であることを確認する。
   - `email_verified` が true（bool または文字列の `"true"`）で、`email` が `SCHEDULER_SERVICE_ACCOUNT_EMAIL` と一致することを確認する。
   - Scheduler のジョブでは audience を明示して指定し、`SCHEDULER_OIDC_AUDIENCE` と同じ値にする。
   - トークンが無い・無効なら 401、有効な Google のトークンでもサービスアカウントが違えば 403。
   - 2 つの環境変数の片方でも未設定、または通知送信ワーカーが無い（Resend 未設定）ときは、エンドポイントを登録しない（404）。
2. **排他**: outbox の行は `ClaimNextDue` が 1 件ずつ確保する。
   - 確保は `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` を 1 行ごとのトランザクションで行い、送信結果の記録（`MarkSent` など）と同じトランザクションでコミットする。
   - 他の呼び出しが確保中の行は飛ばされるため、同じ行を同時に処理しない。
   - 同じ呼び出しの中で、確定されずに残った行（宛先の取得に失敗した行など）を取り直さないよう、処理済みの行 ID を除外して次を確保する。
   - 1 回の呼び出しで処理する上限は 50 件（従来のバッチサイズと同じ）。開始から 50 秒を過ぎたら、新しい行は確保しない。
   - 確保のトランザクションの寿命（確保の期限）は最大 2 分。超えると巻き戻され、行は `pending` に戻る。
   - 宛先取得と送信は、確保の期限の 10 秒前までに打ち切る。打ち切られた送信は失敗として retry（最大試行回数で failed）に記録する。
     送信結果の記録は、確保の期限まで行える。これにより、送信中に行ロックが外れることはない。
   - シャットダウンのシグナル（SIGTERM）を受けると、処理中の呼び出しも新しい行の確保をやめる。
     処理中の 1 件は、送信も中断され、retry として記録される（宛先取得の途中なら記録せず `pending` のまま）。
3. **ローカル開発**: 常駐ワーカー（30 秒ティッカー）は残し、環境変数 `OUTBOX_WORKER_ENABLED=true` のときだけ起動する。
   既定は無効で、本番では設定しない。`.env.example` では有効にする。`Wake()` は削除する。

## 理由

- **認証**: OIDC トークンは Google が署名するため、共有シークレットのように保管・ローテーションする鍵が増えない。
  既に使っている `golang-jwt` と `keyfunc` で検証でき、追加の依存がない。
  `aud` とサービスアカウントの両方を照合することで、別のサービスアカウントや別の宛先向けのトークンを使い回されても通らない。
- **排他の単位**: アドバイザリロックはセッション単位で、トランザクションモードのプーラー（Supabase のポート 6543）では
  取得した接続と後続のクエリの接続が別になりうる。Supabase への接続方式は #213 で未決のため、どの方式でも成り立つ
  トランザクション単位の行ロックを選ぶ。
- **at-least-once の維持**: 送信後・コミット前にプロセスが落ちた場合は、ロックが解けて次の呼び出しで再送される。
  従来の「`MarkSent` の前に落ちたら再送」と同じ性質で、新たな重複は増えない。
- **シャットダウン**: 確保のトランザクションは `context.WithoutCancel` で開始する。リクエストの `ctx` がキャンセルされても、
  送信済みの行の確定が巻き戻されて二重送信になることを防ぐ。
- **時間の上限**: Scheduler は 1 分間隔で呼ぶ。1 回の呼び出しが次の呼び出しまで続かないよう、新しい行の確保に 50 秒の予算を設ける。
  DB や送信先が応答しなくなった場合に、確保した行と接続を持ち続けないよう、確保に期限を付ける。
  送信と記録の期限を確保の期限から導くのは、送信中にトランザクションが巻き戻されて行ロックが外れ、
  別の呼び出しが同じ行を同時に送ることを防ぐため。1 回の呼び出しは最長で 50 秒＋2 分で終わり、
  Scheduler の試行の期限の既定値（3 分）に収まる。
- **シャットダウン時の停止**: `http.Server.Shutdown` は処理中のリクエストの ctx をキャンセルしない。
  そのため内部エンドポイントのハンドラにだけシグナルの ctx を渡し、リクエストの ctx と合成する。
  `http.Server.BaseContext` にシグナルの ctx を渡す方法は、全リクエストの ctx が SIGTERM で即キャンセルされ、
  通常の API の graceful shutdown を壊すため採らない。
- **`email_verified` の型**: 公式ドキュメントの ID トークンの例では bool だが、Scheduler が付けるトークンの形式は公式で確認できていない。
  文字列の `"true"` で全呼び出しが 403 になることを避けるため、両方を受け付ける。
- **ローカルの常駐ワーカー**: Scheduler を用意しなくても、`docker compose up` だけで通知が送られる。
  排他が入るため、常駐ワーカーと内部エンドポイントを同時に有効にしても、同じ行を同時に送ることはない。
- **swag の対象外**: 内部エンドポイントは公開 API ではなく、利用者向けの OpenAPI に載せない。

## 影響（結果）

### 良い影響
- 最大インスタンス数が 2 以上でも、同じ通知を複数の呼び出しが同時に送ることはない（IP レート制限など他の制約は #215 で別に扱う）。
  ただし、送信後に記録できなかった場合と、送信を打ち切ったが実際には届いていた場合に再送されうる（at-least-once）。
- インスタンスが 0 台でも、Scheduler の呼び出しでインスタンスが起動して送信される。メールは最大 1 分遅れる。
- 認証用の秘密情報が増えない（環境変数の 2 つはどちらも秘密ではない）。

### トレードオフ・制約
- 1 回の呼び出しは、確保した行のトランザクションで 1 本、宛先の取得でもう 1 本、同時に最大 2 本の DB 接続を使う。
  呼び出しが重なるとその分増える。接続プールの上限を設ける場合（#213）は、同時に動く呼び出し数の 2 倍以上にする。
- Google の JWKS は起動時に取得するが、取得に失敗しても起動は止まらない（keyfunc v3 の既定の挙動。Supabase の JWKS も同じ）。
  鍵を取得できるまでは、正しいトークンでも 401 になる。再取得は、未知の `kid` のトークンが来たとき（5 分に 1 回まで）と、1 時間ごとの定期更新で行う。
  JWKS が応答しない場合、起動が JWKS 1 つにつき最大 1 分（取得のタイムアウト）遅れる。Supabase と Google の両方が応答しなければ最大 2 分。
- 呼び出しの途中で停止（SIGTERM）が来た場合、処理中の 1 件は送信を中断して retry として記録し、残りは次の呼び出しに回る。
  送信先がすでに受け付けていた場合は、後で再送になる。
  ただし `http.Server.Shutdown` の待ち時間（10 秒）を超えると打ち切られ、送信後・記録前なら再送になる。停止猶予との関係は #216 で扱う。
- 宛先の取得に恒常的に失敗する行は `pending` のまま `next_attempt_at` が更新されず、先頭に居座る。そうした行が 50 件を超えると、後続の行が処理されない（従来の実装と同じ性質）。
- イベントのキャンセルや欠席連絡の直後に即時送信する仕組み（`Wake()`）はなくなり、最大 1 分遅れる。

## 検討した代替案

- **共有シークレット（固定トークン）のヘッダー**: 実装は最小だが、シークレットの保管・ローテーションが必要になり、漏れると誰でも呼べる。不採用。
- **Cloud Run の IAM 認証**: 呼び出し元の制限は最も堅いが、API 全体を非公開にする必要があり、公開 API と共存できない。
  内部エンドポイント専用のサービスを分ける案もあるが、デプロイ単位と費用が増える。不採用。
- **アドバイザリロックで呼び出し全体を直列化**: 実装は小さいが、セッション単位のため #213 で決める接続方式に依存し、
  トランザクションモードのプーラーでは使えない。不採用。
- **行に `claimed_until` のようなリース列を足す**: 接続方式に依存しないが、マイグレーションが必要で、
  リースの期限切れと再送の関係を別途設計することになる。行ロックで足りるため不採用。
- **ローカルの起動も内部エンドポイントのみにする**: 本番と同じ経路で確認できるが、OIDC トークンの用意が必要で、開発の手間が増える。不採用。
