# ADR-0023: 参加者カテゴリ別人数の内訳は event_costs を参照して保持する

- ステータス: Accepted
- 日付: 2026-08-17
- 関連: #165, ADR-0011, ADR-0022

## コンテキストと課題

イベント参加申込で「大人2名・学生1名」のようなカテゴリ別の参加人数を受け取れるようにする。
このとき「参加者カテゴリの実体をどこに置き、内訳をどう保持するか」を決める必要がある。

前提と制約:

- 参加者カテゴリは主催者がイベント作成時に**自由入力で定義**する。プロダクト共通の固定マスタや enum は存在しない。
- 参加申込フォームは参加者が任意の文字列を打つのではなく、**そのイベントの費用カテゴリを参照**して人数を入力する。
- 既存の `event_members.party_size`（申込全体の人数）と、それを使った定員チェック
  （`SUM(party_size)` をイベント行ロック下で実行）が既に動いている。
- 参加費は申込後に書き換えられないほうが望ましい。イベント集約サイトは一次情報の提示者ではなく仲介者であり、
  申込時に提示した金額の証拠性が信頼の土台になる。
- 内訳は「現在の申込」（`event_members`）と「参加状態ログ」（`event_participation_logs`）の両方に必要。
  匿名参加はログに記録されないため、ログ側だけでは匿名参加の内訳が失われる。

## 決定

参加者カテゴリの実体を `event_costs`（費用カテゴリ）とし、専用のカテゴリマスタは作らない。
内訳は `event_member_categories` / `event_participation_log_categories` に `cost_id` で保持し、
`(cost_id, event_id)` の複合 FK でイベントを跨いだカテゴリ参照を封じる。
カテゴリ名の一意性は `lower(category)` で判定し、`head_count` は 1 以上のみ許可する。

## 理由

- 主催者がカテゴリを定義する場所として `event_costs` が既にある。別マスタを設けると定義が二重管理になる。
- 複合 FK は「参加者とカテゴリが同一イベントに属する」ことを DB レベルで保証する。
  アプリ層の事前チェックはレース条件ですり抜けるため、構造として不可能にするほうが信頼できる。
- FK を `NO ACTION`（既定）にすると、参加者がいるカテゴリの削除を DB が拒否する。
  「申込後に参加費の前提を消せない」という要件を制約として表現できる。
- `cost_id` 参照なら参加費合計（`head_count × cost`）が JOIN 1 本で算出できる。
- `lower(category)` での一意判定は、`event_members` が `lower(mail_address)` で重複を防いでいるのと方針が揃う。
  大文字小文字の違いだけで同じカテゴリが二重登録されると、主催者のカテゴリ別集計が分裂する。
- `head_count >= 1` としたのは、0 名のカテゴリが「行が無い」のと同じ情報しか持たないため。
  そのイベントで選べるカテゴリ一覧は `event_costs` から引ける。後から 0 を許す方向へ緩めるのは容易だが、
  0 行が溜まった状態から厳しくするには既存データの削除が必要になる。

## 影響（結果）

### 良い影響

- 別イベントの費用カテゴリを指定した申込・ログが構造的に作れない。
- 参加者がいるカテゴリの削除を DB が拒否する。
- 参加費の突合（カテゴリ別小計・合計）が JOIN 1 本で書ける。
- カテゴリ別集計に人数 0 の行が混ざらない。

### トレードオフ・制約

- **カテゴリの改名は DB では防げない。** `UPDATE event_costs SET category = ...` は FK で止まらないため、
  参加者がいるカテゴリの改名禁止は API 層の責務になる。
- **ログ側もカテゴリ名・金額を凍結しない。** `cost_id` 参照のため、改名・金額変更は過去のログの見え方にも波及する。
  当時の名前・金額を証跡として残す必要が出た場合は、`category` / `cost` をコピーする列を足す拡張が必要。
  今回は履歴の不変性より構造の整合性を優先した。
- **一度 `join` ログが付いたカテゴリは以降削除できない。** ログは leave 後も残るため FK が効き続ける。
  申込実績のあるカテゴリを消させない制約として受け入れる。
- 費用カテゴリが未登録のイベントでは、申込時に選べるカテゴリが 0 件になる。
  `CreateEventRequest.Costs` は `min=1` 必須なので今後作成されるイベントでは起きないが、既存データには残る。
- `head_count >= 1` のため、API は 0 名のカテゴリを保存前に捨てるか 400 で弾く必要がある。
- `event_members.party_size` は非正規化のまま残す（定員チェックが hot path のため合計を保持する）。
  内訳合計と `party_size` の一致は API 層で保証する必要がある。クライアントが送った合計人数は信用しない。
- 複合 FK の参照先として `event_costs` / `event_members` / `event_participation_logs` に
  `UNIQUE (id, event_id)` が必要になる（`id` は PK なので一意性としては冗長）。インデックスが 3 本増える。

## 検討した代替案

- **案A: 専用のカテゴリマスタ（`event_participant_categories`）を作る**:
  「参加費は一律だが人数の内訳は取りたい」ケースを、費用カテゴリを水増しせずに表現できる。
  2026-08-11 に一度 DB へ適用したが、カテゴリの定義場所が `event_costs` と二重になるため撤回した。
- **案B: カテゴリ名を文字列でコピーする（スナップショット）**:
  費用の編集・削除から独立し、申込時点の名前が凍結される。
  ただしイベント跨ぎ参照と表記ゆれの検証がすべて API 層任せになり、参加費の突合も名前での JOIN になるため採らなかった。
- **案C: JSONB カラムで内訳を持つ**:
  新テーブルなしで済み実装も最小だが、カテゴリの妥当性と値の範囲を DB で強制できず、
  カテゴリ別集計にインデックスが効かない。
