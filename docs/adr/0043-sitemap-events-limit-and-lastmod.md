# ADR-0043: sitemap 用イベント一覧は上限超過時に古い更新から切り捨て、匿名アクセスを IP で制限する

- ステータス: Accepted
- 日付: 2026-11-06
- 関連: #259, #264, NatuEve_Web_Frontend#373, ADR-0012, ADR-0034, ADR-0037, ADR-0042

## コンテキストと課題

フロントエンドが `sitemap.xml` を生成するため、`GET /api/v1/sitemap/events` で全イベントの ID と最終更新日時を返す。対象を全イベントとすることは ADR-0042 で決めた。取りやめ済みも含めるのは、ページを残して構造化データで中止を伝えるためである（#259、ADR-0012）。

残る判断は、件数の上限を超えたときの扱い、認証不要のエンドポイントの負荷、`lastmod` になる最終更新日時の意味の 3 つである。

制約と前提は次のとおり。

1. **sitemap 1 ファイルの上限は 50,000 URL**。#259 で API の上限もこの値にした。
2. **`events.id` はランダムな UUID**。id の順で切ると、残るイベントが無作為になる。
3. **API の前段に共有キャッシュがない**。中継 Worker の `fetch()` は `cache: "no-store"` で（ADR-0034）、API 内にも応答のキャッシュはない。
4. **本番は Cloud Run 1 台・同時実行 80・DB 接続に上限あり**（ADR-0037）。6 万行の検証では、応答は約 4.6MB、クエリは 14ms だった（PostgreSQL 14、ローカル）。
5. **`events.updated_at` を更新するのは取りやめだけだった**。イベントの編集 API はなく、レポート投稿はイベントページの内容を変えうるが `events` を更新していなかった。
6. **フロントの sitemap の再生成方式は未定**（NatuEve_Web_Frontend#373）。

## 決定

**上限は 50,000 件とし、超過時は `updated_at` の新しい順に残して警告ログを出す。匿名アクセスは平均 1 回/分・バースト 5 回の IP レートリミットで制限する。レポート投稿でも `events.updated_at` を更新する。**

1. 順序: `updated_at` の降順、同時刻は `id` の昇順で返す。
2. 上限の検知: service が上限 + 1 件を repository へ要求し、超過していれば上限まで切り詰めて `slog.Warn` を出す。応答には切り詰めの印を付けない。
3. レートリミット: `middleware.NewIPRateLimiter` のこのルート専用のインスタンスで、平均 1 回/分・バースト 5 回とする。
4. 最終更新日時: 取りやめとレポート投稿で `events.updated_at` を更新する。`GET /api/v1/events/{id}` の `updatedAt` も同じ値である。
5. キャッシュ: `Cache-Control: public, max-age=3600` を 200 の応答に付ける。

## 理由

- **更新の新しいイベントを残すと、切り捨ての影響が小さい**: 検索エンジンへ伝える価値が高いのは、最近変わったページである。
- **切り詰めは検知できれば足りる**: 上限に近づいたら sitemap index への分割が要る。`level` が WARN のログなら監視で拾え、応答の形を変えずに済む。
- **上限 + 1 件の要求で判定すると、全件数を数えるクエリが要らない**: 上限の値は service の定数 1 か所に集まる。
- **`Cache-Control` だけでは負荷を抑えられない**: 効くのは呼び出し側が持つキャッシュだけで、別のクライアントのリクエストは毎回 DB に届く。そのため匿名の連打はレートリミットで止める。
- **バーストは join と同じ 5 回にする**: 再生成方式が未定のフロントが短時間に数回呼んでも、失敗しないようにする。sitemap の生成は頻繁に要らないので、平均は 1 回/分とする。
- **レポートはイベントページの内容の一部である**: 投稿と同じトランザクションで更新すれば、レポートと `lastmod` がずれない。

## 影響（結果）

### 良い影響

- 上限を超えても、新しく更新されたイベントは sitemap に残り、超過はログで分かる。
- 匿名の連打でも、1 IP あたりの全行取得は平均 1 回/分に抑えられる。
- レポート投稿が `lastmod` に反映され、検索エンジンへ更新が伝わる。

### トレードオフ・制約

- **上限を超えると、古いイベントは sitemap から外れる**: 超過の検知後に sitemap index への分割が要る。
- **IP を共有する呼び出し元は枠も共有する**: `CF-Connecting-IP` が入らない経路では、該当するリクエストが同じ枠を使う（Deployment.md）。sitemap 専用のインスタンスなので、他の API には波及しない。
- **429 に `Retry-After` は付かない**: 呼び出し側は待ち時間を知れない。フロントは 429 と 5xx の扱いを #373 で決める必要がある。
- **`Cache-Control` は API の負荷を下げない**: 下げるには Worker かサーバー内のキャッシュが要る。
- **`updated_at` はイベント本体の更新時刻だけを表さなくなる**: 既存の `updatedAt` の意味が「レポート投稿を含む更新」に広がる。

## 検討した代替案

- **`ORDER BY id` のまま切り捨てる**: 実装は最も単純 / 残るイベントが無作為になるため不採用。
- **最初から sitemap index へ分割する**: 件数の上限がなくなる / 現在の件数では不要で、API とフロントの変更が増えるため不採用。
- **応答に切り詰めの印や総件数を入れる**: フロントで検知できる / `[{ id, updatedAt }]` の形（#259）から変わり、運用の検知はログで足りるため不採用。
- **Worker かサーバー内でキャッシュする**: オリジンへの到達を減らせる / 中継は `no-store` の方針で（ADR-0034）、サーバー内の保持も増えるため、今は不採用。
- **`GREATEST` などで関連テーブルの更新日時をクエリ時に合成する**: `events` を更新しなくて済む / sitemap の取得が重くなり、`GET /events/:id` の `updatedAt` とも値がずれるため不採用。
