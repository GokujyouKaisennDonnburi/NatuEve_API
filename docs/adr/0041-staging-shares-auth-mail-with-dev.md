# ADR-0041: 検証環境は Supabase の Auth とメールの送信元を開発と共有し、Supabase は本番と同じく Auth と DB を分ける

- ステータス: Accepted
- 日付: 2026-10-27
- 関連: #254, #214, ADR-0003, ADR-0036, ADR-0040
- 変更: ADR-0036 の決定事項 5（検証用の DB と Auth を 1 つのプロジェクトにまとめ、NatuPortal の共有 Auth と同じアカウントに置く）を置き換える。
  ADR-0040 の決定事項 8 のうち Resend（検証用の送信専用キーを別に発行し、送信元のドメインは本番と同じにする）を置き換える

## コンテキストと課題

ADR-0036 の決定事項 5 は、検証用の DB と Auth を 1 つのプロジェクトにまとめ、NatuPortal の共有 Auth と同じ Supabase アカウントに置くとしていた。
ADR-0040 の決定事項 8 は、検証環境の Resend のキーを別に発行し、送信元のドメインを本番と同じにするとしていた。

一方、次の状態がある。

- 本番は Auth（NatuPortal の共有 Auth）と DB が別のプロジェクトにある（#214）。
- ローカル開発は、個人の Supabase アカウントにある開発用の Auth 用プロジェクトを使っている。
- Resend の送信元のドメインは、本番が `mail.natuportal.org`、開発が `dev-mail.natuportal.org` に分かれている。

検証環境の初期設定（#254）で、検証環境の Supabase とメールの送信元をどう置くかを決め直した。

## 決定

**検証環境は、Supabase の Auth とメールの送信元を開発と共有する。Supabase は本番と同じく Auth と DB を別のプロジェクトにする。**

1. 検証環境の Auth（`SUPABASE_JWKS_URL`）は、ローカル開発で使っている Auth 用プロジェクトを使う。
2. 検証用の DB（`DATABASE_URL`）は、Auth とは別のプロジェクトとして作る。Data API は無効にする。
3. Supabase のプロジェクトはどちらも個人の Supabase アカウントに置く。なちゅいべ Org とも、NatuPortal の共有 Auth があるアカウントとも別。
4. Resend は、開発と検証環境で同じ送信専用キーと送信元のドメイン（`dev-mail.natuportal.org`）を使う。本番は `mail.natuportal.org` と別のキーを使う。
5. 本番の共有 Auth を使わないこと、検証用 DB に本番のデータをコピーしないことは ADR-0036 のまま。
   R2 は ADR-0039 のまま（検証環境はローカル開発用のバケットを使い、トークンは検証環境用に別に発行する）。

## 理由

- Supabase: 本番と同じ構成にし、環境ごとの構成の違いによる混乱を減らす。
  `SUPABASE_JWKS_URL` は Auth 用、`DATABASE_URL` は DB 用のプロジェクトを指す、という対応がどの環境でも同じになる。
- Resend: 送信元のドメインで、受け取った側が開発・検証のメールと本番のメールを見分けられる。

## 影響（結果）

### 良い影響

- ADR-0036 の「検証環境と本番の構成の差」（検証用は DB と Auth が同じプロジェクト）がなくなる。
  Data API を塞ぐ設定の確認は、本番と同じく DB 用のプロジェクトだけで済む。
- 本番の共有 Auth のアカウントに、検証用のプロジェクトを足さずに済む。
- ADR-0040 の「検証環境のメールは本番と同じドメインから送られ、受け取った側からは見分けにくい」がなくなる。

### トレードオフ・制約

- ローカル開発と検証環境で Auth を共有する。ローカル開発で発行したトークンで検証環境の API を呼べ、テスト用のアカウントも共有になる。
- 検証用 DB はローカル開発の DB と別のため、同じ Auth のユーザーでも、DB にあるプロフィールなどは環境ごとに別になる。
- Auth 用プロジェクトは Cloud Scheduler の呼び出し先ではない。7 日間使われないと一時停止しうる（Free）。止まると、ローカル開発と検証環境のログインが両方止まる。
- 個人アカウントの Free の枠（アクティブなプロジェクト 2 つ。ユーザーごとに数える）のうち、Auth 用と検証用 DB で 2 つを使う。
- Resend のキーは開発者の `.env` と検証環境の Secret Manager で同じ値になる。キーを差し替えるときは両方を更新する。
- `dev-mail.natuportal.org` の送信に要る DNS の設定（SPF・DKIM など）を、本番のドメインとは別に保つ。

## 検討した代替案

- **DB と Auth を 1 つのプロジェクトにまとめる（ADR-0036 の決定事項 5）**: プロジェクトが 1 つで済むが、本番と構成が違い、
  接続先の対応や Data API の確認が環境ごとに変わる。不採用。
- **検証専用の Auth 用プロジェクトを作る**: ローカル開発とトークン・アカウントを分けられるが、個人アカウントのアクティブなプロジェクトが 3 つになり、
  Free の枠（2 つ）に収まらない。不採用。
- **検証環境の送信元を本番と同じドメインにする（ADR-0040 の決定事項 8）**: DNS の設定を足さなくてよいが、受け取った側が本番のメールと見分けにくい。不採用。
