# ADR-0018: イベント終了日時を任意入力とし、省略時は開催日時で補完する

- ステータス: Accepted
- 日付: 2026-07-26
- 関連: #145, #146

## コンテキストと課題

これまで `events` は開催日時 `event_date` のみを持ち、複数日にわたるイベント（観察合宿・連続開催の講座など）の終了日を表現できなかった。`events.end_date` を追加するにあたり、**API 契約として終了日時をどう受け取るか**を決める必要がある。

制約と前提は次のとおり。

1. **単日イベントが多数派である**。日帰りの観察会が中心のため、終了日時の入力を全投稿に強制すると、大半のケースで「開催日と同じ日付」を再入力させることになる。
2. **既存クライアントは `endDate` を送らない**。`POST /api/v1/events` は既に運用されており、リクエストに必須フィールドを追加すると既存クライアントが 400 になる。
3. **DB 側は `NOT NULL` + `CHECK (end_date >= event_date)` とした**（`db/migrations/20260622140000_create_events.sql`）。開始より前の終了日を DB レベルで拒否する不変条件を持たせたい一方、制約違反をそのまま素通しすると `pq` エラーが 500 になり、入力ミスに対する応答としては不適切である。

つまり「NULL を許容せず DB に不変条件を持たせたまま、入力は任意にし、かつ違反は 400 で返す」を同時に満たす設計を決める必要がある。

## 決定

**`endDate` はリクエストでは任意入力とし、省略（ゼロ値）時はサーバーが `eventDate` と同値を補完する。指定された場合に `eventDate` より前であれば service 層で 400 を返す。DB は `NOT NULL` + `CHECK` を維持する。**

1. `model.CreateEventRequest.EndDate` は必須にしない（`validate:"required"` を付けない。OpenAPI の `required` にも含めない）。
2. 補完はサービス層（`buildNewEvent`）で行う。`req.EndDate` がゼロ値なら `req.EventDate` を採用し、`EventDate` と同様に `.UTC()` で正規化して `model.NewEvent.EndDate` に詰める。repository へ渡る時点で必ず非ゼロかつ `EventDate` 以上であることを保証する。
3. 検証は `validateCreateEventRequest` で行う。ゼロ値は未指定として素通しし、非ゼロかつ `EndDate.Before(EventDate)` のときのみ `ValidationError`（HTTP 400、メッセージ「終了日時は開催日時以降を指定してください」）を返す。`EndDate == EventDate` は許可する。
4. DB の `NOT NULL` と `CHECK (end_date >= event_date)` は残す。アプリ側の検証をすり抜けた書き込み（将来の別経路・直接 SQL）に対する最後の防衛線として機能させる。通常運用でこの制約に到達することはない。

## 理由

- **NULL 許容より状態が少ない**: 「単日イベント = 開始と終了が同時刻」と表現することで、`end_date` は常に値を持つ。期間での絞り込みや「開催中のイベント」判定を書くときに `COALESCE(end_date, event_date)` や NULL 分岐が不要になり、`CHECK` 制約も無条件に効かせられる。
- **既存クライアントを壊さない**: `endDate` を送らない現行クライアントは、これまでどおり単日イベントとして投稿できる。OpenAPI の `required` に入らないため、生成した型もオプショナルになる。
- **ADR-0017 と同じ「任意化＋サーバー既定値」の型に揃う**: キャンセル通知の件名・本文で採った「必須にせずサーバーが既定値を補い、不変条件はサーバーが保証する」という方針と一貫する。クライアントに強制する項目を増やさず、契約の解釈はリクエストボディだけで完結する。
- **DB の制約違反を 500 にしない**: `CHECK` 違反は `lib/pq` のエラーとして返り、ハンドラでは 500 に落ちる。入力の誤りは 400 で返すべきであり、CLAUDE.md の「バリデーションは API サーバーで行う（サーバー側が信頼の境界）」にも従う。DB 制約は防衛線として二重に持ち、一次的な判定はサービス層で行う。

## 影響（結果）

### 良い影響

- 単日イベントは `endDate` を送らずに投稿でき、入力の摩擦が増えない。
- `events.end_date` が常に非 NULL なので、今後の期間検索・開催中判定を NULL 分岐なしで実装できる。
- 開始より前の終了日時は、サービス層で 400、DB で `CHECK` の二段で拒否される。

### トレードオフ・制約

- **「単日」と「所要時間ゼロ」を区別できない**: `end_date == event_date` は「日帰り（省略）」と「開始と同時刻に終わる指定」の両方を意味しうる。両者を区別する要件は現時点で存在しないため許容する。区別が必要になった場合は所要時間や終日フラグを別途持つ。
- **ゼロ値を「未指定」とみなす**: Go の `time.Time` ゼロ値（0001-01-01T00:00:00Z）を未指定の代理として扱うため、クライアントがこの値を意図して送っても未指定として補完される。実在しうる日時ではないため実害はない。
- **レスポンスにはまだ `endDate` を含めない**: 本 ADR のスコープは投稿リクエスト（`POST /api/v1/events`）まで。`EventSummary` / `EventResponse` への露出と `sort=end_date` の許可は後続で対応する。それまで、投稿した終了日時は API から読み出せない。
- **既存環境は DB の再作成が必要**: 追加はマイグレーションファイルの直接書き換えで行ったため、適用済みの環境では goose のバージョン管理上、再実行されない。開発 DB はボリュームを破棄して作り直す。

## 検討した代替案

- **`endDate` を必須にする**:
  契約は最も明快で、「単日」と「所要時間ゼロ」の曖昧さも投稿者の意思として解消できる。しかし既存クライアントが即座に 400 になる破壊的変更であり、かつ大多数を占める単日イベントで開催日と同じ値を再入力させる摩擦が残る。不採用。
- **`end_date` を NULL 許容にし、未指定は NULL のまま保存する**:
  「終了日時が指定されていない」ことをデータとして保持できるが、`end_date` を読むすべての箇所で NULL 分岐が必要になり、`CHECK` も NULL のとき素通しになる。表現できる状態が増える割に、その区別を使う要件が無い。不採用。
- **DB の `CHECK` を持たず、アプリ側の検証だけに任せる**:
  400 を返す経路は同じだが、将来バッチや別経路から書き込む際に不変条件が失われる。制約を残しても通常運用のコストはゼロ。不採用。
- **`endDate` 未指定時に「開催日の終わり（23:59:59 等）」を補完する**:
  日帰りイベントの直感には近いが、サーバーが勝手に時刻を作ることになり、投稿者が指定していない情報を持たせてしまう。タイムゾーン（どのゾーンの一日の終わりか）の判断も必要になる。単純に `eventDate` と同値にする方が説明可能。不採用。
