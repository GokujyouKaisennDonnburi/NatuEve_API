# ADR-0024: イベント詳細で参加人数を公開し、残り人数はクライアントで算出する

- ステータス: Accepted
- 日付: 2026-08-18
- 関連: #169, ADR-0022, ADR-0023

## コンテキストと課題

イベント詳細画面で「定員30人・申込20人なので残り10人」を出せるようにする。
このとき「サーバーが何を返すか」と「その数をどこで数えるか」を決める必要がある。

前提と制約:

- `events.capacity` は NULL または 0 が「定員なし」を意味し、定員を設定しないイベントが実在する。
- 申込1件の人数は `event_members.party_size`。参加キャンセルでは行ごと削除されるため、
  `SUM(party_size)` が常に「現在申込中の人数」になる。
- 定員チェック（`internal/repository/event_join.go`）は、イベント行を `FOR UPDATE` でロックした
  トランザクション内で同じ `SUM(party_size)` を実行している。
- 参加者一覧（`GET /api/v1/events/{id}/members`）は `totalMembers`（`party_size` の合計）を返すが、
  主催者専用エンドポイントであり、氏名・メールアドレスを含む全参加者行を取得したうえで
  service 層がループで合計している。
- イベント詳細（`GET /api/v1/events/{id}`）は未認証でも取得できる公開エンドポイント。

## 決定

イベント詳細レスポンスに `participantCount`（`party_size` の合計）を追加し、
残り人数はサーバーで算出しない。集計は詳細取得クエリの相関サブクエリで行い、
参加者一覧の集計経路は流用しない。

## 理由

- 定員なしのイベントでは残り人数を定義できないが、参加人数は定義できる。人数を返す形なら
  定員あり・なしの両方を 1 フィールドで賄える。残り人数は `capacity - participantCount` で導ける。
- 残り人数をサーバーが返しても、`capacity` を同じレスポンスに含んでいる以上、情報量は変わらない。
  同じ事実を 2 フィールドで返すと、定員変更直後などに 2 つの値が食い違って見える経路が増えるだけになる。
- 公開エンドポイントから参加者一覧の集計経路を呼ぶと、表示に不要な氏名・メールアドレスを
  アプリのメモリへ載せることになる。数え方（`party_size` の合計）は揃えたうえで、取り方は SQL 集計にする。
- 詳細は 1 件取得なので、相関サブクエリでも `event_members(event_id, created_at)` の索引を使った
  集計 1 回で済み、DB への往復は 1 回のまま保てる。実行計画の実測は行っておらず、
  `event_members` が大きくなった時点で再評価する。
- 残り人数を返さない以上、Go 側に共通化できるロジック（定員なし判定・負値のクランプ）は存在しない。
  呼び出し側が 1 箇所ずつの薄いラッパになるため、共通関数は作らない。

## 影響（結果）

### 良い影響

- 定員を設定していないイベントでも「今何人集まっているか」を表示できる。
- 残り人数の表示条件（定員ありのときだけ出す、残りわずかを強調する等）をクライアント側の
  表示仕様として決められる。サーバーの変更を伴わない。
- 参加人数を知るために主催者専用の参加者一覧を叩く必要がなくなる。

### トレードオフ・制約

- **参加人数が公開情報になる。** これまで人数を知れるのは主催者だけだった。
  誰が参加しているか（氏名・プロフィール）は引き続き主催者専用のまま。
- **定員を後から下げると `participantCount > capacity` になりうる。** 減算結果が負値になるため、
  表示側でのクランプが必要。サーバーは実測値をそのまま返す。
- **一覧（`EventSummary`）には出さない。** 一覧へ広げる場合、件数分の相関サブクエリを避けるために
  一覧クエリを LEFT JOIN + GROUP BY へ書き換え、`capacity` のレスポンス追加も必要になる。
- **`participantCount` は取得時点のスナップショット。** 直後に他の申込が入れば残り人数はずれる。
  定員超過を防ぐ保証は、申込時にイベント行をロックして行う定員チェックが引き続き唯一の担保であり、
  クライアントが残り人数を見て申込可否を判断する経路は UX 補助にとどまる。

## 検討した代替案

- **案A: `remainingCapacity`（定員なしは null）をサーバーが算出して返す**:
  クライアントの計算が不要になるが、定員なしのイベントで参加人数が取れないままになり、
  「定員なしでも人数を出したい」という要件を満たさない。人数と併せて両方返す案は同じ事実の二重提供になる。
- **案B: 参加者一覧サービスの合計（`totalMembers`）を詳細取得から流用する**:
  合計の実装を 1 箇所にできるが、公開エンドポイントで全参加者の氏名・メールアドレスを
  取得することになり、取得する情報の範囲が表示目的を超える。
- **案C: `events` に参加人数のカウンタ列を持ち、申込・キャンセルで更新する**:
  読み取りは最速だが、`party_size` の合計との整合を維持する責務が増える。
  現状の申込規模では索引付きの `SUM` で足りる。
- **案D: 参加人数専用のエンドポイントを別に生やす**:
  詳細表示のたびに往復が 2 回になり、詳細画面の初期表示が遅くなる。
