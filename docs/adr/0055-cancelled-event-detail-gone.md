# ADR-0055: 取りやめ済みのイベントの詳細とレポートは 410 を返す

- ステータス: Accepted
- 日付: 2026-11-26
- 関連: #314, #311, NatuEve_Web_Frontend#473, NatuEve_Web_Frontend#471, ADR-0012, ADR-0054
- 変更: ADR-0054 の決定事項 4（詳細 API は取りやめ済みも返す）・決定事項 6（構造化データが入ったら sitemap に戻すかを見直す）と、代替案「詳細 API でも取りやめ済みを返さない」を不採用とした判断、ADR-0012 の決定事項 7 の詳細に関する部分を置き換える（Supersedes, 部分的）

## コンテキストと課題

ADR-0054 で、一覧系の API と sitemap は取りやめ済みのイベントを返さなくなった。詳細 API（`GET /api/v1/events/{id}`）だけは、メールや共有リンクから来た人が `404` になって取りやめたことが分からなくならないよう、取りやめ済みも `cancelledAt` を付けて返していた。

ADR-0054 の後、詳細も返さないようにすることになった（#314）。制約と前提は次のとおり。

1. **画面では取りやめを「削除」と呼んでいる**。フロントの `EventCancelModal.tsx` は「イベントを削除しました」と表示し、一覧へ移る。
2. **詳細ページは取りやめを表示していない**。`EventDetail.tsx` は `cancelledAt` を見ておらず、取りやめ済みも開催予定のように見える。申し込むと `409`（`event_cancelled`）で初めて分かる。
3. **イベントを削除する機能がない**（ADR-0054 の前提 4）。テストやスパムのイベントも、取りやめで片付ける。
4. **レポート API（`GET /api/v1/events/{id}/report`）は認証なしでイベント ID から読める**。レポートの投稿は、取りやめ済みのイベントにもできる。
5. **フロントは詳細をイベント ID だけをキーにして共有キャッシュしている**（`unstable_cache`）。

## 決定

**取りやめ済みのイベント（`cancelled_at IS NOT NULL`）について、詳細 API とレポート API は `410 Gone` を返す。**

1. `GET /api/v1/events/{id}`: 取りやめ済みなら `410` を返す。
2. `GET /api/v1/events/{id}/report`: イベントが取りやめ済みなら、レポートの有無にかかわらず `410` を返す。
3. 本文は `{"error": {"code": "event_cancelled", "message": "..."}}` とし、イベントのタイトルや `cancelledAt` は含めない。
4. 主催者本人のリクエストも例外にしない。
5. 書き込み系の API（`/join`・`/join/confirm`・`/absence` など）は変えず、取りやめ済みには `409`（`event_cancelled`）を返す。
6. 認証が要る参照系の API（`/members`・`/members/me`・`/participation-logs`）は変えない。
7. 取りやめ済みは詳細ページごと無くなるので、sitemap に戻すことは見直さない（ADR-0054 の決定 6 は取り下げる）。

## 理由

- **利用者は取りやめを削除と受け取っている**: 画面が「削除」と呼んでいるのに、URL を開けば見える状態は期待と食い違う。取りやめが削除の代わりに使われる以上、片付けたイベントが外から読めるのは目的と逆になる。
- **ADR-0054 が詳細を返し続けた理由は 410 で満たせる**: 退けた理由は「直リンクから来た人が `404` になり、取りやめたことが分からない」だった。`410` は `404` と区別できるので、フロントは「削除された」と伝えられる。詳細ページは今 `cancelledAt` を表示しておらず、返し続けても取りやめは伝わっていなかった。
- **レポートは詳細と同じ扱いにする**: 詳細だけを止めると、取りやめ済みのイベントのレポートが ID から読めてしまう。
- **コードは原因で決める**: 409 と 410 はステータスで区別できる。原因は同じ「取りやめ済み」なので、既存の `event_cancelled` を使う。
- **主催者を例外にしない**: 公開 API の応答を見る人で変えると、フロントの共有キャッシュに混ざる。画面はもう削除として扱っている。
- **書き込み系は 409 のまま**: 「イベントはあるが、今の状態ではその操作ができない」という意味は変わらず、フロントのエラー処理も変えずに済む。

## 影響（結果）

### 良い影響

- 取りやめた（削除した）イベントとそのレポートが、一覧・sitemap・詳細のどこからも見えなくなる。
- 詳細ページが 2xx を返さなくなるので、すでに検索結果に載ったページも外れていく。フロントの `noindex`（NatuEve_Web_Frontend#471）は不要になる。

### トレードオフ・制約

- **フロントが先に対応する必要がある**: フロントは `404` だけを「不存在」として扱っている。API を先に出すと、取りやめ済みの詳細ページがエラーページになる。フロントの対応（NatuEve_Web_Frontend#473）をデプロイしてから、API をデプロイする。
- **主催者は自分が取りやめたイベントを API から見られない**: 一覧（ADR-0054）に続いて、詳細とレポートも見られなくなる。取りやめを取り消す API はない（ADR-0012）。
- **410 を返すと、その ID のイベントがあったことは分かる**: ID は UUID で、取りやめ前は公開されていた。
- **フロントのキャッシュが切れるまでは、取りやめ後も詳細が見える**: 今は最大 60 秒。
- **取りやめ済みのイベントへのレポート投稿は、まだ拒否していない**: 投稿しても `410` で読めない。拒否するかは別に決める。

## 検討した代替案

- **詳細は返し続ける（ADR-0054 のまま）**: 直リンクの受け皿になる / 詳細ページが取りやめを表示しておらず受け皿になっていないうえ、削除したはずのイベントが読めるため不採用。
- **404 を返す**: 存在しない ID と同じ扱いにでき、ID があったことも分からない / フロントが「削除された」と伝えられないため不採用。
- **主催者には 200 を返す**: 主催者が自分の取りやめたイベントを確かめられる / 公開 API の応答が見る人で変わり、フロントの共有キャッシュに混ざるため不採用。
- **書き込み系も 410 にする**: 取りやめ済みの扱いが全 API で揃う / 「あるが操作できない」という 409 の意味に合っており、フロントのエラー処理も変わるため不採用。
- **エラーコードを `event_deleted` にする**: 画面の呼び方に揃う / API と DB では取りやめ（cancel）と呼んでおり、409 の `event_cancelled` と原因が同じため不採用。
