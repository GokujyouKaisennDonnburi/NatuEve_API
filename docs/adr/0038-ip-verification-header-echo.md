# ADR-0038: 利用者 IP の検証は、ヘッダーを返す検証用サービスを API とは別にデプロイして行う

- ステータス: Accepted
- 日付: 2026-10-23
- 関連: #241, #215, #242, #243, #244, ADR-0034
- 構成の詳細・手順は [docs/Deployment.md](../Deployment.md) の「利用者 IP の検証（#215）」を参照

## コンテキストと課題

ADR-0034 で、利用者 IP は中継用 Worker が `CF-Connecting-IP` の値を利用者 IP 用のヘッダーに上書きして渡し、
API が Gin の `TrustedPlatform` で読む方式に決めた。参加申込の IP レート制限（`internal/middleware/ratelimit.go`）は
この値ごとに数える。

#215 では、デプロイ後に Worker 経由と run.app の URL への直接アクセスのそれぞれで、コンテナに届く接続元 IP と
IP 系ヘッダーの中身を確かめる。Cloudflare と Cloud Run がどのヘッダーに何を入れるかは、公式ドキュメントだけでは
確定できない（利用者が付けた `CF-Connecting-IP` を Cloudflare が上書きするかは公式に明記がない。ADR-0034）。

API のリクエストログ（`internal/middleware/logger.go`）に出るのは `c.ClientIP()` の結果だけで、接続元の IP や
ヘッダーの中身は出ない。確かめる手段を、デプロイ前に用意する必要があった。

前提・制約は次のとおり。

- ADR-0034 で、拒否したリクエストのログに偽装されたヘッダーの IP を記録しないことにしている。
- run.app の URL への直接アクセスは、中継元の確認で 403 になる。
- 秘密ヘッダー（`X-Relay-Auth`）の値は記録・表示しない。
- 確認の結果は、公開リポジトリの issue に返信する。

## 決定

**コンテナに届く接続元 IP と IP 系ヘッダーの確認は、届いたリクエストの情報を JSON で返すだけの検証用サービス
（`cmd/headerecho`）を、API とは別の Cloud Run サービスとしてデプロイして行う。API には確認用の記録を入れない。**

1. **返す内容**: 接続元（`RemoteAddr`）、IP 系ヘッダーの値、届いた全ヘッダーの名前、秘密ヘッダーの有無。
   値を返すのは決めた IP 系のヘッダー（`X-Forwarded-For`・`Forwarded`・`X-Real-IP`・`True-Client-IP`・
   `CF-Connecting-IP`・`CF-Connecting-IPv6`・`CF-Pseudo-IPv4` と、利用者 IP 用のヘッダー）だけで、それ以外は名前だけを返す。
   秘密ヘッダーは有無だけを返す。Host は返さない。
2. **確かめ方**: Worker 経由は、中継用 Worker の転送先（secret `ORIGIN_URL`）を一時的に検証用サービスへ向けて確かめる。
   直接アクセスは、検証用サービスの run.app の URL を呼んで確かめる。
3. **時期と後片付け**: 利用者に公開する前に行う。確認が終わったら転送先を API に戻し、検証用サービスとイメージを削除する。
   コードはリポジトリに残す。
4. **デプロイの設定**: ingress と認証（`allUsers` に invoker を付ける）は API と同じにし、最大インスタンス数は 1 にする。

## 理由

- **API に入れない理由**:
  - 検証のためのコードと設定が本番のイメージに入り、無効にし忘れると本番で記録が続く。
  - run.app の URL への直接アクセスは中継元の確認で拒否される。そのヘッダーを記録すると、ADR-0034 の
    「拒否したリクエストのログに、偽装されたヘッダーの IP を記録しない」と両立しない。
- **別のサービスで足りる理由**: 確かめたいのは、Cloudflare と Cloud Run がコンテナに何を渡すかである。
  ingress と認証を API と同じにすれば、同じ経路を通る。API が `c.ClientIP()` として何を使うかは、
  既存のリクエストログの `ip` で確かめられる（#244）。
- **値を返すヘッダーを一覧で絞る理由**: 検証用サービスは秘密ヘッダーを確かめず、誰でも呼べる。Worker 経由では、
  返してはならない値（秘密ヘッダー）も届く。返す値を決めた一覧に限れば、想定していないヘッダーの値を返さない。
  一覧にない IP 系のヘッダーが届いても、名前の一覧で気づける。
- **Host を返さない理由**: run.app の URL は推測されにくくしておく前提（ADR-0034）で、結果は公開リポジトリの issue に返信する。
- **転送先の切り替えで確かめる理由**: 本番と同じ Worker（Custom Domain・設定）を通して確かめられる。
  別の Worker とサブドメインを用意する手間がかからない。
- **コードを残す理由**: ロードバランサーへの切り替え（ADR-0034 の決定事項 7）など、中継の構成を変えたときに同じ確認をやり直せる。

## 影響（結果）

### 良い影響

- 本番の API のコードと設定は変わらない。
- 秘密ヘッダーの値と、IP 系以外のヘッダーの値を返さない。

### トレードオフ・制約

- Worker の転送先を検証用サービスに向けている間は、独自ドメインから API に届かない。利用者に公開した後は、
  この方法では確かめられない（やり直す場合は、別の Worker とサブドメインを用意する）。
- 検証用サービスは、デプロイしている間は誰でも呼べる。返すのは呼び出したリクエスト自身の情報だけ。
- 検証用サービスの ingress・認証が API と異なると、結果が API に当てはまらない。
- `cmd/headerecho` のコードと Dockerfile を管理するものとして抱える。

## 検討した代替案

- **API に一時的な記録を入れる（環境変数で有効にするログやエンドポイント）**: 上記「API に入れない理由」のとおり。不採用。
- **公開されている既存のヘッダーを返すイメージを使う**: 全ヘッダーの値を返すものでは、Worker が付ける秘密ヘッダーの値も
  応答に出る。第三者のイメージを自分たちの Cloud Run で動かすことにもなる。不採用。
- **別の Worker と別のサブドメインで中継する**: 本番の Worker を変えずに済み、公開後でも確かめられる。
  Worker とサブドメインの追加・削除の手間がかかる。公開前に確かめれば足りるため不採用（公開後にやり直す場合の手段とする）。
- **Cloud Run のリクエストログで確かめる**: リクエストログの `httpRequest` に残るのは送信元 IP・User-Agent などの決まった項目で、
  コンテナに届くヘッダーの中身は残らない。不採用。
