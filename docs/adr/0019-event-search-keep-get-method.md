# ADR-0019: イベント検索は GET を維持し、QUERY メソッドへは移行しない

- ステータス: Accepted
- 日付: 2026-08-04
- 関連: #155, ADR-0008（イベント検索は ILIKE 部分一致＋クエリ時 NFKC 正規化で実装する）

## コンテキストと課題

イベント検索 `GET /api/v1/events` は現在、`q`（キーワード、反復指定で最大 10 語）・`sort`・`order`・`limit`・`offset` をクエリパラメータで受け取っている（`internal/handler/event.go`）。

ここに **タグ・地域・金額による絞り込みとソートを追加する予定**がある。タグは UUID の反復指定、地域は `location`（自由文字列、最大 255 文字）、金額は下限・上限の指定になる見込みで、クエリ文字列が長くなることが懸念された。

一方で 2026-06-19 に **RFC 10008「The HTTP QUERY Method」** が Proposed Standard として発行された。QUERY は safe かつ idempotent（RFC 10008 §2）でありながらリクエストボディを持てるメソッドで、まさに「検索条件が長大になる読み取り操作」のために定義されている。POST で検索する際の不都合（safe でない・キャッシュできない・リトライの安全性が保証されない）を仕様として解消するものである。

そこで、**イベント検索エンドポイントの HTTP メソッドを GET のまま維持するか、QUERY へ移行するか**を決める必要がある。

## 決定

**イベント検索は `GET /api/v1/events` を維持し、QUERY メソッドへは移行しない。**

1. タグ・地域・金額のフィルタとソートは、これまでどおりクエリパラメータとして追加する。
2. QUERY への移行は「再検討の条件」（後述）が揃うまで保留する。本 ADR は QUERY を恒久的に否定するものではない。
3. 将来クエリ文字列長が実際に問題となった場合は、**まず `POST /api/v1/events/search` を併設**し、`GET /api/v1/events` は共有可能な検索手段として残す。その際、リクエストボディのスキーマは将来 QUERY へ付け替えられる形で設計する。

## 理由

- **検索結果 URL を共有・ブックマークできなくなるのが受け入れられない**。「この条件のイベント一覧」を SNS で共有する、ブラウザの履歴やブックマークから再訪する、という導線はイベント検索サービスの中核にある。QUERY は条件をボディに載せるため URL が条件を表さなくなり、この導線が失われる。RFC 10008 §2.3 は結果リソースを `Content-Location` で返し GET で取得可能にする道を用意しているが、それを実装するなら結局サーバー側に別の仕組みが必要で、GET を維持する場合に対する利点が薄い。

- **ツールチェーンが QUERY に追いついていない**。QUERY を記述できる API 記述形式は OpenAPI 3.2 以降（`query` オペレーションおよび `additionalOperations`）である。本プロジェクトの `make swag` は swag v1.16.6 で **Swagger 2.0** を出力しており（`api/swagger.yaml`）、QUERY を表現する構文が存在しない。swag v2 系でも OpenAPI 3.1 止まりである。QUERY に移行すると検索エンドポイントが `api/swagger.yaml` から消え、CLAUDE.md が定める「生成元を `api/swagger.yaml` にする」型共有方針が成立しなくなる。`api/` を手で編集する運用は CI の `make swag-check`（`git diff --exit-code`）で必ず失敗する。

- **キャッシュを失う**。公開イベント検索は同一条件のリクエストが繰り返し飛ぶ、CDN・ブラウザキャッシュが最も効く種類の API である。RFC 10008 §2.7 は QUERY の応答をキャッシュ可能と定め、キャッシュキーにリクエストボディを含めることを要求しているが、これを実装した CDN・リバースプロキシはまだ普及していない。当面は「キャッシュされない」前提で考える必要がある。

- **中間装置での疎通リスクがある**。現行構成は Xserver VPS + Docker Compose であり、前段の nginx・WAF・ロードバランサが未知メソッドを 405 / 403 で落とす可能性が残る。移行するなら本番構成での疎通確認が前提条件になる。

- **そもそも URL 長が不足しない**。想定される最大構成（タグ 20 件の UUID 指定で約 820 バイト、キーワード 10 語で約 500 バイト、`location`・金額・ソート・ページングで数百バイト）を合計しても 2KB に届かない。nginx の既定リクエストヘッダバッファは 8KB、現代のブラウザの URL 長は実質制限にならない。**移行の動機である「パラメータが長すぎる」が現時点では発生していない。**

## 影響（結果）

### 良い影響

- 既存コード（`internal/server/router.go` のルート定義、`internal/handler/event.go` の `List`、`internal/middleware/cors.go` の `AllowMethods`）およびクライアント・テストへの変更が一切発生しない。
- 検索結果 URL の共有・ブックマーク・ブラウザ履歴からの再訪が維持される。
- CDN・ブラウザによるレスポンスキャッシュが引き続き効く。
- `make swag` による OpenAPI 生成と型共有のフローが維持され、CI（`make swag-check`）も従来どおり通る。
- ブラウザからの CORS プリフライト（OPTIONS）が増えない。GET は CORS safelisted method である。

### トレードオフ・制約

- **検索条件の表現が平坦なキーバリューに制限される**。ネストした条件や複雑な論理式（OR 条件の入れ子など）はクエリパラメータでは表現しづらい。将来そうした要件が出た場合は本 ADR の再検討対象となる。
- **検索キーワードがアクセスログ・Referer に残る**。RFC 10008 §4 が QUERY の利点として挙げている点の裏返しで、検索語がログに記録される。現状は個人情報を含む検索を想定していないため許容するが、位置情報や個人を特定しうる条件を検索パラメータに載せる場合は再検討する。
- **将来 QUERY へ移行する際のコストを先送りしている**。ただし移行時は「ボディにフィルタ条件を JSON で載せる」形になるため、下記の段階的移行パスによりコストは抑えられる。
- **本 ADR は検索エンドポイントのみを対象とする**。他のエンドポイントのメソッド選定には影響しない。

## 再検討の条件

以下のいずれかが発生した時点で、本 ADR を見直す。

1. 実際のクエリ文字列長が 4KB を超える、または前段のプロキシで 414 / 431 が観測される。
2. 地図の矩形・ポリゴンによる範囲検索、ID の一括指定（数百件）、ネストしたフィルタ条件など、クエリパラメータで表現しきれない検索要件が発生する。
3. swag（または代替の OpenAPI 生成手段）が OpenAPI 3.2 出力に対応し、QUERY をドキュメント化できるようになる。
4. 本番構成の前段（リバースプロキシ・WAF・CDN）が QUERY を透過し、かつボディを含むキャッシュキーに対応する。

3 と 4 が揃った段階で「決定」の 3 で併設した `POST /api/v1/events/search` を `QUERY /api/v1/events` に付け替えるのが最も安価な移行経路になる。ボディのスキーマをそのまま流用でき、サーバー側の変更は Gin のルート登録（`Handle("QUERY", ...)`、gin 1.12.0 はメソッド名を `^[A-Z]+$` で検証するのみ）、CORS の `AllowMethods` への `QUERY` 追加、`Content-Type` 欠落時に 415 を返す処理（RFC 10008 §2.1）の追加にとどまる。

## 検討した代替案

- **`GET /api/v1/events` を `QUERY /api/v1/events` に移行する**:
  検索条件を JSON で構造化でき、URL 長制限から解放される。実装自体は軽く、Gin は任意のメソッド名を登録でき、ブラウザの Fetch 標準も QUERY を送出できる（forbidden method は CONNECT / TRACE / TRACK のみ）。しかし検索結果 URL の共有が失われ、`api/swagger.yaml` に記述できず型共有が壊れ、キャッシュも失う。得られる利点（URL 長からの解放）が現時点で必要とされていない。不採用。

- **いま `POST /api/v1/events/search` を併設する**:
  Swagger 2.0 で記述でき、どの中間装置も透過するため、長大な検索条件への現実的な解になる。ただし現時点で URL 長は不足しておらず、同じ検索に 2 つの入口を作ると仕様・テスト・クライアント実装が二重化する。必要になってから作る（「決定」の 3）。いま作るのは不採用。

- **GET と QUERY を併存させ、クライアントに選ばせる**:
  移行期の互換性は最も高いが、`api/swagger.yaml` に QUERY 側を記述できない問題は解決せず、ハンドラのパラメータ解釈が 2 経路に分岐して検索ロジックの変更コストが倍になる。不採用。

- **検索条件を JSON にして Base64 エンコードし、単一のクエリパラメータに詰める**:
  URL 長を圧縮しつつ URL の共有可能性を保てる。しかし条件が人間に読めなくなり、`api/swagger.yaml` 上も不透明な文字列パラメータとしてしか表現できず、フロントの型生成の恩恵も失われる。デバッグ性とドキュメント性の劣化に対して、いま解決すべき問題がない。不採用。
