# ADR-0020: イベント一覧のタグ絞り込みは OR 条件とし、検索条件を構造体へ集約する

- ステータス: Accepted
- 日付: 2026-08-04
- 関連: #154, ADR-0019（イベント検索は GET を維持する）, ADR-0015（一覧レスポンスでのタグ公開）, ADR-0013（投稿時のタグ紐づけ）, ADR-0008（検索は ILIKE 部分一致＋NFKC 正規化）

## コンテキストと課題

イベント一覧 `GET /api/v1/events` は現在、`q`（キーワード・反復指定・最大 10 語で AND 検索）・`sort`・`order`・`limit`・`offset` を受け取る。レスポンスの各イベントには ADR-0015 で紐づくタグ（`id` + `name`）が既に含まれており、フロントはタグチップを表示できる。しかし**表示されているタグで絞り込む手段が無い**。

前提として揃っているもの:

- 中間テーブル `event_tags`（`event_id`, `tag_id` の複合 PK）と `tags`（`id`, `name`, `normalized_name`）
- 投稿時のタグ紐づけ（ADR-0013）と、そこで確立した「タグ ID は UUID 正準形へ正規化してから扱う」方針
- ADR-0019 の決定「タグ・地域・金額のフィルタはクエリパラメータとして GET に追加する」

決めるべき点は以下だった。

1. タグを複数指定したときの意味を AND（全タグを持つ）と OR（いずれかを持つ）のどちらにするか。
2. 不正な値（UUID 形式でない、件数超過）をエラーにするか、既存の `sort` / `order` / `q` のように安全側へ丸めるか。
3. repository の検索メソッドに条件をどう渡すか。ADR-0019 は地域・金額フィルタの追加も予定しており、条件はこの先も増える。
4. タグ条件の SQL 表現。JOIN で展開すると 1 イベントがタグ数ぶん重複し、既存の `COUNT(*)` が壊れる。

## 決定

**`GET /api/v1/events` に `tagId` を反復指定で受け付け、複数指定時は OR（いずれかのタグを持つイベント）で絞り込む。`q` とは AND で結合する。不正な UUID と 20 件超過は 400 を返す。repository へ渡す検索条件は `model.EventSearchFilter` に集約し、タグ条件は `EXISTS` + `IN` で表現する。**

1. **パラメータ**: `?tagId=<uuid>&tagId=<uuid>` の反復指定。`q` と同じ流儀に揃える。
2. **結合規則**: タグどうしは **OR**。キーワード条件とタグ条件は **AND**。
3. **検証**（service 層 `normalizeTagIDs`）:
   - trim 後に空の要素（`?tagId=`）は除去し、未指定として扱う
   - UUID として解釈できない値は `*ValidationError` → handler が 400 `invalid_request`
   - UUID 正準形（小文字ハイフン区切り）へ正規化し、順序を保持して重複除去する（既存 `dedupeTagIDs` を再利用）
   - 重複除去**後**の件数が 20 を超えたら `*ValidationError` → 400
4. **repository interface**: 検索系メソッドの引数を構造体へ集約する。
   ```go
   type EventSearchFilter struct {
       Keywords []string // AND 検索するキーワード
       TagIDs   []string // OR 条件のタグ UUID（正準形・重複除去済み）
   }
   func (f EventSearchFilter) IsEmpty() bool

   SearchSummaries(ctx, filter EventSearchFilter, sort, order string, limit, offset int) ([]EventSummary, error)
   CountSearchSummaries(ctx, filter EventSearchFilter) (int, error)
   ```
   `filter.IsEmpty()` が true のときだけ既存の全件経路（`ListSummaries` / `CountSummaries`）を使う。
5. **SQL**: タグ条件は 1 つの相関サブクエリにまとめる。
   ```sql
   EXISTS (SELECT 1 FROM event_tags et
           WHERE et.event_id = e.id AND et.tag_id IN ($n, $n+1, ...))
   ```
   プレースホルダ番号のみを動的生成し、値は必ず引数経由で渡す。
6. 全件経路の `ListSummaries` / `CountSummaries`（ソート順ごとのホワイトリスト文字列による完全静的 SQL）は変更しない。

## 理由

- **OR を選んだのは、タグチップを複数選択する UI で結果が消えないため**。イベントに付くタグは平均して数個で、`event_tags` の分布上「A と B を両方持つイベント」は「A を持つイベント」よりはるかに少ない。AND にすると 2 つ目のタグを選んだ瞬間に 0 件になる体験が頻発する。「興味のあるジャンルを複数選ぶ → 該当するものを広く見る」という一覧の絞り込み導線には OR が合う。キーワード（`q`）が AND なのは、語を足すほど対象を絞りたいという検索の意図が別だからで、両者で規則が違うのは意図的である。

- **不正値を 400 にするのは、黙って条件を捨てると誤動作に見えるため**。`sort` / `order` を安全側へ丸めるのは「並び順が既定に戻るだけで結果集合は変わらない」からで、絞り込み条件は事情が違う。存在しない条件として無視すると「絞り込んだのに全件返ってくる」挙動になり、クライアントは失敗に気づけない。投稿 API（`POST /api/v1/events`）のタグ ID 検証が同じ理由で 400 を返しており、扱いも揃う。

- **空文字だけ例外的に無視するのは、クエリ文字列の性質による**。`?tagId=` は「パラメータを送らない」と区別が付きにくく、フロントが未選択状態で `?tagId=${selected}` を組み立てると自然に発生する。キーワードの `normalizeKeywords` も空要素を除去しており、扱いを揃えた。「値が空＝未指定」は誤動作を招かない解釈である。

- **重複除去後に件数を判定するのは、同じタグの重複指定で上限に達しないため**。重複は正準形へそろえた時点で消えるので、実際にクエリへ載る条件数で判定する方が実態に合う。上限 20 件は ADR-0019 が URL 長の想定最大として挙げた件数に合わせた。

- **構造体へ集約したのは、この先フィルタが増えるため**。ADR-0019 は地域・金額フィルタの追加を予定している。引数を並べる形のままだと、
  ```go
  SearchSummaries(ctx, keywords []string, tagIDs []string, location string,
                  minCost, maxCost int, sort, order string, limit, offset int)
  ```
  のように同型の引数（`[]string` が 2 つ、`string` が 3 つ、`int` が 4 つ）が並び、**取り違えてもコンパイラも `go vet` も検出できない**。しかもこの種のバグは 500 にならず静かに違う結果を返す。構造体ならフィールド名で渡すため取り違えが起きず、条件追加時に既存の呼び出し側とテストスタブがコンパイルを通ったまま済む。今回の変更時点では呼び出し側が 3 箇所しか無く、どちらの案でも作業量は同等だったため、次の追加でコストが逆転する構造体案を採った。

- **`EXISTS` + `IN` にしたのは、行の重複を作らないため**。`JOIN event_tags` で展開すると、指定した複数のタグを持つイベントがタグ数ぶん重複して現れ、`SearchSummaries` の結果に同じイベントが並び、`CountSearchSummaries` の `COUNT(*)` も過大になる。`DISTINCT` を足せば消せるが、ソート・ページングとの組み合わせで意図を読み取りにくくなる。相関サブクエリなら外側の行は増えず、「持ち物は EXISTS のため行の重複は起きず `COUNT(*)` で正しい」という既存の前提をそのまま維持できる。

- **全件経路を触らないのは、その安全性を保つため**。`ListSummaries` は `listSummariesQueries` マップから固定文字列を選ぶだけで、動的な SQL 組み立てを一切行わない。条件が無いときの経路をこの形のまま残すことで、動的組み立てを行う範囲を「実際に条件が指定されたとき」に限定できる。

## 影響（結果）

### 良い影響

- 一覧に表示されているタグ（ADR-0015）をそのまま絞り込み条件として使えるようになり、タグの表示と検索が一貫した導線になる。
- 検索条件が URL に載るため、ADR-0019 が重視した「条件付き一覧 URL の共有・ブックマーク」がタグ絞り込みでも成立する。
- 条件は `EXISTS` に閉じるため行が重複せず、`totalCount` とページングが従来どおり正しく動く。
- 今後 ADR-0019 が予定する地域・金額フィルタは `EventSearchFilter` にフィールドを足すだけで追加でき、repository interface のシグネチャも呼び出し側も変わらない。
- 不正なタグ ID がクライアントのバグとして 400 で表面化するため、「絞り込みが効いていない」状態を見逃さずに済む。

### トレードオフ・制約

- **「複数タグをすべて持つ」絞り込みはできない**。OR を選んだ結果で、AND 相当の要件が出た場合は `tagMatch=all|any` のようなパラメータ追加を検討することになる（今回は仕様・テスト・ドキュメントの二重化を避けて見送った）。
- **`q` は AND、`tagId` は OR と規則が異なる**。直感的ではあるが自明ではないため、Swagger の `@Description` に明記して補っている。
- **空文字は無視、形式不正は 400 という非対称がある**。上述のとおり理由はあるが、`?tagId=` と `?tagId=abc` で挙動が分かれる点はクライアント実装者にとって驚きになり得る。
- **service 層 `List` の引数はまだ構造体化していない**。`List(ctx, keywords, tagIDs, sort, order, limit, offset)` は repository と同じ「同型引数が並ぶ」問題を抱えるが、呼び出し元が handler の 1 箇所のみのため今回は据え置いた。地域・金額フィルタを追加する際に、handler → service 境界にも同様の集約を行うか再検討する。
- **タグ ID の存在確認は行わない**。存在しないタグ ID を指定すると 0 件が返る（404 ではない）。絞り込み条件として自然な挙動であり、余分なクエリも避けられるため意図的にそうしている。
- **タグ数に比例してプレースホルダが増える**。上限 20 件で頭打ちになるが、`IN` のリストが長いほどプランナの選択が変わり得る。`event_tags` は複合 PK のインデックスが効くため現実的な件数では問題にならない。

## 検討した代替案

- **複数タグを AND（全タグを持つ）にする**: `q` が AND であることと規則が揃い、「絞り込み」という語義にも忠実。`EXISTS` をタグ数ぶん AND で並べれば実装も同程度に単純で、行の重複も起きない。しかしタグチップを複数選ぶ UI で結果が 0 件になりやすく、一覧の絞り込み体験として使いにくい。不採用。

- **`tagMatch=all|any` で切り替えられるようにする**: 両方の要件に応えられ、既定値を決めれば互換性も保てる。ただし現時点で AND を必要とする具体的な要件が無く、パラメータを増やすと仕様・テスト・OpenAPI・クライアント実装がその分二重化する。要件が出てから追加する（本 ADR の再検討対象）。不採用。

- **不正なタグ ID を無視して残りで検索する**: `sort` / `order` / `q` の既存方針と揃い、エラーハンドリングも増えない。しかし絞り込み条件が黙って落ちると「フィルタしたのに全件返る」誤動作に見え、クライアントは失敗を検知できない。投稿 API のタグ ID 検証とも扱いが割れる。不採用。

- **`SearchSummaries` に `tagIDs []string` 引数を足すだけにする**: 今回の差分は最小になる。しかし ADR-0019 が予定する地域・金額フィルタを足した時点で同型引数が並び、取り違えをコンパイラが検出できないシグネチャになる。フィルタ追加のたびに呼び出し側とテストスタブの全面修正も必要になる。不採用。

- **`JOIN event_tags` + `DISTINCT` で絞り込む**: 素直に書ける一方、複数タグを持つイベントが重複するのを `DISTINCT` で打ち消す構造になり、`COUNT(DISTINCT e.id)` への変更も必要で、既存の「行は重複しない」という前提が崩れる。ソート・ページングとの相互作用も読み取りにくい。不採用。

- **`tag_id = ANY($n::uuid[])` で配列を 1 プレースホルダにまとめる**: プレースホルダが 1 つで済み SQL も短い。しかし既存の `buildSearchWhere` / `attachTagsToSummaries` は「プレースホルダ番号のみ動的生成し、ドライバの配列エンコードには依存しない」流儀で統一されている（ADR-0015）。上限 20 件では `IN` の展開でも十分短く、既存の書き方に揃える利点の方が大きい。不採用。

- **タグ名（`name`）で絞り込めるようにする**: URL が人間に読めるようになる。しかしタグ名は変更され得るため URL の永続性が保証されず、正規化（`normalized_name`）を介した照合が必要になり、同名解決の曖昧さも持ち込む。一覧レスポンスが `id` と `name` の両方を返している（ADR-0015）ため、クライアントは ID を持っている。不採用。
