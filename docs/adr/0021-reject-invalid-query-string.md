# ADR-0021: 不正なクエリ文字列はミドルウェアで 400 を返す

- ステータス: Accepted
- 日付: 2026-08-04
- 関連: #158, ADR-0019（イベント検索は GET を維持する）, ADR-0020（イベント一覧のタグ絞り込み）

## コンテキストと課題

`GET /api/v1/events` にクエリパラメータを 10,001 件以上送ると、**全パラメータが黙って捨てられ 200 が返る**。

```
tagId 21件(別UUID)                    -> 400 タグIDは20件以内で指定してください
tagId 10001件パディング + q + limit=1 -> 200 totalCount=71 limit=20   # q も limit も消えている
```

原因は Go 側にある。`net/url.ParseQuery` はパラメータ数が 10,000 を超えるとエラーを返すが（`src/net/url/url.go` の `defaultMaxParams`）、`url.URL.Query()` はそのエラーを握りつぶして空マップを返す。そのため gin の `c.Query` / `c.QueryArray` からは「パラメータが指定されなかった」のと区別できない。判定式は `strings.Count(query, "&") + 1` で、超過時は 1 件もパースせずに返るため、**一部ではなく全条件が消える**。

この上限は **CVE-2025-61726**（Go 脆弱性DB GO-2026-4341 / golang/go #77101）のセキュリティ修正として導入された。`ParseQuery` に上限がなくメモリ枯渇 DoS になる問題への対処で、Go 1.24.12 / 1.25.6（2026-01-15）にバックポートされ、本プロジェクトが `go.mod` で pin している 1.26 系は GA 時点から含む。同じ silent drop に起因する派生 CVE-2026-39825（`httputil.ReverseProxy`）もあり、「上限超過が呼び出し側から見えない」ことは上流でもセキュリティ問題として扱われている。

これは #154 のタグ絞り込み実装中に発見されたが、**その変更が原因ではなく、`q` / `sort` / `order` / `limit` / `offset` を含む全パラメータ・全エンドポイントに効く既存の挙動**である。ただし ADR-0020 で確立した「条件を黙って捨てず 400 を返す」方針（タグ 21 件で 400）を、まさにその境界で裏切る形になっている。

`GET /api/v1/events` は認証不要の公開エンドポイントであり、リクエストの送り手は自社フロントに限らない。CLAUDE.md が定めるとおり信頼境界はサーバー側にあるため、**外部クライアントが「フィルタ済みのつもりの全件」を 200 で受け取る状態は API の契約として正しくない**。

## 決定

**`internal/middleware/query.go` に `ValidateQuery()` を新設し、`url.ParseQuery(RawQuery)` を明示的に実行してエラーなら 400（`invalid_query`）を返す。全ルートに適用する。**

1. `RawQuery` が空の場合は一切パースせず素通しする。
2. ミドルウェアチェーンでは必ず `NewCORS()` より後ろに置く。前に置くと 400 レスポンスに CORS ヘッダが付かず、ブラウザから 400 ではなく CORS エラーに見えるため。
3. 検査は構文レベルのみとし、未知のパラメータ名や値の妥当性は各ハンドラの責務とする。
4. エラーコードは新規に `invalid_query` を用いる。ハンドラ層の意味的バリデーションが使う `invalid_request`（既存 23 箇所）とは区別し、**ミドルウェア層が構文レベルで拒否したこと**を示す。これは `BodyLimit` が `request_too_large` という固有コードを持つのと同じ扱いで、既存の慣習からの逸脱ではない。クライアントはコードを見て「リクエストの組み立てが壊れている」と「入力値が業務ルールに反する」を区別できる。

## 理由

- **公開 API が嘘の 200 を返さないことを、アプリ自身で保証できる唯一の手段である**。前段プロキシの URL 長制限に頼る方法はインフラ依存で、`.claude/rules/docker.md` が掲げる AWS 移行時の可搬性方針に反する。

- **上限値 10000 を自前に複製しない**。`ParseQuery` のエラーをそのまま見るため、Go 側が将来上限を変更しても、`GODEBUG=urlmaxqueryparams` が設定されても判定が自動的に追随する。件数を自前で数える実装（後述の代替案A）はこの追随性を持たない。

- **カバー範囲が件数超過にとどまらない**。不正なパーセントエンコードや生セミコロンによる silent drop も同時に拾える。これらは今回の Go の変更以前から存在する挙動で、同じ「黙って捨てる」クラスの問題である。

- **性能上のコストが無視できる**。`internal/middleware/query_bench_test.go` で再計測できる（go1.26.4 / Core i5-12500、`-count=3` の代表値）。計測ハーネス（`ResponseRecorder` と `gin.Context` の生成）自体が約 480 ns を占めるため、**絶対値ではなく `BenchmarkBaseline_NoMiddleware` との差分**が本ミドルウェアの増分である。

  | ケース | 実測 | 基準値との差＝増分 |
  |---|---|---|
  | クエリなし | 約 488 ns / 12 allocs | ほぼ 0・**追加アロケーションなし** |
  | 典型的なクエリ | 約 882 ns / 18 allocs | 約 0.4 µs |
  | 現実的な最大構成（約 1.4KB） | 約 3.53 µs / 26 allocs | 約 3.1 µs |
  | 上限超過（10,001 パラメータ） | 約 1.42 µs / 22 allocs | 約 0.9 µs |

  最大構成でも増分は数 µs にとどまり、ミリ秒オーダーを占める DB 問い合わせに対して 1% に満たない。クエリなしのリクエストはショートサーキットで追加アロケーションが発生しないことも実測で確認している。

  なお本ミドルウェアの `ParseQuery` の結果は破棄され、ハンドラが `c.Query()` を呼ぶと gin が内部の `queryCache` 用に**同じ文字列をもう一度パースする**（gin のキャッシュは本ミドルウェアと共有されない）。したがってリクエスト全体でのパースコストは上表の増分のおおむね 2 倍だが、最大構成でも 6 µs 程度であり結論は変わらない。二重パースを避けるには gin の非公開フィールドへの介入が必要になるため採らない。

- **拒否が増幅経路にならない**。`parseQuery` は件数チェックをループの前に置いているため、上限超過時は 1 件もパースせずに返る（`ParseQuery` 単体では約 140 ns）。ただし**拒否パス全体では 400 レスポンスの JSON 生成が乗るため約 0.9 µs** となり、正常なクエリの通過（約 0.4 µs）より高くつく。それでも DB 問い合わせを伴う正常応答より 3 桁安いため、攻撃者が拒否そのものを負荷の増幅に使える非対称性は生じない。

## 影響（結果）

### 良い影響

- フィルタ条件が黙って捨てられたまま 200 が返る状態が解消される。
- `r.Use` で全ルートに適用されるため、将来クエリパラメータを追加するエンドポイントも自動的に保護される。ミドルウェアの付け忘れによる穴が生じない。
- 不正なパーセントエンコード・生セミコロンによる部分的な silent drop も同時に解消される。
- エラーレスポンスは既存の統一フォーマット（`model.NewErrorResponse`）に乗るため、クライアント側のエラーハンドリングに変更が要らない。

### トレードオフ・制約

- **正しいクエリのリクエストは挙動が変わらないが、壊れたクエリは 400 になる**。従来は壊れたペアだけを黙って無視して残りの条件で検索していた。とくに**パーセントエンコードされた日本語キーワードを含む共有 URL が切り詰められた場合**（`%E3%8` のような不完全エスケープ）、従来「その語だけ無視して一覧が出る」が「400 で何も出ない」に変わる。ADR-0019 が中核導線と位置づけた検索結果 URL の共有に関わるが、**「壊れた URL には部分結果より明確なエラーを返す」ことを選択した**。

- **クエリを読まないエンドポイントでも壊れたクエリで 400 になる**。現時点でクエリパラメータを読むハンドラは `internal/handler/event.go` の一覧のみで、他のエンドポイントにはそもそも silent drop のリスクがない。この範囲では正しさの利得がなく影響だけが増える。ただし `ParseQuery` がエラーになるのは `%` の後が 16 進 2 桁でない場合に限られ、`utm_source` や `fbclid` のようなトラッキングパラメータは英数字なので切り詰められてもエラーにならない。実際の発火条件は限定的と判断した。

- **構文レベルしか検査しない**。`limt=5` のような未知パラメータ名や打ち間違いは従来どおり黙って無視される。ここまで塞ぐには許可リスト管理が必要で、パラメータ追加のたびに保守コストが発生するため本 ADR のスコープ外とする。**このミドルウェアは「黙って捨てない」を完全には保証しない。**

- **クライアントから見て未知のエラーコードが 1 つ増える**。エラーコードで分岐しているクライアントは `invalid_query` を未知の値として既定の分岐で処理することになる。統一フォーマット自体は変わらないため表示は破綻しないが、コード一覧を共有しているクライアントには周知が要る。

- **エラーの粒度が粗い**。`ParseQuery` は最初のエラーのみを返し、どのパラメータの何文字目が不正かの位置情報を持たない。そのためメッセージは「クエリ文字列が不正です」程度にとどまり、ADR-0020 のタグ件数超過（「タグIDは20件以内で指定してください」）のような具体性は出せない。

- **`api/swagger.yaml` に現れない**。横断的な 400 は Swagger 2.0 でエンドポイント個別に表現できないため、ドキュメント上の根拠は本 ADR に置く。`make swag` の生成物に差分は出ない（ハンドラの godoc コメントを変更しないため）。

## 再検討の条件

1. 切り詰められた共有 URL 由来の 400 が実際に観測され、ユーザー導線の問題として顕在化した場合。
2. 未知のパラメータ名まで弾く要件が発生した場合（許可リスト方式の是非を含めて再検討する）。
3. Go 側が上限値または `URL.Query()` のエラー処理の挙動を変更した場合。

## 検討した代替案

- **`strings.Count(RawQuery, "&") + 1 > 10000` のみを検査する**:
  Go 側の判定式と完全に同一のため、今回の silent drop だけを正確に検知でき、パーセントエンコードやセミコロンの従来挙動を一切変えない（挙動変更ゼロ）。しかし上限値 10000 を自前に複製するため、Go 側の変更や `GODEBUG` 設定で判定がずれうる。この案の唯一の利点は「挙動を変えないこと」であり、切り詰められた共有 URL に 400 を返してよいと判断した時点で採用理由が消えた。不採用。

- **`GODEBUG=urlmaxqueryparams` で上限を引き上げる・無効化する**:
  上限そのものを外せば silent drop は起きなくなる。しかしこれは CVE-2025-61726 のメモリ枯渇 DoS 修正を自ら無効化することであり、公開エンドポイントにレート制限がない（`joinLimiter` は join のみ）現状では選択肢にならない。不採用。

- **`http.Server` の `MaxHeaderBytes` を絞る（既定 1MB → 64KB 等）**:
  本問題の解決にはならない。空セグメント `&` は 1 バイトで 1 パラメータに数えられるため、**最小の 10,001 パラメータリクエストは約 10KB** にしかならず、正当なトラフィック（Supabase JWT 約 1KB ＋ Cookie ＋ 通常ヘッダ）を壊さない値では重ならない。また 431 は `http.Server` 層で生の HTTP レスポンスとして直接書かれるため gin に到達せず、slog に残らず統一エラーフォーマットでもなく CORS ヘッダも付かない（Go のソース自身が、クライアントがこれを読めるかは不定と注記している）。ただし既定 1MB は資源消費の観点では過剰であり、**本問題とは独立した DoS ハードニングとして別 issue で検討する**。

- **前段のリバースプロキシ・WAF で URL 長を制限する（414）**:
  実務では最も一般的な防御で、nginx や ALB は既定でこの役を担う。しかしインフラ依存であり、Xserver VPS から AWS への移行のたびに前提が変わる。`.claude/rules/docker.md` の可搬性方針に反するため、アプリ側の保証としては採用しない（多層防御として前段に入れること自体は否定しない）。

- **適用対象を `GET /api/v1/events` のみに限定する**:
  現時点でクエリパラメータを読むハンドラは一覧のみなので、影響範囲を最小化できる。しかし将来クエリを追加するエンドポイントでミドルウェアの登録を忘れると同じ穴が再発する。フェイルセーフを優先して全ルート適用とした。不採用。
