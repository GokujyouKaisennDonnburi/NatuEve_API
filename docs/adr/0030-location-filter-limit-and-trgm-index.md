# ADR-0030: 地域絞り込みの上限を 200 件へ引き上げ、pg_trgm の GIN インデックスを導入する

- ステータス: Accepted
- 日付: 2026-08-22
- 関連: #192, ADR-0028（イベント一覧の地域絞り込み）, ADR-0019（イベント検索は GET を維持する）, ADR-0021（不正なクエリ文字列は 400）

## コンテキストと課題

ADR-0028 で `GET /api/v1/events` に `location` の絞り込みを導入した。上限は 50 件、インデックスは追加しないという判断だった。この判断は「地域は都道府県を並べる使い方が本質」という想定に基づいており、47 都道府県すべてを指定しても収まる 50 件を上限としていた。

その後、フロントの地域選択 UI が **地方 → 都道府県 → 市区町村の 3 階層チェックボックス**であることが判明した（「近畿」を開くと「兵庫」「和歌山」…が並び、「兵庫」を開くと「神戸」「明石」「姫路」「西宮」が並ぶ）。市区町村を個別に選べるため、**50 件を超える指定が現実に発生する**。

判断の材料として、次を実測した。

**1. URL 長**（クライアントが都道府県名・市区町村名を送る前提。市区町村は県名を前置）

| 選択 | 件数 | URL 長 |
|---|---|---|
| 「兵庫」全選択（配下 4 市を含む） | 1 | 36 文字 |
| 「近畿」全選択 | 7 | 267 文字 |
| 全国すべて | 47 | 1,765 文字 |
| 47 都道府県 + 各県 1 市 | 94 | 4,001 文字 |
| 47 都道府県 + 各県 3 市 | 188 | 8,473 文字 |

部分一致であるため、**県を全選択したときは県名 1 件で配下の市区町村をすべてカバーできる**。クライアントが「親が全選択なら親だけ送る」畳み込みを行えば、全国全選択でも 47 件で収まる。件数が膨らむのは「県の一部の市区町村だけを選ぶ」ケースに限られる。

**2. クエリ実行時間**（いずれも 10 万行の一時テーブル。`EXPLAIN ANALYZE` の Execution Time）

計測 A: インデックスの有無を比較する。`location` は 6 種類の値を循環させて生成したため、**47 件以上の指定は全行に一致する**。

| 指定 | インデックスなし | pg_trgm GIN あり | 採用プラン |
|---|---|---|---|
| 1 件 | 85.6 ms | **16.8 ms** | Bitmap Index Scan |
| 7 件 | 482.6 ms | **14.7 ms** | Bitmap Index Scan |
| 47 件（全行に一致） | 1,582.6 ms | 1,539.2 ms | Seq Scan |
| 188 件（全行に一致） | 1,551.9 ms | 1,537.5 ms | Seq Scan |

計測 B: プランの切り替わりが何で決まるかを見る。47 都道府県 × 各 50 市区町村（2,350 種類）で生成し、インデックスを張った状態で計測した。

| 指定 | 件数 | 一致する行 | 採用プラン | 実行時間 |
|---|---|---|---|---|
| 東京都 | 1 | 2.1% | Bitmap Index Scan | 1.9 ms |
| 関東 7 県 | 7 | 15% | BitmapOr + Index Scan | 34.0 ms |
| 東京都の 47 市区町村 | 47 | 2.1% | BitmapOr + Index Scan | **29.6 ms** |
| 47 都道府県すべて | 47 | 100% | Seq Scan | 1,255.3 ms |

**同じ 47 件でもプランが正反対になる**。インデックスが使われるかは指定件数ではなく選択率で決まり、件数の上限そのものが性能の閾値になるわけではない。

**3. クライアントが送る値の誤ヒット**

UI の表示名（`京都`・`兵庫`・`神戸`）をそのまま送ると、部分一致のため別地域に一致する。

| 保存値 | 表示名で一致 | 正式名称で一致 |
|---|---|---|
| `東京都渋谷区` | `京都` → **一致してしまう** | `京都府` → しない |
| `香川県高松市兵庫町` | `兵庫` → **一致してしまう** | `兵庫県` → しない |
| `岐阜県安八郡神戸町` | `神戸` → **一致してしまう** | `兵庫県神戸市` → しない |

決めるべき点は以下だった。

1. `location` の件数上限をいくつにするか。
2. インデックスを導入するか。導入するならどの方式か。
3. `POST /api/v1/events/search` を併設するか（ADR-0019 の段階論）。

## 決定

**`location` の上限を 200 件へ引き上げ、`pg_trgm` 拡張と `normalize(location, NFKC)` に対する GIN インデックスをマイグレーションで追加する。`POST /api/v1/events/search` は導入しない。**

1. **上限**: `maxFilterLocations` を 50 → **200** とする。超過時に 400 を返す扱いは ADR-0028 のまま変更しない。

2. **インデックス**: 次をマイグレーションで追加する。`normalize` は IMMUTABLE（`pg_proc.provolatile = 'i'`）のため式インデックスを作成できる。

   ```sql
   CREATE EXTENSION IF NOT EXISTS pg_trgm;
   CREATE INDEX events_location_trgm_idx
       ON events USING gin (normalize(location, NFKC) gin_trgm_ops);
   ```

   `buildSearchWhere` が生成する条件式（`normalize(e.location, NFKC) ILIKE $n`）とインデックスの式は**完全に一致していなければ使われない**。条件式を変更する場合はインデックス定義も同時に変更する。

   ロールバック（goose Down）ではインデックスのみ削除し、`pg_trgm` 拡張は残す。拡張は他の用途から参照されうるため、本マイグレーションが作ったオブジェクトだけを取り消す。

3. **クライアントが送る値**: 都道府県は正式名称（`京都府`、`東京都`）、市区町村は都道府県名を前置した形（`兵庫県神戸市`）を前提とする。`@Description` に明記し、API 利用者の責務とする。サーバー側では検証しない。

4. **`POST /api/v1/events/search` は今回導入しない**。ADR-0019 の段階論は維持する。

5. **クライアント側の最適化（親への畳み込み、全選択時の `location` 省略）は API の契約に含めない**。`@Description` で推奨として案内するにとどめる。

## 理由

- **上限 200 件は「県の一部の市区町村を選ぶ」最悪ケースから決めた**。畳み込みを行えば全国全選択でも 47 件だが、47 都道府県それぞれで数市ずつ選ぶと 188 件に達する。200 件はこれを収めた上での切りのよい値である。100 件では 94 件（各県 1 市）で早々に上限へ触れる。

- **pg_trgm を導入するのは、実運用で支配的な「少数指定」が劇的に速くなるため**。7 件指定で 482.6 ms → 14.7 ms（約 33 倍）。階層 UI で親に畳む前提なら、「近畿を見る」は 7 件、「兵庫を見る」は 1 件であり、この帯域が最も頻繁に使われる。

- **インデックスが使われるかは件数ではなく選択率で決まる**。計測 B のとおり、同じ 47 件でも東京都内の市区町村を並べた指定（一致 2.1%）ではインデックスが使われて 29.6 ms、全都道府県を並べた指定（一致 100%）では Seq Scan で 1,255.3 ms になる。後者でインデックスが使われないのはプランナの判断が正しく、全行に一致する条件をインデックス経由で辿るより順に読む方が安いためである。**これは「絞り込みとして全件取得と変わらないケース」であり、性能問題として扱うべきものではない**。クライアントが全選択時に `location` を送らなければ、そもそもこのクエリは発生しない。**上限 200 件まで使ってもインデックスが無効になるわけではない**点に注意する。

- **正式名称を前提にするのは、部分一致では誤ヒットをサーバー側で防げないため**。`東京都` は `京都` を部分文字列として含むため、表示名をそのまま送ると「京都で絞ったのに東京都のイベントが出る」。`府中市` のように複数県に同名の市区町村が存在するケースも同様で、県名の前置が必要になる。ADR-0028 が「投稿者の書き方に結果が左右される」と書いた制約の、クライアント側の対応物にあたる。

- **`POST /api/v1/events/search` を今回入れないのは、畳み込みで大半のケースが収まる見込みがあるため**。ADR-0019 の再検討条件①（クエリ文字列 4KB 超）は 94 件で到達するが、畳み込みを実装すれば通常の選択は 2KB 未満に収まる。エンドポイントを増やすとハンドラ・テスト・ドキュメント・クライアントの分岐が恒久的なコストになるため、畳み込みを入れた上で実データを観測し、4KB 超が実際に頻発してから判断する。

- **クライアント側の最適化を契約に含めないのは、サーバーが強制できないため**。畳み込みを行わないクライアントも仕様上は正しく、200 件の上限内であれば結果も正しい。契約に書けば守られる保証があるかのように読めてしまうため、推奨として案内する。

## 影響（結果）

### 良い影響

- 階層 UI での選択をそのまま送れるようになり、市区町村を跨いだ絞り込みが 50 件の壁で弾かれなくなる。
- 実運用で支配的な、選択率の低い指定が約 33 倍高速になる。10 万行規模でも 15 ms 前後で応答する。
- インデックスは API の契約を変えないため、クライアント側の変更を伴わない。
- `@Description` に値の規約を明記することで、`京都` を送って東京都が混ざる事故を防げる。

### トレードオフ・制約

- **GIN インデックスは書き込みを重くする**。イベントの投稿・更新のたびにトライグラムの転置索引が更新される。`events` は読み取りが圧倒的に多いテーブルであり許容するが、書き込み性能を測ったわけではない。

- **インデックスと WHERE 句の式が結合している**。`buildSearchWhere` の条件式を変更するとインデックスが黙って使われなくなり、エラーではなく性能劣化として現れる。ADR-0028 の `location` 条件式を変更する際は、このインデックスもあわせて変更する必要がある。

- **全行に一致する指定は依然として遅い**（10 万行で約 1.3 秒）。原因は件数の多さではなく選択率の高さ（全都道府県を並べるなど）である。プランナの判断としては正しいが、クライアントが全選択時に `location` を送ってしまうと発生する。畳み込み・省略の実装はクライアント側に委ねられており、サーバーからは強制できない。

- **200 件は ADR-0019 の再検討条件①を超える**。94 件でクエリ文字列 4KB に達するため、上限まで使われると条件①が成立する。本 ADR はその状態を許容した上で `POST /search` の導入を見送っており、**条件①の成立をもって自動的に POST を併設するわけではない**ことを明示しておく。

- **`pg_trgm` は PostgreSQL 固有の拡張である**。`.claude/rules/docker.md` が掲げる可搬性は Docker イメージについてのものであり、DB は PostgreSQL 前提（Xserver VPS → AWS RDS/Aurora）のため実害はないが、他の DBMS へ移る場合はインデックス戦略の再設計が必要になる。

- **正式名称の前提はサーバーが保証しない**。クライアントが `京都` を送れば東京都のイベントが混ざるが、サーバーからは正当なリクエストと区別できない。

## 再検討の条件

1. 畳み込みを実装した上でなお、実測でクエリ文字列 4KB 超が頻発する場合（`POST /api/v1/events/search` の併設を判断する。ADR-0019 決定 3）。
2. GIN インデックスの更新コストがイベント投稿・更新のレイテンシとして観測された場合。
3. 全行に一致する指定（全選択に近い指定）が実運用で頻発すると分かった場合（クライアント側の省略の徹底、またはサーバー側での「全件と等価な条件」の検出を検討する）。
4. 地域の正確な絞り込み・集計が要件になった場合（ADR-0028 再検討の条件 3 と同じく、`prefecture` の構造化を検討する）。

## 検討した代替案

- **上限を 100 件にとどめる**:
  クエリ文字列が 4KB 前後に収まり、ADR-0019 の再検討条件①をほぼ超えない。しかし「47 都道府県 + 各県 1 市」で 94 件に達し、少しでも市区町村を細かく選ぶと上限に触れる。UI が市区町村を個別に選べる以上、上限に触れる体験が頻発する方が問題である。不採用。

- **上限を撤廃する**:
  クライアントの選択をそのまま受け取れる。しかし URL 長・DB 負荷ともに自然な歯止めがなくなり、極端な指定でサーバーが 431（`MaxHeaderBytes` 1MB 超）を返す。431 は ADR-0021 が指摘したとおり gin に到達せず統一エラーフォーマットにならないため、クライアントから見て原因が分からない失敗になる。明示的な上限で 400 を返す方が良い。不採用。

- **pg_trgm を入れずに上限だけ引き上げる**:
  マイグレーションが不要で、PostgreSQL 固有の拡張への依存も増えない。しかし 10 万行規模で 200 件指定が約 6 秒（1 件あたり約 30 ms の実測から）となり、実用に耐えない。少数指定でも 85 ms かかり、インデックス導入時の 16.8 ms と差が大きい。不採用。

- **`POST /api/v1/events/search` を今回あわせて併設する**:
  URL 長の制約から完全に解放され、上限を件数だけで決められる。しかしエンドポイントが増える恒久コストに対し、畳み込みで大半が収まる見込みがある段階では時期尚早である。ADR-0019 の段階論も「クエリ文字列長が実際に問題となった場合」を条件としている。不採用（再検討の条件 1 で扱う）。

- **`(created_at DESC)` を含む複合インデックスにする**:
  既定ソートが `created_at DESC` であるため、絞り込みとソートを 1 つのインデックスで賄えれば理想的である。しかし GIN はトライグラムの転置索引であり、B-tree のような順序を持たないため複合にできない。中間一致を諦めて前方一致に切り替えれば B-tree の複合インデックスが作れるが、ADR-0028 が「入力形式の変更で静かに壊れる」として却下済みである。不採用。

- **クライアント側の畳み込みを API の契約として必須にする**:
  全行に一致する指定が発生しなくなり、性能の上限を設計で保証できる。しかしサーバーからは畳み込みの有無を検証できず、守られる保証のない契約になる。守らないクライアントのリクエストも上限内なら結果は正しいため、エラーにする根拠もない。推奨の案内にとどめる。不採用。
