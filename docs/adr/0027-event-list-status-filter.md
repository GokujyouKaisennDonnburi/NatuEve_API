# ADR-0027: イベント一覧の開催状況絞り込みは排他な 3 値の status で表す

- ステータス: Accepted
- 日付: 2026-08-21
- 関連: #178, ADR-0020（イベント一覧のタグ絞り込み）, ADR-0018（終了日時の任意入力と既定値）, ADR-0024（マイページのイベント一覧）, ADR-0019（検索は GET を維持する）

## コンテキストと課題

イベント一覧 `GET /api/v1/events` が受け取るのは `q`・`tagId`・`sort`・`order`・`limit`・`offset` だけで、**開催状況で絞り込む手段が無い**。

そのためクライアントが「開催前のイベントだけ見たい」を実現するには、返ってきたレスポンスを自前でフィルタするしかない。これは `limit` で切り出した後の集合に対する絞り込みになるため、20 件取得して開催前が 3 件なら 3 件しか表示できず、`totalCount` も絞り込み前の値のままページネーションが破綻する。既に `q` と `tagId` は WHERE 句でサーバー側絞り込みを行っており（ADR-0020）、開催状況だけがこの原則から外れている状態だった。

前提として揃っているもの:

- `events.event_date` / `events.end_date` はともに `NOT NULL` で、`CHECK (end_date >= event_date)` を持つ（`db/migrations/20260622140000_create_events.sql`）。ADR-0018 が「今後の期間検索・開催中判定を NULL 分岐なしで実装できる」ことを明示的な利点として挙げている。
- 反復指定のクエリパラメータを OR で結合し、条件を `model.EventSearchFilter` へ集約する枠組み（ADR-0020）。
- 絞り込み条件の不正値は黙って捨てず 400 を返すという方針（ADR-0020、ADR-0021）。

決めるべき点は以下だった。

1. パラメータ名と値の語彙。
2. 「開催中」をどう扱うか。開催前・開催後の 2 値にすると、**複数日開催のイベントが会期中はどちらにも該当せず、どのタブにも表示されない**穴ができる。
3. 将来足しうる軸（レポートの有無、キャンセル済み）を同じパラメータに載せるか。
4. 不正値をエラーにするか、`sort` / `order` のように安全側へ丸めるか。

## 決定

**`GET /api/v1/events` に `status` を反復指定で受け付け、`upcoming` / `ongoing` / `ended` の排他な 3 値で開催状況を表す。値どうしは OR、`q` / `tagId` とは AND で結合する。許可値以外は 400 を返す。**

1. **パラメータ**: `?status=upcoming&status=ongoing` の反復指定。`tagId` と同じ流儀に揃える。未指定なら開催状況では絞り込まない。

2. **値と判定条件**: `end_date >= event_date` の CHECK があるため、この 3 値は**排他かつ網羅**（どのイベントも必ず 1 つだけに該当する）。

   | 値 | 意味 | 条件 |
   |---|---|---|
   | `upcoming` | 開催前 | `e.event_date > now()` |
   | `ongoing` | 開催中 | `e.event_date <= now() AND e.end_date >= now()` |
   | `ended` | 開催後 | `e.end_date < now()` |

3. **結合規則**: `status` どうしは **OR**。キーワード条件・タグ条件とは **AND**。

4. **検証**（service 層 `normalizeStatuses`）:
   - trim 後に空の要素（`?status=`）は除去し、未指定として扱う（`normalizeTagIDs` と同じ）
   - 許可値との照合は完全一致とする。`UPCOMING` のような大文字表記は不正値として 400 にする（`sort` / `order` / `type` と揃える。`tagId` が表記ゆれを吸収するのは UUID に正準形が定義されているためで、列挙値には当てはまらない）
   - 許可値以外は `*ValidationError` → handler が 400 `invalid_request`
   - 重複は除去する。値は 3 種しかないため、`tagId` のような件数上限は設けない
   - 重複除去後は定義順（`upcoming` → `ongoing` → `ended`）へ並べ替える。指定順に依存せず同じ SQL が生成され、テストが安定する

5. **条件の集約**: `model.EventSearchFilter` に `Statuses` を追加し、`IsEmpty()` の判定に含める。`status` だけが指定された場合も検索経路（`SearchSummaries` / `CountSearchSummaries`）に乗るため、`totalCount` は絞り込み後の件数になる。

6. **SQL**: 値ごとの条件を OR で括り、1 つの括弧として他条件と AND 結合する。条件式はホワイトリスト由来の定数のみで組み立て、ユーザー入力は文字列連結しない。

   ```sql
   (e.event_date > now() OR (e.event_date <= now() AND e.end_date >= now()))
   ```

7. **スコープ外**: キャンセル済みイベント（`cancelled_at IS NOT NULL`）の扱いは本 ADR では変更せず、従来どおり一覧に含めて `cancelledAt` でクライアントに判別させる。レポートの有無による絞り込みも扱わない。

8. **インデックスは追加しない**。

## 理由

- **2 値ではなく 3 値にしたのは、開催中のイベントを取りこぼさないため**。当初は必要なのが開催前・開催後の 2 つだったが、`upcoming` を `event_date > now()`、`ended` を `end_date < now()` と厳密に定義すると、会期中のイベント（`event_date <= now() <= end_date`）がどちらの条件にも該当しない。フロントが「開催前」「開催後」のタブを作ると、複数日開催のイベントは会期中どこにも表示されなくなる。`ongoing` の実装コストは WHERE 条件が 1 本増えるだけで、後から足す場合の issue・PR・再テストのコストより明確に安い。

- **3 値を排他かつ網羅にしたことが、この設計の要になっている**。`end_date >= event_date` の CHECK があるおかげで境界が重ならず、`?status=upcoming&status=ongoing&status=ended` は未指定と同じ結果になる。クライアントは「開催前と開催中」のようなタブを OR の指定だけで組み立てられ、サーバー側に「終了以外」のような合成値を持たなくて済む。

- **`GET /api/v1/me/events` の applied / attended と同じ `end_date` 二分にはしなかった**。あちらは `e.end_date >= now()` / `e.end_date < now()` で切っており（ADR-0024）、開催中を「申し込み中」側に含める。この境界をそのまま持ち込めば 2 値で網羅できたが、`upcoming` が「開催中を含む」意味になり、後から `ongoing` を足すときに `upcoming` の意味を変える破壊的変更が要る。マイページは「自分が関わるイベントを済・未済で二分する」画面、一覧は「開催状況で絞る」画面で目的が違うため、境界が異なること自体は許容する。

- **`status` という名前と、軸を混ぜないこと**。開催状況は日時から導出される時間軸だが、レポートの有無は `reports.event_id`（UNIQUE、`internal/repository/report.go:16`）の存在という独立した真偽値で、キャンセルは `cancelled_at` というさらに別の軸である。これらを `status` の値として並べると `?status=ended` と `?status=reported` が排他になり、「開催後でレポート未投稿」が表現できなくなる。時間軸だけを `status` が担い、他の軸は別パラメータで直交させる。名前が汎用的なぶん値を吸い込む引力があるため、swag の `@Description` に「開催状況（時間軸）のみ」と明記して運用で抑える。

- **許可値以外を 400 にするのは、絞り込み条件を黙って捨てないため**。`sort` / `order` を既定値へ丸めてよいのは並び順が変わるだけで結果集合が変わらないからで、絞り込み条件は事情が違う。無視すれば「開催前で絞ったのに全件が 200 で返る」ことになり、クライアントは失敗に気づけない。ADR-0020 のタグ ID、ADR-0021 の構文エラーと同じ扱いに揃える。

- **インデックスを張らないのは、現状の規模で効果が見込めないため**。一覧の既定は `ORDER BY e.created_at DESC LIMIT 20` であり、`event_date` / `end_date` の単独インデックスではソートに使えず、絞り込みで得られる選択率も高くない（`ended` は将来的にテーブルの大半を占める）。実効するには `(created_at DESC)` との複合や部分インデックスの設計が要り、それは実測なしに決めるべきではない。現時点のデータ量では Seq Scan で十分と判断する。

## 影響（結果）

### 良い影響

- 開催状況の絞り込みが WHERE 句で行われるため、`limit` は絞り込み後の集合に効き、`totalCount` も一致する。クライアント側のページ内フィルタが不要になる。
- 3 値が排他かつ網羅なので、フロントのタブ構成（開催前 / 開催中 / 開催後、あるいは「開催前＋開催中」の 2 タブ）を OR の反復指定だけで表現できる。
- `q` / `tagId` と同じ `EventSearchFilter` に乗るため、`SearchSummaries` と `CountSearchSummaries` の両方へ同じ条件式が適用される。条件の追加漏れで一覧と `totalCount` が食い違うことがない（`now()` の評価タイミングに起因する境界上のずれについては後述）。
- 値の追加・変更が service 層のホワイトリストと repository の条件式に閉じており、他の絞り込み条件と干渉しない。

### トレードオフ・制約

- **`endDate` を指定せず投稿された単日イベントは、開始時刻を過ぎた瞬間に `ended` になる**。ADR-0018 により `endDate` 省略時は `eventDate` と同値が入るため、10 時開始の日帰り観察会は 10:00:01 時点で `ended` に分類され、`ongoing` には一瞬しか該当しない。「本日開催中」を実用的に拾いたい場合、投稿側で `endDate` を入れる運用が前提になる。これは ADR-0018 が「単日と所要時間ゼロを区別できない」として許容したトレードオフの帰結であり、本 ADR で新たに作った制約ではないが、`status` を通じて初めてユーザーの目に見える形になる。

- **境界の判定は `now()` に依存し、1 リクエスト内でも一貫しない**。`SearchSummaries` と `CountSearchSummaries` は明示的なトランザクションを張らず個別に発行されるため、PostgreSQL の autocommit では両者の `now()` がそれぞれ独立に評価される。境界上のイベントは `totalCount` と実際に返る一覧の間でずれうる。ページングの途中で時刻が進めば、ページ間での重複・欠落も起きる。いずれもミリ秒オーダーの窓でしか成立せず、`created_at` 降順の既定ソートでは実害が小さいため許容する。両者を一貫させるには読み取り専用の一覧を単一トランザクションに包む必要があり、得られる正確性に対してコストが見合わない。

- **同一プロダクト内に「終わったイベント」の境界が 2 つ存在する**。一覧の `ended`（`end_date < now()`）とマイページの attended（同じ式だが開催中を applied 側に含める二分）は、開催中イベントの扱いが異なる。両者を統一する要件が出た場合は ADR-0024 とあわせて再検討する。

- **キャンセル済みイベントが各 status に混ざる**。`?status=upcoming` の結果にキャンセル済みイベントが含まれ、クライアントが `cancelledAt` で除外する必要がある。既存挙動の据え置きであり本 ADR で悪化はしないが、`status` を導入したことで「キャンセル済みも status で扱えるはず」という期待は生じる。

- **インデックスが無いため、`events` の行数が増えると日付条件のスキャンコストが線形に増える**。

## 再検討の条件

1. `events` の行数が増え、`status` 付きの一覧が実測で遅くなった場合（複合インデックスまたは部分インデックスを設計する）。
2. キャンセル済みイベントを絞り込みたい要件が出た場合（`status` の値にせず、別パラメータで直交させる方針を維持できるか検証する）。
3. レポートの有無による絞り込みを実装する場合（`hasReport` 等の別パラメータとして設計する）。
4. 「本日開催」を実用的に扱う要件が出た場合（ADR-0018 の `endDate` 補完仕様とあわせて再検討する）。

## 検討した代替案

- **`upcoming` / `ended` の 2 値のみとし、`ongoing` は別 issue に切る**:
  当初の合意案。今回必要な要件だけを満たし、`ongoing` は値の追加だけで後から足せる（既存 2 値の意味が変わらないため破壊的変更にならない）。しかし会期中のイベントがどちらにも該当しない期間が生まれ、フロントのタブから消える。この穴を抱えたまま先送りする理由が、条件式 1 本ぶんの実装コストに見合わない。不採用。

- **`upcoming` を「まだ終わっていない」（`end_date >= now()`）と定義して 2 値で網羅する**:
  `ended` と補集合になり穴が消え、ADR-0024 の applied / attended と境界が揃う。しかし `upcoming`（開催前）という語が開催中を含むことになり、名前と意味が乖離する。さらに将来 `ongoing` を足すには `upcoming` の意味を狭める破壊的変更が必要で、既にリリースしたクライアントの表示が黙って変わる。不採用。

- **`from` / `to` の日付範囲パラメータにする**:
  カレンダー UI との相性がよく、「今週末のイベント」のような要求にも同じ仕組みで応えられる。しかし開催前・開催後を表現するにはクライアントが現在時刻を渡す必要があり、**開催状況の定義がクライアント側に漏れる**。クライアントの時計のずれがそのまま結果のずれになり、CLAUDE.md の「ドメインロジックは API サーバーに集約する」に反する。期間指定は開催状況とは別の要件として、必要になった時点で追加する。不採用。

- **`status` の値に `cancelled` や `reported` を含める**:
  パラメータが 1 つで済み、フロントは値を 1 つ選ぶだけでタブを切り替えられる。しかし時間軸と直交する軸を排他な列挙に押し込むことになり、「開催後でレポート未投稿」「開催前でキャンセル済み」といった組み合わせが表現できない。後から分離するのは破壊的変更になる。不採用。

- **不正値を `sort` / `order` と同様に無視して全件返す**:
  実装は最も単純で 400 の分岐が要らない。しかし絞り込んだつもりのクライアントに全件が 200 で返り、失敗に気づけない。ADR-0020・ADR-0021 が一貫して否定してきた挙動であり、ここだけ例外にする理由がない。不採用。

- **`phase` など時間軸専用の名前にする**:
  名前自体が時間軸に限定されることを示すため、他の軸が値として混入する引力を構造的に断てる。しかし API 利用者にとって `status` ほど推測しやすくなく、フロント側で毎回ドキュメントを引く手間が増える。命名の一般性を優先し、軸の限定は `@Description` と本 ADR で担保する。不採用。
