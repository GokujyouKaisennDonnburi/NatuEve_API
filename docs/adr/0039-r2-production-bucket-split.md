# ADR-0039: R2 の本番用バケットを新しく作り、今のバケットをローカル開発と検証環境で使う

- ステータス: Accepted
- 日付: 2026-10-25
- 関連: #247, #239, #41, #219, ADR-0036, NatuEve_Web_Frontend#353
- 変更: ADR-0036 の決定事項 4 のうち R2（検証用の専用バケット）を、ローカル開発用のバケットの共用に変える

## コンテキストと課題

R2 は本番とローカル開発で同じバケット・同じ公開ドメイン（`assets.natuportal.org`）を使っていた（#239）。
この状態には次の問題があった。

- 開発者の `.env` のトークンで、本番のファイルを書き換え・削除できる。
- ローカル開発で上げたファイルも本番のドメインで配信され、キーでは本番のファイルと区別できない。
- GC（#41）や手作業の削除が、本番とローカル開発の両方のファイルに効く。

前提:

- 本番は公開前で、今のバケットには開発中に上げたファイルしかない。ほかのプロダクトは今のバケットを使っていない。
- R2 のトークンは対象をバケット単位で絞れる。プレフィックス単位で絞れるという記載は公式にない。

## 決定

**本番用のバケットを新しく作り、`assets.natuportal.org` を付け替える。
今のバケットはローカル開発と検証環境で使い、公開ドメインを `assets-dev.natuportal.org` にする。**

1. トークンはバケットごとに発行し、対象をそのバケットだけにする。クライアント IP アドレスによる制限はかけない。
2. 本番用のバケットの CORS は、本番のフロントのオリジン（`https://natueve-web.natuportal.org`）だけを許可する。
3. ライフサイクルルール（`natueve/tmp/` を 1 日後に削除）は両方のバケットに付ける。
4. 検証環境もローカル開発用のバケットを使う。トークンは検証環境用に別に発行し、対象はローカル開発用のバケットだけにする。
5. API のコードは変えない。バケットと公開ドメインは環境変数（`R2_BUCKET`・`R2_PUBLIC_BASE_URL`）で切り替える。
6. フロントの画像の許可リストには、開発用のドメインを開発時だけ加える（NatuEve_Web_Frontend#353）。

## 理由

- バケットを分ければ、トークンの対象をバケット単位で絞れる。開発者の `.env` が漏れても本番のファイルには届かない。
- 今のバケットを開発用にすると、手元の DB のイベントが指すファイルはそのまま残る。開発者は `R2_PUBLIC_BASE_URL` を替えるだけで既存の画像を表示できる。
- 本番は空のバケットから始まり、開発中に上げたファイルが混ざらない。公開後に分けると、混ざったファイルをキーで見分けられない。
- 検証環境との共用: 開発用のバケットは、もともと開発者それぞれの DB から参照されている。検証環境の DB が加わっても本番には届かない。
  バケット・公開ドメイン・フロントの許可を増やさずに済む。
- IP 制限をかけない理由:
  - Cloud Run から外へ出る通信の IP は固定されていない（固定には VPC・Cloud NAT・静的 IP が要る）。
  - presign の URL は本番用のトークンの鍵で署名され、利用者のブラウザから R2 へ送られる。トークンの IP 制限がこの URL に効くかは公式に記載がなく、効く場合は利用者のアップロードがすべて失敗する。

## 影響（結果）

### 良い影響

- 開発者のトークンで本番のファイルを書き換え・削除できなくなる。
- 本番のバケットは本番の DB だけが参照するため、GC（#41）を本番に対して動かせる。
- 本番の公開ドメインと保存キーの形式は変わらない。フロントの本番の許可リスト（`assets.natuportal.org`、#351 の `pathname`）はそのまま使える。

### トレードオフ・制約

- バケットの設定（公開ドメイン・CORS・ライフサイクルルール）はダッシュボードで行い、リポジトリには無い。バケットを作るときは揃える。
- 開発者は `.env` の `R2_PUBLIC_BASE_URL`（トークンを発行し直した場合はトークンも）を切り替える必要がある。
- フロントは NatuEve_Web_Frontend#353 が入るまで、ローカル開発で実 API の画像を表示できない。
- ローカル開発用のバケットは、開発者それぞれの DB と検証環境の DB から参照される。DB に無いキーを孤立とみなす GC（#41）は、このバケットには使えない。
- 検証環境のフロントのオリジンを、ローカル開発用のバケットの CORS に加える。
- 本番用のトークンの保護は、対象のバケットを絞ることと Secret Manager での管理に頼る。

## 検討した代替案

- **同じバケットでプレフィックスを分ける**: キーの先頭 `natueve/` が `internal/service/upload.go` に直書きされており改修が要る。
  トークンをプレフィックスで絞れず、開発者のトークンで本番のファイルを書き換え・削除できる状態が残る。不採用。
- **ローカル開発用のバケットを新しく作り、今のバケットを本番用にする**: 手元の DB のイベントが指すファイルが新しいバケットに無く、
  DB の作り直しかファイルのコピーが要る。本番のバケットに開発中のファイルが残る。不採用。
- **検証環境に専用のバケットを作る（ADR-0036 の決定事項 4）**: 検証環境のファイルを開発者の DB と分けられるが、
  バケット・公開ドメイン・トークン・フロントの許可が 1 組増える。本番に届かない点は共用でも変わらない。不採用。
- **本番用のトークンにクライアント IP アドレスの制限をかける**: 「理由」のとおり。不採用。
