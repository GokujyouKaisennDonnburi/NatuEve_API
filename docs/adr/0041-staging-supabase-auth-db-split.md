# ADR-0041: 検証環境の Supabase は本番と同じく Auth と DB を別のプロジェクトにし、Auth はローカル開発と共有する

- ステータス: Accepted
- 日付: 2026-10-27
- 関連: #254, #214, ADR-0036
- 変更: ADR-0036 の決定事項 5（検証用の DB と Auth を 1 つのプロジェクトにまとめ、NatuPortal の共有 Auth と同じアカウントに置く）を置き換える

## コンテキストと課題

ADR-0036 の決定事項 5 は、検証用の DB と Auth を 1 つのプロジェクトにまとめ、NatuPortal の共有 Auth と同じ Supabase アカウントに置くとしていた。
一方、本番は Auth（NatuPortal の共有 Auth）と DB が別のプロジェクトにある（#214）。
ローカル開発は、個人の Supabase アカウントにある開発用の Auth 用プロジェクトを使っている。

検証環境の初期設定（#254）で、検証環境の Supabase をどう置くかを決め直した。

## 決定

**検証環境の Supabase は、本番と同じく Auth と DB を別のプロジェクトにする。Auth はローカル開発の Auth 用プロジェクトを共有する。**

1. 検証環境の Auth（`SUPABASE_JWKS_URL`）は、ローカル開発で使っている Auth 用プロジェクトを使う。
2. 検証用の DB（`DATABASE_URL`）は、Auth とは別のプロジェクトとして作る。Data API は無効にする。
3. どちらも個人の Supabase アカウントに置く。なちゅいべ Org とも、NatuPortal の共有 Auth があるアカウントとも別。
4. 本番の共有 Auth を使わないこと、検証用 DB に本番のデータをコピーしないことは ADR-0036 のまま。

## 理由

- 本番と同じ構成にし、環境ごとの構成の違いによる混乱を減らす。
  `SUPABASE_JWKS_URL` は Auth 用、`DATABASE_URL` は DB 用のプロジェクトを指す、という対応がどの環境でも同じになる。

## 影響（結果）

### 良い影響

- ADR-0036 の「検証環境と本番の構成の差」（検証用は DB と Auth が同じプロジェクト）がなくなる。
  Data API を塞ぐ設定の確認は、本番と同じく DB 用のプロジェクトだけで済む。
- 本番の共有 Auth のアカウントに、検証用のプロジェクトを足さずに済む。

### トレードオフ・制約

- ローカル開発と検証環境で Auth を共有する。ローカル開発で発行したトークンで検証環境の API を呼べ、テスト用のアカウントも共有になる。
- 検証用 DB はローカル開発の DB と別のため、同じ Auth のユーザーでも、DB にあるプロフィールなどは環境ごとに別になる。
- 個人アカウントの Free の枠（アクティブなプロジェクト 2 つ。ユーザーごとに数える）のうち、Auth 用と検証用 DB で 2 つを使う。

## 検討した代替案

- **DB と Auth を 1 つのプロジェクトにまとめる（ADR-0036 の決定事項 5）**: プロジェクトが 1 つで済むが、本番と構成が違い、
  接続先の対応や Data API の確認が環境ごとに変わる。不採用。
- **検証専用の Auth 用プロジェクトを作る**: ローカル開発とトークン・アカウントを分けられるが、個人アカウントのアクティブなプロジェクトが 3 つになり、
  Free の枠（2 つ）に収まらない。不採用。
