# ADR-0028: イベント一覧の地域絞り込みは location への部分一致で行う

- ステータス: Accepted（決定事項 7 と、決定事項 4 の上限値 50 件は [ADR-0030](./0030-location-filter-limit-and-trgm-index.md) により Superseded。決定事項 4 のその他の規則（trim・空要素除去・重複除去・255 文字上限）は有効）
- 日付: 2026-08-21
- 関連: #180, ADR-0019（イベント検索は GET を維持する）, ADR-0020（イベント一覧のタグ絞り込み）, ADR-0027（開催状況の絞り込み）, ADR-0008（検索は ILIKE 部分一致＋NFKC 正規化）

## コンテキストと課題

イベント一覧 `GET /api/v1/events` は `q`・`tagId`・`status`・`sort`・`order`・`limit`・`offset` を受け取るが、**地域で絞り込む手段が無い**。ADR-0019 は「タグ・地域・金額のフィルタはクエリパラメータとして追加する」と決めており、地域については「`location`（自由文字列、最大 255 文字）」を想定していた。

前提と制約は次のとおり。

1. **`events.location` は自由入力の文字列で、地域マスタは存在しない**。フロントの入力は必須で、現在は「県＋市区町村＋自由記述」の形式で入る（例: `東京都新宿区新宿御苑`）。ただしこの形式は今後変わりうる。
2. **`q` は既に `location` を横断検索している**。`q` はタイトル・詳細・主催者名・地域名・持ち物の 5 項目を OR で横断するため、`q=東京` では詳細に「東京から 2 時間」と書かれた長野のイベントも該当する。地域で絞る用途には精度が足りない。
3. **地域データの実運用実績が無い**。`events` 942 行のうち `location` が埋まっているのは 9 行で、いずれもテストデータである（残り 933 行は NULL の旧テストデータ）。構造を変えるなら移行コストが最も低い時点にある。
4. ADR-0020 以降、絞り込み条件は `model.EventSearchFilter` へ集約し、反復指定を OR で結合する枠組みが確立している。

決めるべき点は以下だった。

1. 地域を自由文字列のまま扱うか、都道府県として構造化するか。
2. 照合方法（部分一致か前方一致か）。
3. 反復指定の結合規則と件数上限。

## 決定

**`GET /api/v1/events` に `location` を反復指定で受け付け、`events.location` への NFKC 正規化つき部分一致（ILIKE）で絞り込む。複数指定時は OR、`q` / `tagId` / `status` とは AND で結合する。上限は 50 件とし、超過は 400 を返す。**

1. **パラメータ**: `?location=東京都&location=神奈川県` の反復指定。未指定なら地域では絞り込まない。

2. **照合**: `q` と同じ規則に揃える。カラム側は `normalize(e.location, NFKC)`、入力側は NFKC 正規化 → LIKE エスケープ → `%` で囲む の順で処理し、`ILIKE` で大文字小文字を無視する（ADR-0008）。`q` が 5 項目を横断するのに対し、こちらは `location` のみを対象とする。

   ```sql
   normalize(e.location, NFKC) ILIKE $n
   ```

3. **結合規則**: `location` どうしは **OR**。キーワード条件・タグ条件・開催状況条件とは **AND**。

4. **検証**（service 層 `normalizeLocations`）:
   - trim 後に空の要素（`?location=`）は除去し、未指定として扱う（`normalizeTagIDs` / `normalizeStatuses` と同じ）
   - 重複を除去する。判定キーは NFKC 正規化＋小文字化した値とし（`東京都` と全角表記、`Tokyo` と `TOKYO` を同一視）、SQL へ渡すのは最初に現れた入力値そのものとする
   - 重複除去**後**の件数が `maxFilterLocations`(50) を超えたら `*ValidationError` → handler が 400 `invalid_request`。`q` のように切り捨てない
   - 1 要素あたりの文字数は `events.location` と同じ 255 文字を上限とし、超過は 400 とする

5. **条件の集約**: `model.EventSearchFilter` に `Locations []string` を追加し、`IsEmpty()` の判定に含める。

6. **NFKC 正規化の共有**: 重複除去の判定キー（service 層）と ILIKE パターン（repository 層）は同一の正規化形である必要があるため、既存の `normalizeSearchText` を `repository.NormalizeSearchText` として公開し、両層で共有する。正規化のためだけの共通パッケージは設けない。

7. **インデックスは追加しない**。

8. **`prefecture` のような構造化カラムは追加しない**。

## 理由

- **地域を構造化しなかったのは、入力形式が変わりうるうえ、後から加算的に足せるため**。現在は「県＋市区町村＋自由記述」だが、この前提は運用で変わりうる。`location` への部分一致は形式に依存しないため、形式が変わっても壊れない。将来「都道府県で確実に絞る」要件が出たら `prefecture` を**別のクエリパラメータとして追加**でき、`location` と共存する。既存パラメータの意味を変えないので破壊的変更にならない。実運用データが無い今なら構造化のコストも低いが、それは「今やらなければ二度とできない」ことを意味しない。

- **前方一致（`LIKE '東京都%'`）にしなかったのは、形式変更で静かに壊れるため**。「県が必ず先頭に来る」前提を SQL に埋め込むと、インデックスは効くようになるが、入力形式が変わった瞬間に絞り込みがエラーではなく**ヒットしない**形で壊れる。検知が難しい壊れ方であり、942 行という現在の規模で得られる速度の利得に見合わない。

- **`q` と分けるのは精度のため**。`q` の 5 項目横断は「関連しそうなものを広く拾う」検索の意図に合っているが、地域の絞り込みは「その地域のイベントだけを見る」という別の意図を持つ。対象を `location` 1 項目に限定することで、詳細文中の地名による誤ヒットを避けられる。パラメータを分けることで、クライアントは両者を AND で組み合わせられる。

- **OR を選んだのは、複数地域をまとめて検索する導線があるため**。「関東のイベントを一括で見る」ように、複数の県を選んで横断的に探す使い方が想定される。ADR-0020 がタグで OR を選んだのと同じく、「候補を複数選ぶ → 該当するものを広く見る」導線には OR が合う。

- **上限を 50 件としたのは、47 都道府県すべてを指定しても収まるため**。地方ブロック単位のまとめ検索（関東 7 県など）はもちろん、全都道府県を並べる指定も許容される。`tagId` の 20 件より緩いが、地域は「網羅的に並べる」使い方が本質的にありうる点が異なる。

- **件数超過を切り捨てず 400 にするのは、絞り込み条件を黙って捨てないため**。ADR-0020・ADR-0027 と同じ扱いに揃える。

- **1 要素 255 文字の上限は、`events.location` の桁と揃えたもの**。それを超える入力はどのレコードにも一致しえないため、無駄なスキャンを避ける意味でも早期に弾く。

- **インデックスを張らないのは、現在の規模で効果が見込めないため**。中間一致（`%x%`）は B-tree インデックスが効かず全行スキャンになるが、`events` は 942 行であり実測で問題が出ていない。必要になった時点で `pg_trgm` の GIN インデックスを追加すれば、中間一致のままインデックスを効かせられる。これは後から加算的に導入でき、API の契約を変えない。ADR-0027 と同じ判断である。

## 影響（結果）

### 良い影響

- 地域の絞り込みが WHERE 句で行われるため、`limit` は絞り込み後の集合に効き、`totalCount` も一致する。
- 対象を `location` に限定したことで、`q` では避けられなかった詳細文中の地名による誤ヒットが起きない。
- 複数県の OR 指定により、地方ブロック単位のまとめ検索をクライアント側の値の並べ方だけで実現できる。サーバーに「関東」のようなブロック定義を持たなくて済む。
- マイグレーションも投稿 API の変更も伴わないため、既存クライアントへの影響がない。

### トレードオフ・制約

- **投稿者の書き方に結果が左右される**。`location` に「新宿御苑」とだけ書かれたイベントは `?location=東京都` では該当しない。フロントの入力形式（県＋市区町村＋自由記述）が守られている限り実用上の問題は小さいが、サーバー側でこれを保証する手段は無い。地域の正確性を API が保証したい場合は `prefecture` の構造化が必要になる。

- **表記ゆれを吸収できない**。`東京` と `東京都`、`神奈川` と `神奈川県` は別の文字列として扱われる（部分一致のため `東京` は `東京都` を含むレコードに一致するが、その逆は成立しない）。同様に旧字体・略記も同一視されない。

- **中間一致のためインデックスが効かず、行数に対して線形にコストが増える**。加えて 50 件の OR 指定では 1 行あたり 50 回の `normalize()` + `ILIKE` 評価が走るため、`tagId` の 20 件（`IN` 1 回）より行数増加時のコストが高い。現在の規模では問題にならないが、悪化の傾き自体は既存の絞り込み条件より急である。

- **`q` と機能が重複する**。`?q=東京都` と `?location=東京都` は「`location` に一致する」という点では同じ結果を含み、利用者から見て使い分けが自明ではない。`@Description` で対象範囲の違いを明記して補う。

## 再検討の条件

1. `events` の行数が増え、`location` 付きの一覧が実測で遅くなった場合（`pg_trgm` の GIN インデックスを追加する）。
2. `location` の入力形式が変わった、または自由記述の度合いが増して部分一致の精度が実用に耐えなくなった場合。
3. 都道府県単位での正確な絞り込み・集計（地域別のイベント数表示など）が要件になった場合（`prefecture` を別パラメータ・別カラムとして追加する）。
4. 表記ゆれの吸収が必要になった場合（正規化辞書または構造化の導入を検討する）。

## 検討した代替案

- **`events` に `prefecture` カラムを追加し、47 固定値で絞り込む**:
  表記ゆれが構造的に排除され、フロントはセレクトボックスで確実に絞り込める。地域別の集計も正確になる。実運用データが無い現時点なら移行コストもほぼゼロで、最も「正しい」設計ではある。しかし入力形式が変わりうる段階で投稿 API に項目を増やすことになり、未設定イベントの扱い（必須にするか、`location` から推定するか）という別の判断も抱え込む。`location` の部分一致で当面の要件が満たせること、`prefecture` は後から別パラメータとして加算的に追加でき破壊的変更にならないことから、今回は採らない。不採用。

- **前方一致（`LIKE '東京都%'`）にしてインデックスを効かせる**:
  「県が必ず先頭」という現在の入力形式を利用すれば、`text_pattern_ops` の B-tree インデックスが効き、行数が増えても高速に保てる。しかし入力形式の変更に対して脆く、壊れてもエラーにならず「ヒットしない」形で表面化するため検知が難しい。現在の規模では速度の利得も体感できない。不採用。

- **地方ブロック（関東・関西など）で絞る**:
  「近場を大づかみに探す」導線に直接応える。しかしブロックの定義をサーバーが持つ必要があり、`location` が自由文字列である以上どの県に属するかを判定できないため、結局は都道府県の構造化が前提になる。都道府県を複数 OR 指定すればクライアント側で同じ結果を得られるため、サーバーに定義を置く利点が薄い。不採用。

- **`q` に統合し、対象項目を指定できるようにする（`?q=東京都&qField=location` など）**:
  パラメータの数が増えない。しかし `q` は反復指定で AND、対象項目は横断固定という契約が既にあり、そこに項目指定を持ち込むと組み合わせの意味（どの語がどの項目に掛かるのか）が破綻する。独立したパラメータの方が契約が単純である。不採用。

- **件数上限を `tagId` と同じ 20 件にそろえる**:
  既存パラメータと数字が揃い、クエリの肥大化も抑えられる。しかし地域は 47 都道府県を網羅的に並べる使い方が本質的にありうるため、20 件では地方ブロックを複数またぐ検索で足りなくなる。上限の一貫性より用途に合わせることを優先した。不採用。
