# ADR-0024: マイページのイベント一覧は種別つきの単一エンドポイントで返し、参加済みは終了日時で判定する

- ステータス: Accepted
- 日付: 2026-08-18
- 関連: #164, ADR-0010, ADR-0011, ADR-0020, ADR-0022

## コンテキストと課題

マイページで「主催したイベント」「申し込み中イベント」「参加済みイベント」の3つを表示したい。
画面はタブ切り替えで、各タブに件数バッジが出る。返すイベントの中身は `GET /api/v1/events` の
サマリー（`model.EventSummary`）と同じでよい。

決めるべきことは4つある。

1. **エンドポイントの形**: プロフィール取得（`GET /api/v1/me`）に相乗りさせるか、独立させるか。
   独立させる場合、種別ごとにルートを分けるか1ルートにまとめるか。
2. **「申し込み中」と「参加済み」を分ける軸**: DB にはこの2つを区別するフラグが無い。
   `event_members` は「現在申し込んでいる」行の集合で、参加キャンセル（leave）時に削除される
   （ADR-0011）。出欠確認・チェックインの仕組みも存在しない。
3. **タブの件数バッジをどう供給するか**: 初回表示の時点で3種別すべての件数が必要になる。
4. **他人のプロフィールページ（`GET /api/v1/profiles/{id}`）との関係**: 同じ画面構成を
   他人のプロフィールでも使う予定があり、そこでは「主催した」「参加済み」を出したい。
   一方「申し込み中」は本人にしか見せられない（誰がどのイベントに申し込んだかが漏れる）。

前提と制約:

- 参加済みイベントは時間とともに単調に増える。一覧はページングを前提にする必要がある。
- 匿名参加（`event_members.profile_id` が NULL）は本人と紐づかないため、一覧に出しようがない。
- `events.end_date` は NOT NULL で、未指定時は `event_date` で補完される（ADR-0018）。

## 決定

マイページのイベント一覧は `GET /api/v1/me/events?type=hosted|applied|attended`（認証必須）の
**単一エンドポイント**で返す。`type` は必須で、不正値は既定へ丸めず 400 を返す。

「申し込み中」と「参加済み」は `event_members` に自分の行があるイベントを **`end_date` と現在時刻の
比較で二分**する（`end_date >= now()` なら申し込み中、`end_date < now()` なら参加済み）。

レスポンスには一覧（`events`）に加えて**3種別すべての件数（`counts`）を常に含める**。

他人向けの `GET /api/v1/profiles/{id}/events` は別 issue で追加する。URL は分けるが、
service（`EventQueryService.ListByProfile`）と repository（`myEventClauses`）は共有し、
公開してよい種別（`hosted` / `attended`）の制限だけを handler 側で行う。

## 理由

**プロフィール取得に相乗りさせない**のは、一覧が増え続けるリソースだからである。`GET /me` に
3配列を埋め込むと、種別ごとの `limit` / `offset` / `sort` を表現できず、名前とアイコンだけ
必要な画面でもイベント4クエリ（3種別＋タグ）が走る。プロフィールは1件のリソース、イベント一覧は
コレクションで、寿命もサイズ特性も違う。

**1ルート＋`type`** にしたのは、3種別が「同じ形のコレクションを条件だけ変えて返す」ものだからである。
ルートを3本に割ると、ページング・ソートの仕様が3箇所に複製され、片方だけ直す事故が起きる。
`type` を必須にして不正値を 400 にするのは、種別を取り違えたまま別のリストが 200 で返ると
クライアント側で誤りに気付けないため。既定値へ丸める `sort` / `order` とは扱いを分ける
（ADR-0020 でタグIDの扱いを切り分けたのと同じ判断軸）。

**`end_date` で二分する**のは、現在の DB でこの2つを分けられる唯一の軸だからである。出欠確認を
導入すれば「申し込んだが来なかった」を区別できるが、それには主催者の当日運用フロー（受付・
チェックイン）が要る。`end_date`（`event_date` ではなく）を使うのは、複数日にまたがるイベントの
開催中に「参加済み」へ移ってしまうのを避けるため。

**`counts` を常に含める**のは、タブのバッジが初回表示で3つとも埋まる必要があるからである。
`totalCount` だけだと初回に3回リクエストすることになる。`GET /me` に件数を持たせる案もあるが、
タブを切り替えても件数が更新されず（申込直後に古い値が残る）、プロフィールのリソースが
イベントの関心事を持つことになる。件数は種別ごとのスカラーサブクエリ3本を1クエリにまとめて取得する。

**URL を本人用と公開用で分ける**のは、認可の境界をルーティングの時点で確定させるためである。
1つの URL で本人と他人を兼ねると、`type=applied` のときだけ本人判定するという分岐が必要になり、
分岐を1つ落としただけで申込履歴が漏れる。パスが分かれていれば、公開側に `applied` が存在しない
ことがルート定義から読める。データの形は同じなので、service と repository は共有できる。

## 影響（結果）

### 良い影響

- 一覧のページング・ソートの仕様が1箇所（`ListByProfile`）に集約される。
- タブ表示に必要な情報（現在のリスト＋3種別の件数）が1リクエストで揃う。
- `GET /profiles/{id}/events` の追加は handler とルートの追加だけで済む。
- 種別ごとの絞り込み条件が `myEventClauses` の1箇所にあり、一覧と件数が同じ定義を参照するため、
  タブのバッジと中身がずれない。

### トレードオフ・制約

- **参加をキャンセルしたイベントはどちらの一覧にも出ない**。`event_members` の行が削除されるため
  （ADR-0011）。`event_participation_logs` には履歴が残るが、「参加していない」という結果は
  正しいので一覧の対象にはしない。
- **匿名で申し込んだイベントは出ない**。ログイン状態で申し込んだ分だけが `profile_id` を持つ。
- **「参加済み」は出席の記録ではない**。申し込んだまま欠席したイベントも含まれる。UI の文言も
  この意味に合わせる必要がある。
- **中止されたイベントも時間で振り分けられる**。中止判定はサマリーの `cancelledAt` で行う。
- `totalCount` と `counts` の該当値が重複する。`GET /api/v1/events` とレスポンスの形を
  そろえる（`events` / `totalCount` / `limit` / `offset`）ほうを優先した。
- 一覧1回につき件数クエリが1本増える。`events(profile_id)` と `event_members(profile_id)` に
  インデックスを追加してこれを支える。既存の `UNIQUE (event_id, profile_id)` は先頭列が
  `event_id` のため、`profile_id` 単独の検索には使えない。

## 検討した代替案

- **案A: `GET /api/v1/me` に3配列を埋め込む** / 追加の往復が要らない点は魅力だが、種別ごとの
  ページングが表現できず、過去イベントが増え続けるとレスポンスが際限なく膨らむ。プロフィールだけ
  必要な画面のコストも上がる。
- **案B: 種別ごとに3ルートへ分ける** / Swagger の説明を種別ごとに書ける利点はあるが、ページングと
  ソートの仕様が3箇所に複製される。公開側で `applied` を出さない制御は URL を本人用/公開用で
  分ける時点で達成できており、種別まで割る必要はない。
- **案C: 1リクエストで3種別すべての一覧を返す** / タブ切り替えのリクエストが不要になるが、
  ページング単位が種別ごとに持てない。件数だけを `counts` で返す形にすれば、初回表示の要求は
  満たしつつページングも保てる。
- **案D: 出欠確認（チェックイン）を導入して「参加済み」を実績で判定する** / 意味としては最も正確だが、
  主催者の当日運用フローと新しいテーブルが必要で、マイページ表示のために導入する規模ではない。
  導入する場合は本 ADR を置き換える。
- **案E: `event_date`（開始日時）で二分する** / 複数日イベントの開催中に「参加済み」へ移ってしまう。
- **案F: `event_participation_logs` の最新アクションで判定する** / ログには匿名参加が記録されず
  （`profile_id` が NOT NULL）、現在の申込状態は `event_members` が持つ。判定の拠り所を2つに
  分けると不整合の余地が生まれる。
