# ADR-0048: CI で govulncheck を実行し、週1回の定期実行でも検査する

- ステータス: Accepted
- 日付: 2026-11-13
- 関連: #281, #235

## コンテキストと課題

依存モジュールや Go 標準ライブラリの脆弱性は、govulncheck を手で実行したときにしか確認していなかった。
脆弱性は新しく公開されるため、一度確認しただけでは、その後に公開されたものに気づけない。
CI に組み込むにあたり、次の 2 点を決める必要がある。

- どの検出で CI を失敗させるか（コードから呼ばれる脆弱性だけか、依存に含まれるだけのものも含めるか）
- コードを変えていない期間にも検査するか（定期実行の有無）

## 決定

- `.github/workflows/ci.yml` に `vulncheck` ジョブを追加し、プルリクエストと main への push で実行する
- govulncheck は既定のモード（ソース解析）で実行し、コードから呼ばれる脆弱性があるときだけ失敗させる。
  依存に含まれるだけで呼ばれない脆弱性では失敗させない
- 週 1 回（月曜 09:00 JST）の schedule でも実行する。schedule では `vulncheck` ジョブだけを動かす
- govulncheck のバージョンは `Makefile` で固定し、CI からは `make vulncheck` で実行する

## 理由

- 呼ばれない脆弱性まで失敗扱いにすると、上流の修正版が出るまで対処できないまま CI が落ち続け、
  本当に対処が必要な失敗と区別できなくなる。呼ばれるかどうかの判定は govulncheck の既定の動作に任せる
- 新しく公開された脆弱性は、PR や push が無い期間には CI で検出されない。週 1 回の定期実行で、
  コードを変えていない期間も検査する
- schedule で build・migrate 等まで動かしても、コードが変わっていないので得られる情報が無い
- swag・golangci-lint と同じく、ツールの版を Makefile に集約して手元と CI の結果を揃える

## 影響（結果）

### 良い影響
- コードから呼ばれる脆弱性が入った・公開された時点で CI が落ち、気づける
- コードを変えていない期間も、週 1 回は検査される

### トレードオフ・制約
- 新しい脆弱性が公開されると、その PR の変更と関係なく `vulncheck` ジョブが落ちる。
  その場合は依存の更新を別の Issue として扱う
- schedule はデフォルトブランチ（main）の ci.yml でのみ動く
- 公開リポジトリでは、60 日間リポジトリに活動が無いと GitHub が schedule のワークフローを自動で無効にする
- 呼ばれない脆弱性は CI では検出されない。依存モジュール単位の通知は Dependabot に任せる

## 検討した代替案

- **定期実行を入れない**: PR・push が無い期間に公開された脆弱性に気づけないため不採用
- **呼ばれない脆弱性でも失敗させる**: 上流の修正待ちの間 CI が落ち続け、対処すべき失敗が埋もれるため不採用
- **schedule で全ジョブを動かす**: コードが変わっていないため build・test・migrate を再実行しても得られる情報が無く、不採用
- **govulncheck 用に別のワークフローファイルを作る**: CI の設定を `ci.yml` 1 か所にまとめるため不採用
- **`golang/govulncheck-action` を使う**: 手元と CI で同じ `make` ターゲットを使い、版の固定を Makefile に集約するため不採用
