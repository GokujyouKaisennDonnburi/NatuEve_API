# ADR-0047: 画像の幅と高さを各8000pxに制限し超過は400で拒否する

- ステータス: Accepted
- 日付: 2026-11-13
- 関連: #274, NatuEve_Web_Frontend#404, PBI78, ADR-0037

## コンテキストと課題

画像は tmp 領域から昇格するとき、EXIF/GPS 情報を除去するために
`stripEXIFAndReencode` で全体をデコードしてから再エンコードしている。
ファイル容量が10MB以内でも、圧縮された画像の幅・高さが大きい場合は、デコード時に
Cloud Run のメモリを大きく消費する。

Web 側ではアップロード前に画像の幅・高さを検証するが、API を直接呼び出す送信にも
同じ制約を適用する必要がある。

## 決定

画像の幅と高さの上限をそれぞれ8000pxとする。tmp 領域からの昇格時に
`image.DecodeConfig` で寸法を取得し、どちらかが上限を超える場合は、画像全体を
デコードせず HTTP 400 で拒否する。

上限値は Web 側と共通にする。画像ヘッダが壊れていて寸法を取得できない場合も、
入力された画像を処理できないため HTTP 400 で拒否する。

## 理由

- `image.DecodeConfig` は画像全体を復元せずに寸法を取得できるため、大きな画像による
  メモリ展開を事前に防げる。
- Web を経由しない送信にもサーバー側で同じ制約を適用できる。
- Web と API の上限を揃えることで、画面では受け付けた画像を API が拒否する不整合を防げる。
- 上限超過と壊れた画像はクライアント入力の問題であり、`ValidationError`（400）として扱う。

## 影響（結果）

### 良い影響

- 幅または高さが8000pxを超える画像は、全体デコード前に拒否される。
- JPEG・PNGの圧縮率に依存せず、極端な寸法によるメモリ枯渇リスクを抑えられる。
- ブラウザ以外から送信された画像にも上限が適用される。

### トレードオフ・制約

- 8000×8000pxの画像は許可され、RGBA 展開時には画像本体だけで約256MBを使用する。
- 本番の Cloud Run は1インスタンス512MiB・同時実行数80のため、上限付近の画像を
  同時に処理するとメモリ不足になる可能性がある。実運用で必要になった場合は、上限の引き下げ、
  同時実行数の制限、またはメモリ割り当ての増加を検討する。
- 上限を変更するときは Web 側の値も同時に変更する必要がある。

## 検討した代替案

- **ファイル容量10MBの制限だけを使う**: 圧縮率が高く寸法の大きい画像を防げず、
  デコード時のメモリ使用量を制限できないため不採用。
- **総ピクセル数だけを制限する**: Web 側の幅・高さそれぞれ8000pxという制約と一致せず、
  クライアントと API で受け付ける画像が変わるため不採用。
- **上限超過画像を縮小して保存する**: デコードが必要になり、今回防ぎたいメモリ展開が
  発生するため不採用。
