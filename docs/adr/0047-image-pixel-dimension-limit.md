# ADR-0047: 画像の寸法・展開後サイズ・同時展開数を制限し超過は400で拒否する

- ステータス: Accepted
- 日付: 2026-11-13（2026-11-26 に展開後サイズと同時展開数の制限を追加）
- 関連: #274, #308, NatuEve_Web_Frontend#404, NatuEve_Web_Frontend#470, PBI78, ADR-0037

## コンテキストと課題

画像は tmp 領域から昇格するとき、EXIF/GPS 情報を除去するために
`stripEXIFAndReencode` で全体をデコードしてから再エンコードしている。
ファイル容量が10MB以内でも、圧縮された画像の幅・高さが大きい場合は、デコード時に
Cloud Run のメモリを大きく消費する。

Web 側ではアップロード前に画像の幅・高さを検証するが、API を直接呼び出す送信にも
同じ制約を適用する必要がある。

幅・高さの上限だけでは不十分なケースがある。16 ビットの PNG は 1 ピクセルあたり
8 バイトで展開されるため、8000×8000 でも展開後は約488MiB になり、Cloud Run の
メモリ上限（512MiB）を超える。実際に昇格処理と同じ順（`DecodeConfig` → `Decode` →
`png.Encode`）で標準ライブラリを呼ぶ検証用プログラムを、本番と同じ distroless
イメージ・メモリ上限 512MiB のコンテナで実行したところ、次の結果だった（#308 備考）。

- 8000×8000 の16ビット PNG（0.49MiB）1枚: メモリ不足で強制終了（exit 137）
- 8000×8000 の8ビット PNG 2枚を同時に処理: 成功したがヒープが 504MiB で上限に近い
- 検証用プログラムには API 本体のメモリは含まれない。本番と検証環境では試していない

## 決定

画像は tmp 領域からの昇格時に、画像全体をデコードする前に次の検証を行い、
超える場合は HTTP 400 で拒否する。

1. **寸法**: `image.DecodeConfig` で幅・高さを取得し、どちらかが 8000px を超える場合
2. **展開後サイズの推定値**: 幅 × 高さ × 1ピクセルあたりのバイト数（`DecodeConfig` の
   ColorModel から求める。16ビット RGBA 系は 8 バイト、グレースケール16は 2 バイト、
   8ビット RGBA 系・YCbCr は 4 バイト、グレースケール8・パレットは 1 バイト、
   未知の形式は保守的に 8 バイト）が 256MiB（268,435,456 bytes）を超える場合。
   ただし標準パッケージが ColorModel より多くのメモリを確保するケースは次の通り
   見積もりを上書きする。
   - PNG のグレースケールに tRNS が付くと NRGBA/NRGBA64 として展開されるため、
     tRNS を検出した場合はグレースケール8を 4 バイト、グレースケール16を 8 バイト
   - JPEG の Adobe CMYK は YCbCr 3 面 + K 面 + image.NewCMYK として展開されるため 8 バイト
   - JPEG の Adobe RGB は YCbCr 3 面 + image.NewRGBA として展開されるため 7 バイト
   - JPEG のプログレッシブ（SOF2）は成分ごとの係数バッファ（成分数 × 4 バイト）を
     画像本体と同時に確保するため加算する（YCbCr 3 成分なら 4 + 12 = 16 バイト）
   - PNG の Adam7 インターレースは全体の画像に加えて最大パス（面積 1/2）の画像を
     同時に確保するため、推定値を 1.5 倍にする
3. **同時展開数**: 展開・再エンコード（`stripEXIFAndReencode` から `Put` の完了まで）は
   プロセス全体で同時に 1 件までに制限する

上限値の根拠:

- 展開後 256MiB は、寸法上限ちょうどの 8000×8000 RGBA 展開（256,000,000 bytes）が
  受け付けられる値であり、寸法上限との整合を保つ。16ビット画像はこの上限により
  約5792×5792 px までしか受け付けられない
- 同時展開数 1 は、展開後上限 256MiB の画像が 2 件同時に展開されると
  2 × 256MiB = 512MiB となり、コンテナ上限（512MiB）を単独で消費するため。
  圧縮データ本体（最大10MB × 同時処理数）と再エンコード出力、API 本体のメモリを
  考慮しても、同時に展開できるのは 1 件が上限と判断した
- 検証結果の「2枚同時でヒープ 504MiB」は、展開後 488MiB + 出力がほぼゼロ（単色画像）の
  条件での成功例であり、出力バッファや API 本体のメモリを含む実運用では余裕がない

画像ヘッダが壊れていて寸法を取得できない場合も、入力された画像を処理できないため
HTTP 400 で拒否する。

## 理由

- `image.DecodeConfig` は画像全体を復元せずに寸法と色の形式を取得できるため、
  大きな画像によるメモリ展開を事前に防げる。
- Web を経由しない送信にもサーバー側で同じ制約を適用できる。
- Web と API の上限を揃えることで、画面では受け付けた画像を API が拒否する不整合を防げる。
  16ビット画像については Web 側でも展開後サイズの事前確認が必要になるため、
  Web 側に Issue を作成して対応を依頼する（NatuEve_Web_Frontend#470）。
- 上限超過と壊れた画像はクライアント入力の問題であり、`ValidationError`（400）として扱う。
- 同時展開数はリクエスト単位では制御できず、複数の投稿が同時に届くため、
  プロセス全体のセマフォで制限する。Cloud Run は負荷に応じてインスタンスを
  増やすため、1 インスタンス内での直列化がスループットの上限になることは避けられる。

## 影響（結果）

### 良い影響

- 幅または高さが8000pxを超える画像、および展開後サイズの推定値が 256MiB を超える画像は、
  全体デコード前に拒否される。
- 8000×8000 の16ビット PNG のような、寸法上限内でもメモリ不足になる画像を防げる。
- JPEG・PNGの圧縮率に依存せず、極端な寸法・色深度によるメモリ枯渇リスクを抑えられる。
- 複数の投稿が同時に届いても、画像の展開は 1 件ずつ処理され、メモリ上限を超えない。

### トレードオフ・制約

- 展開後サイズの推定値は ColorModel と形式ごとの作業バッファからの概算であり、
  YCbCr（実態は 1.5〜3 バイト/ピクセル）を 4 バイトとするなど、
  実際より大きく見積もる方向に倒している。
- プログレッシブ JPEG の係数バッファはサブサンプリングで小さくなるが、
  ColorModel からの成分数推定では最大（4:4:4 相当）に倒している。
- 高エントロピーな画像の再エンコード出力は展開後サイズに近づくため、
  展開後 256MiB + 出力バッファで 512MiB に対する余裕は限られる。実運用でメモリ不足が
  発生した場合は、上限の引き下げ、`GOMEMLIMIT` の設定、またはメモリ割り当ての増加を検討する。
- 画像の展開・再エンコードが 1 インスタンス内で直列化されるため、大きな画像の同時投稿では
  待ち時間が増える。待ち行列は `context` のキャンセルで中断できる。
- 上限を変更するときは Web 側の値も同時に変更する必要がある。

## 検討した代替案

- **ファイル容量10MBの制限だけを使う**: 圧縮率が高く寸法の大きい画像を防げず、
  デコード時のメモリ使用量を制限できないため不採用。
- **総ピクセル数だけを制限する**: Web 側の幅・高さそれぞれ8000pxという制約と一致せず、
  クライアントと API で受け付ける画像が変わるため不採用。
- **上限超過画像を縮小して保存する**: デコードが必要になり、今回防ぎたいメモリ展開が
  発生するため不採用。
- **同時展開数を 2 以上にする**: 展開後上限 256MiB の画像が 2 件重なると 512MiB に達し、
  API 本体のメモリと出力バッファの分が足りなくなるため不採用。
