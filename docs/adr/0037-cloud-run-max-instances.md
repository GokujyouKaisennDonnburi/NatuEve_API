# ADR-0037: Cloud Run の最大インスタンス数をサービス単位で 1 とし、1 台あたりの DB 接続数に上限を設ける

- ステータス: Accepted
- 日付: 2026-10-23
- 関連: #240, #215, #213, #214, ADR-0032, ADR-0034, ADR-0035, ADR-0036
- 構成の詳細・設定値は [docs/Deployment.md](../Deployment.md) を参照

## コンテキストと課題

ADR-0032 で、API は Cloud Run にリクエスト課金・最小インスタンス数 0 で載せると決めた。最大インスタンス数は未決だった
（Deployment.md の未決事項 9。#215 の受け入れ基準を #240 で扱う）。デプロイ時に指定しないと、Cloud Run の既定値で動く。

判断に効く前提は次のとおり（Cloud Run・Supabase の仕様は 2026-10 時点で公式ドキュメントを確認した値）。

- **Cloud Run の既定値と上限の扱い**
  - 指定しない場合、リビジョンは最大 100 インスタンスまで増える。
  - 最大インスタンス数はサービス単位とリビジョン単位で設定できる。公式はサービス単位を推奨しており、設定は即時に反映される。
    リビジョン単位の値はリビジョンごとの上限で、デプロイ中は旧・新のリビジョンの合計が上限を超えうる。
  - 通常の運用でも、指定した最大インスタンス数を短時間超えることがある（公式: 週に数回。トラフィックの急増やメンテナンスで、
    追加のインスタンスが既存のものを一時的に置き換える）。
  - 最大インスタンス数に達すると、リクエストは「10 秒」と「インスタンスの平均起動時間の 3.5 倍」の長い方まで待ち、
    空かなければ 429 で失敗する。
  - 同時実行数の既定値は 80（1 vCPU の場合）。
- **費用**: リクエスト課金では、インスタンスはリクエストの処理中・起動時・停止時にだけ課金される。
  最大インスタンス数で抑えられるのは CPU・メモリの費用で、リクエストの件数による課金は抑えられない（ADR-0034）。
- **処理量**: 月額の試算（Deployment.md）の「大」は月 1,000 万リクエストで、平均 毎秒 約 4 件。1 件 0.1 秒とすると、
  処理中の時間の合計は月 約 100 万秒で、1 台が月の 4 割弱の時間だけ処理している量になる。
- **IP レート制限**: 参加申込の IP レート制限（`internal/middleware/ratelimit.go`）はインスタンスのメモリ上で数える。
  インスタンスが N 台あると、制限は最大 N 倍まで緩む。
- **outbox の排他**: 行の確保は `FOR UPDATE SKIP LOCKED` で行い、複数台でも同じ行を同時に送らない（ADR-0035）。
  1 件の処理中は接続を 2 本同時に使う（確保した行のトランザクションと、宛先の取得）。
- **DB の接続数**: `SetMaxOpenConns` を設定しておらず、1 台が開く接続の数に上限がない（同時実行数（80）に近い数まで開きうる）。
  - Supabase への接続はセッションモードのプーラー（Supavisor、ポート 5432）を使う（#213）。
  - Free（コンピュートは Nano）の上限は、DB の最大接続数 60、プーラーの最大クライアント数 200。
    Supabase の Auth・Storage・PostgREST なども同じ DB の接続数を使う。
  - プールの大きさ（Pool Size）は「ユーザー・DB・モード」の組ごとの、プーラーが DB へ張る接続の上限。
    Nano での既定値は公式ドキュメントで確認できなかった（第三者の情報では 15 または 20）。
  - セッションモードでは、プーラーが割り当てた DB への接続は、クライアントが切断するまでそのクライアントが使い続ける。
    空きがない場合、クライアントは最大 1 分待たされる。空かなかった場合はエラーになる（エラーの内容は第三者の情報でのみ確認）。

## 決定

**Cloud Run の最大インスタンス数はサービス単位で 1 とする。1 プロセスあたりの DB 接続数の上限を環境変数
`DB_MAX_OPEN_CONNS` で設定できるようにし、本番は 6 にする。**

1. **最大インスタンス数**: サービス単位で 1 にする（`gcloud run services update <サービス> --max 1`）。リビジョン単位では設定しない。
   検証環境（ADR-0036）も同じ値にする。
2. **同時実行数**: 既定値（80）のままにする。
3. **DB 接続数の上限**: 環境変数 `DB_MAX_OPEN_CONNS` の値を `database/sql` の `SetMaxOpenConns` に渡す。
   - 未設定なら上限なし（起動時に警告ログを出す）。整数でない値と 2 未満の値では起動しない。
   - 本番と検証環境は 6 にする。
4. **守る関係**: `(最大インスタンス数 + 1) × DB_MAX_OPEN_CONNS + 2 ≦ Pool Size` を満たすように決める。
   - `+ 1` は Cloud Run が最大インスタンス数を短時間超える分、`+ 2` はマイグレーションと手作業の接続の分。
   - Pool Size を 15 とみなして計算した（(1 + 1) × 6 + 2 = 14）。デプロイ前に Supabase のダッシュボードで実際の値を確かめ、
     15 より小さければ `DB_MAX_OPEN_CONNS` を下げる。最大インスタンス数を変えるときも計算し直す。
5. **見直す条件**: 正規の利用で Cloud Run の 429（インスタンスの空き待ちの失敗）が出る、または CPU 使用率が高い状態が続く場合は、
   最大インスタンス数を上げる。その際は IP レート制限の緩み（決定時の台数の倍率）と決定事項 4 を見直す。

## 理由

- **1 台で処理が足りる**: 試算の「大」の規模でも、処理中の時間は 1 台が月の 4 割弱の時間だけ動く量で、平均の同時処理数は
  1 件未満（毎秒 約 4 件 × 0.1 秒）と、同時実行数（80）より十分小さい。
- **費用の上限を最小にする**: 最大インスタンス数は通常の負荷での費用には効かず、処理中の時間が続いたとき（大量のアクセスを
  受け続けたとき）の CPU・メモリの費用の上限を決める。1 台が 1 か月休まず処理し続けた場合、無料枠を引いて 約 $60／月
  （Deployment.md の単価。東京の単価は未確認）。2 台なら 約 $126、3 台なら 約 $191 になる。
- **IP レート制限が設定どおりに効く**: 1 台なら、短時間上限を超える場合を除き、制限は緩まない。
- **サービス単位にする理由**: 公式の推奨で、設定が即時に反映される。リビジョン単位はリビジョンごとの上限で、
  デプロイ中は合計が上限を超えうる。
- **DB 接続数の上限が必要な理由**: 最大インスタンス数を決めても、1 台が開く接続の数に上限がなければ、接続の合計は抑えられない。
  上限がないと、1 台で Pool Size を使い切りうる。その場合、マイグレーションなど他の接続がプーラーで待たされる、または失敗する。
  上限を設けると、超えた分は API のプロセスの中で接続が空くのを待つ。
- **6 にする理由**: 決定事項 4 の関係を、Pool Size の候補のうち小さい方（15）で満たす最大の値。
  1 件が接続を 0.1 秒使うとして、1 台で毎秒 約 60 件まで処理でき、試算の「大」の規模に足りる。
- **2 未満を拒否する理由**: outbox の処理は 1 件につき接続を 2 本同時に使うため、上限が 1 だと宛先の取得に使う接続が空かず、
  どの行も送信されない。2 以上でも、同時に走る outbox の処理の数によっては同じことが起きる（トレードオフ・制約）。
- **未設定なら上限なしにする理由**: 開発環境（docker compose の PostgreSQL）とテストで、接続数の扱いを変えないため。

## 影響（結果）

### 良い影響

- 大量のアクセスを受け続けても、CPU・メモリの費用は 約 $60／月 で頭打ちになる。
- 参加申込の IP レート制限が、設定した値（平均 5 回／分・瞬間 5 回）どおりに効く。
- DB の接続の合計が、Supabase のプールの上限に収まる。

### トレードオフ・制約

- **予備がない**: 1 台が処理で埋まると、リクエストは待たされた後に 429 になる。独自ドメイン経由・run.app の URL への直接の
  いずれでも、大量のアクセスを受けると正規の利用者も API を使えなくなる。台数を増やすと耐えられる量は増えるが、
  費用の上限も同じ倍率で上がる。
- **リクエストの件数による課金は抑えられない**（ADR-0034）。予算アラート（Deployment.md の未決事項 11）で検知する。
- **上限は短時間超えうる**: その間は IP レート制限が最大 2 倍まで緩む。DB の接続数は決定事項 4 の `+ 1` で見込んでいる。
- **デプロイ中の数え方は未確認**: サービス単位の上限が、デプロイ中の旧・新のリビジョンをどう数えるかは公式ドキュメントで確認できていない。
  上限 1 で切り替え中に 429 が出ないかを、デプロイ後に確かめる（Deployment.md）。
- **outbox の処理が上限以上の数だけ同時に走ると詰まる**: どの処理も 1 本目の接続を持ったまま宛先の取得で 2 本目を待ち、
  確保の期限（ADR-0035）の直前まで進まない。宛先の取得は期限切れで失敗し、行は `pending` のまま残って次の呼び出しで再試行される。
  Cloud Scheduler は実行中のジョブの次の実行をスキップするため、同時に走るのは通常 1 つ（まれな重複実行で 2 つ）で、
  本番の 6 には届かない。
  ジョブを増やす、または `DB_MAX_OPEN_CONNS` を下げるときは、同時に走りうる数が上限より小さいことを確かめる。
- **Pool Size は未確認**: 実際の値が 15 より小さい場合、`DB_MAX_OPEN_CONNS` を下げないと決定事項 4 を満たさない。
- **`DB_MAX_OPEN_CONNS` の設定漏れは起動時に止まらない**: 未設定でも警告ログを出して上限なしで起動する。
  本番・検証環境の環境変数に必ず入れる（Deployment.md の本番の環境変数）。
- **DB を Auth と同じ Supabase プロジェクトに置く場合**（#214）: Auth などのサービスや他のプロダクトの接続が、
  同じ DB の最大接続数（60）を使う。Pool Size は「ユーザー・DB・モード」の組ごとの上限なので決定事項 4 の計算は変わらないが、
  最大接続数の残りが Pool Size より少なくなると、プールの上限まで接続できない。
- コールドスタートの扱いは変わらない（最小インスタンス数 0。ADR-0032）。

## 検討した代替案

- **最大インスタンス数 2**: 1 台が埋まったときの予備を持てる。大量のアクセスを受け続けたときの費用の上限が 約 $126／月 になり、
  IP レート制限は最大 2 倍まで緩む。処理量は 1 台で足りるため、予備の利点が上記に見合わない。不採用。
- **最大インスタンス数 3**: 公式（About maximum instances）が、予算の保護のために最初の値として勧めている。費用の上限が 約 $191／月 になり、
  IP レート制限は最大 3 倍まで緩む。不採用。
- **最大インスタンス数を指定しない（既定の 100）**: 費用の上限がほぼなく、IP レート制限は最大 100 倍まで緩み、
  DB の接続数も抑えられない。不採用。
- **リビジョン単位で設定する**: デプロイ中は旧・新のリビジョンの合計が上限を超えうる。公式はサービス単位を推奨している。不採用。
- **Cloud Run の同時実行数で DB の接続数を抑える**: DB を使わないリクエスト（`/health`、中継元の確認で拒否するリクエスト）も
  同じ枠を使い、大量のアクセスを受けると正規のリクエストの枠が早く埋まる。不採用。
- **トランザクションモードのプーラー（ポート 6543）で接続を共有する**: prepared statement に対応していない（#213）。不採用。
- **IP レート制限を DB や外部のストアで数え、台数に依存させない**: 処理と依存が増える。最大インスタンス数が 1 なら必要ない。
  最大インスタンス数を上げるときに見直す。
