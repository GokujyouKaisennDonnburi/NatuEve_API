# ADR-0026: 自分の申込内容は本人スコープの単一リソースで返し、参加費は含めない

- ステータス: Accepted
- 日付: 2026-08-20
- 関連: #176, ADR-0009, ADR-0011, ADR-0022, ADR-0023,
  ADR-0024（`event-detail-participant-count`）, ADR-0024（`my-page-event-lists`）, ADR-0025

## コンテキストと課題

申込を済ませたユーザーが「自分はこのイベントに何をどう申し込んだか」を後から確認できるようにする。
表示するのは申込日時と、カテゴリ別の参加人数（カテゴリ名と人数の両方）。

決めるべきことは4つある。

1. **URL の置き場所**: 本人スコープの参照をどこに生やすか。
2. **参加費（金額）を含めるか**: カテゴリ別人数を返す以上、「大人2名 × 500円」の金額まで返すかどうか。
3. **未申込・イベント不存在の返し方**: 404 か、200 で空を返すか。
4. **申込時に入力した氏名・メールアドレスを含めるか**。

前提と制約:

- 現在の申込は `event_members` の1行。参加キャンセルでは行ごと削除される（ADR-0011）。
- カテゴリ別人数は `event_member_categories` が `cost_id` で `event_costs` を参照する形で保持し、
  **申込時点のカテゴリ名・金額のスナップショットは持たない**（ADR-0023）。
- 匿名申込は `profile_id` が NULL で、本人と紐づけられない。
- 参加者一覧（`GET /api/v1/events/{id}/members`）は主催者専用で、氏名・メールアドレスを含む（ADR-0022）。
- 本人スコープの参照エンドポイントとして `GET /api/v1/events/{id}/participation-logs`
  （認証ユーザー自身の最新の参加状態）が既にある。
- イベント詳細（`GET /api/v1/events/{id}`）は公開エンドポイントで、`costs[]`（カテゴリと金額）を返す。

## 決定

`GET /api/v1/events/{id}/members/me`（認証必須）を追加し、認証ユーザー自身の申込1件を返す。

レスポンスは `eventId` / `username` / `mailAddress` / `partySize` / `participants[]`（`category`・`headCount`）
/ `createdAt` とし、**参加費（金額）は含めない**。`participants` はカテゴリ名の昇順で返す。

未申込とイベント不存在はいずれも 404 `not_found` とし、メッセージで区別する。
匿名で申し込んだ内容を取得する経路は設けない。

## 理由

**参加費を含めないのは、申込時点の金額を DB が持っていないからである。** ADR-0023 は
`cost_id` 参照を採り、履歴の不変性より構造の整合性を優先すると決めた。したがってここで返せるのは
`event_costs` の**現在値**だけで、「申し込んだときに提示された金額」ではない。申込内容の確認という
文脈で金額を返すと、それは申込の証跡として読まれる。API が保証できないことを、保証しているように
見える形で返すべきではない。証跡が必要になったら、金額とカテゴリ名をコピーする列を足す拡張
（ADR-0023 に記載済み）が先に必要になる。

加えて、同じ値をイベント詳細が既に返している。同じ事実を2箇所で返すと、片方だけ更新された瞬間に
食い違って見える経路が増えるだけになる（ADR-0024 `event-detail-participant-count` で残り人数をサーバーが返さないと決めたのと同じ判断軸）。
突合は `participants[].category` と `costs[].category` で行える。両者は同じ `event_costs` 行に由来する
同一文字列なので、主催者がカテゴリを改名しても同時に変わり、突合は壊れない。

**`/events/{id}/members/me` に置くのは、返すものが参加者一覧の1要素そのものだからである。** パスに
`me` を置くと本人スコープが経路の時点で確定し、閲覧者の判定をハンドラの分岐に委ねずに済む
（ADR-0025 で「公開範囲は分岐ではなく URL で決める」と採ったのと同じ形）。親（`members`）が主催者専用で
子（`members/me`）が本人専用という認可の非対称は残るが、`me` は呼び出し元自身を指す固定セグメントで
あり、第三者が要素を指名できる形（`/members/{memberId}`）ではないため、権限の読み違えは起きない。

**未申込を 404 にするのは、ADR-0009 で確認した分岐軸に従うためである。** 所有者・権限の認可チェックを
持たない参照は、不存在を秘匿する動機がないので純粋なリソース不存在として 404 を返す。`POST /events/{id}/leave`
が既に「イベント不存在」「未参加」の両方を 404 で返しており、同じ `event_members` の行の有無を見る
エンドポイント同士で流儀を揃える。code を分けないのも leave と揃えるためで、区別はメッセージで行う。

**氏名・メールアドレスを含めるのは、それが申込内容の中心的な情報だからである。** 「誰の名前で、どのメール
アドレスで申し込んだか」は確認画面で最初に見る項目で、同じ行から追加クエリなしで取れる。本人にしか
返さないため、参加者情報の公開範囲（ADR-0022）の議論には触れない。

**申込行と内訳は LEFT JOIN の1クエリで取得する。** 別々の SELECT にすると、申込行を読んだ直後に本人の
参加キャンセルが割り込んだ場合に、`partySize` は非ゼロなのに内訳が空という読み取りずれが起きる。単一文なら
スナップショットが1つに定まり、この状態を返しえない。トランザクションで包む案は、既定の READ COMMITTED が
文ごとにスナップショットを取るため分離レベルを上げる必要があり、参照1件のために既存の参照系
（`ListMembers` など）と流儀が割れる。1クエリなら DB への往復も1回で済む。

**内訳が 0 件の申込を DB 制約で禁じることはしない。** `event_member_categories` には「申込1件につき1行以上」を
強制する制約が無く、API 経由の申込で内訳が必ず入ることは service のバリデーション（`participants` は `min=1`）が
担保している。DB で強制するには申込 INSERT 時点ではまだ内訳が無いため `DEFERRABLE INITIALLY DEFERRED` の
制約トリガが要るが、ADR-0023 は同じ性質の不変条件（`party_size` と内訳合計の一致）を API 層の責務と決めており、
片方だけ DB へ落とすと責務の所在が分かれる。

## 影響（結果）

### 良い影響

- 申込内容を確認するために主催者専用の参加者一覧を叩く必要がなくなる。
- 「申込時点の金額を保持していない」という DB の事実と、API が主張する内容が食い違わない。
- マイグレーションは不要。既存の sentinel（`ErrEventNotFound` / `ErrNotJoined`）を再利用でき、
  未申込時の挙動が leave と揃う。
- 本人スコープであることが URL から読めるため、公開エンドポイントへ誤って流用されにくい。

### トレードオフ・制約

- **合計金額を出すにはイベント詳細が要る。** 申込確認を単独で開く導線では往復が2回になる。
- **クライアントが計算する金額は現在値。** 申込後に主催者が金額を変えれば表示も変わる。これは
  本 API が金額を返しても同じで、返さないことで「申込時の金額」という誤読だけを避けている。
- **匿名で申し込んだ内容は本人でも取得できない。** `profile_id` が NULL で識別できないため（ADR-0011 と同じ制約）。
- **未申込とイベント不存在が同じ `code` になる。** 区別が必要ならメッセージで判定するしかない。
- **返すのは現在の申込であって履歴ではない。** 参加をキャンセルすると 404 になり、過去に何を申し込んだかは
  参照できない（`event_participation_logs` には残るが本 API の対象外）。
- **内訳 0 件の申込は DB 上作れる。** API を通さない直接 INSERT や、内訳テーブル導入前に作られた行がこれに当たり、
  その場合 `participants` は空配列で返る。API 経由の申込では起きない。
- LEFT JOIN のため申込行の列が内訳の件数だけ重複して返る。内訳は申込1件あたり数件で、影響は小さい。
- DB への往復は1回。内訳は `event_member_categories` の PK 先頭列（`member_id`）で引ける。

## 検討した代替案

- **案A: 参加費（`participants[].cost` と合計金額）を含める**:
  1往復で金額まで表示できるが、返せるのは申込時点ではなく現在値であり、申込確認の文脈では
  証跡として誤読される。1往復の節約に対して誤読のリスクが釣り合わない。
- **案B: 申込時の金額・カテゴリ名を `event_member_categories` にコピーする**:
  証跡としては最も正しいが、ADR-0023 の決定を覆す変更であり、マイグレーションと参加状態ログ側の
  対応も要る。証跡が要件になった時点で ADR-0023 を置き換える形で行う。
- **案C: `GET /me/events/{id}/application` に置く**:
  本人スコープが URL から自明だが、`/me/events` が一覧（ADR-0024 `my-page-event-lists`）であるため、その下の `{id}` が
  一覧の要素＝イベントサマリーと読める。
- **案D: 未申込を 200 + 空レスポンスで返す**:
  `GET /events/{id}/participation-logs` と同じ流儀で、1リクエストで申込の有無も判定できる。
  ただしリソース取得系で 404 を返す leave と流儀が割れる。参加有無の判定は既存の participation-logs で足りる。
- **案E: イベント詳細に自分の申込内容を埋め込む**:
  往復が減るが、公開エンドポイントに認証依存のフィールドが入り、キャッシュ可能性と公開範囲の判断が
  複雑になる。未認証・匿名・ログイン済みで同じ URL の応答が変わるのは避ける。
