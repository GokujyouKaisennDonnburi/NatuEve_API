# ADR-0044: 1回の参加申込の人数上限を10人とし、超過は400で拒否する

- ステータス: Accepted
- 日付: 2026-11-11
- 関連: PBI76, ADR-0023

## コンテキストと課題

参加申込は `participants` のカテゴリ別人数（`headCount`）を受け取り、合計を
`event_members.party_size` として保存している。現状は各カテゴリの人数が1人以上であること
だけを検証しており、1回の申込で何十人でも登録できる。

イベントの定員チェックは「イベント全体の残枠」を見るものであり、1回の申込人数に対する
上限ではない。そのため、定員100人のイベントに100人で申し込むと、定員内であることを理由に
`capacity_full`（409）ではなく登録できてしまう。

PBI76 のゴール2〜4として、1回の参加申込の人数上限を設ける必要がある。制約は次のとおり。

- 上限は10人とし、イベントごとに変更できる必要はない。
- 上限超過はクライアントの入力エラーとして扱い、申込を登録しない。
- 定員超過（`capacity_full`）とはエラーコードで区別できるようにする。

## 決定

参加申込の入力検証で `participants[].headCount` の合計を算出し、10人を超える場合は
HTTP 400・エラーコード `party_size_exceeded` で拒否する。上限は service 層の定数
`maxPartySize = 10` とし、イベントごとの設定は持たない。

検証は repository の定員チェックより前に行い、上限超過時は DB に到達させない。

## 理由

- 1回の申込人数上限はイベント定員とは別の入力制約であり、`ValidationError`（400）として
  扱うのが意味的に正しい。`capacity_full` はイベント全体の残枠との競合を表す。
- service の入力検証で先に弾くことで、定員100人のイベントに100人で申し込んだ場合も
  `capacity_full` ではなく `party_size_exceeded` を返せる。
- イベントごとの上限設定はゴール外であり、固定値で足りる。設定可能にすると DB スキーマ・
  作成 API・管理画面の追加が必要になる。
- クライアントがエラーコードで「人数上限」と「定員」を分岐できる。

## 影響（結果）

### 良い影響

- 1回の申込で大量の参加者を登録できなくなる。
- 定員に余裕があるイベントでも、10人を超える申込は 400 `party_size_exceeded` で拒否される。
- 定員チェックは従来どおり、合計10人以下の申込に対してのみ適用される。

### トレードオフ・制約

- 10人を超える団体申込は、複数回に分けるか主催者へ直接相談する運用になる。
- イベントごとに上限を変えたい場合は、別途スキーマと API の拡張が必要になる。
- クライアントは未知のエラーコード `party_size_exceeded` を処理できるよう更新が必要。

## 検討した代替案

- **案A: イベントごとに上限人数を設定できるようにする**:
  柔軟だが PBI76 のゴール外。`events` のカラム追加、作成・更新 API、入力フォームの追加が必要になる。
- **案B: 定員チェックと同じ 409（`capacity_full`）で返す**:
  1回の申込人数超過とイベント全体の残枠不足をクライアントが区別できず、表示や案内を分けられない。
- **案C: repository の定員チェック内で上限も検証する**:
  DB トランザクション内まで到達してから拒否することになり、入力検証で完結する制約を
  repository に持ち込む必要がある。service の入力検証で十分。
