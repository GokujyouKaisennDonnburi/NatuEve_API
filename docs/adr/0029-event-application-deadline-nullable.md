# ADR-0029: イベントの申込期限は NULL 許容の単一カラムで表現する

- ステータス: Accepted
- 日付: 2026-08-21
- 関連: #183, ADR-0018

## コンテキストと課題

`events` は開催日時 `event_date` と終了日時 `end_date` を持つが、**いつまで申し込めるか**を表現できない。申込期限を DB に追加するにあたり、「期限を設けないイベント」をどう表現するかを決める必要がある。

制約と前提は次のとおり。

1. **期限なしのイベントが実在する**。定員に達するまで受け付ける観察会や、当日参加自由のイベントでは締切を設けない。したがって「期限なし」は表現できなければならない。
2. **ADR-0018 では `end_date` の NULL 許容を退けている**。ただしそれが成立したのは「単日イベント = 開始と終了が同時刻」という自然な既定値があったためである。申込期限に同じ手が使えるかは別途判断が要る。
3. **既存の日時列はすべて `TIMESTAMPTZ`**であり、不変条件は `CHECK` を最後の防衛線として持つ（ADR-0018）。申込期限にも同じ形を適用するかを決める。
4. **DB 表現と投稿 API の契約を順に決める**。当初の対象は DB 表現のみだったが、投稿 API での受け取り方は後続の作業で本 ADR に追記した（決定 4〜6）。締切後の申込をどう弾くか、レスポンスへの露出は引き続き後続の issue で扱う。

## 決定

**`events.application_deadline TIMESTAMPTZ`（NULL 許容）を追加し、NULL を「申込期限なし」として扱う。DB 制約は `CHECK (application_deadline <= end_date)` とする。**

1. 期限なしは NULL で表す。DEFAULT は置かない。
2. `CHECK (application_deadline <= end_date)` で、終了日時より後の期限を拒否する。NULL のとき `CHECK` の評価は UNKNOWN となり合格するため、「期限なし」と制約は両立する。
3. マイグレーションは既存ファイル `db/migrations/20260622140000_create_events.sql` の `CREATE TABLE` を直接編集する（テーブル定義を 1 か所で読めるようにする既存の運用に従う）。
4. 投稿 API `POST /api/v1/events` は `applicationDeadline`（RFC3339・任意）で受け取る。未指定（Go のゼロ値）は「期限なし」として NULL を保存する。
5. サービス層は「指定時は終了日時以前」を検証し、違反は 400 で返す。`endDate` 省略時は補完後の値（＝`eventDate`）を上限とする。過去日時の申込期限は許可する。
6. 単体取得（`EventResponse`）と一覧（`EventSummary`）の双方で `applicationDeadline` を返す。期限なしのときはキーごと省略する（`*time.Time` + `omitempty`）。`EventSummary` は一覧・マイページ・プロフィールの 3 エンドポイントで共有しているため、3 つに同時に露出する。

## 理由

- **「期限なし」に補完できる既定値がない**: ADR-0018 が NULL を避けられたのは、未指定を `event_date` と同値で補完しても意味が歪まなかったからである。申込期限には対応する値がない。`event_date` や `end_date` を既定値にすると「開催直前まで申し込める」という投稿者が選んでいない意思表示になり、「期限を設けない」と「開始時刻が期限」を区別できなくなる。この 2 つは告知内容として別物であり、区別する要件がある。
- **状態が 1 つ増える代わりに意味が一意になる**: 読み出し側に NULL 分岐が増えるのは ADR-0018 が指摘したとおりだが、今回の NULL は「実在する状態（期限なし）」を表しており、ADR-0018 が退けた「未入力を保持するだけの NULL」とは性質が異なる。
- **`CHECK` の上限を `end_date` にする**: 開催中の飛び入り受付を DB が禁止しないようにする。制約は緩める方向なら既存データを壊さない一方、締める方向は違反データが出うる。ただし本リポジトリは適用済みマイグレーションを直接編集する運用のため、どちらの向きでも DB の作り直しか手当てが要る。移行の容易さで差がつかない以上、運用の幅を先に確保する方を採る。
- **サービス層の検証境界を DB の `CHECK` と揃える**: 二段の境界をずらすと、DB が許すのに API が拒む状態になり、どちらが仕様かを説明できなくなる。開催中の飛び入り受付を許すという DB 側の判断を、そのまま API の契約とする。
- **未指定はゼロ値で表す**: ADR-0018 の `EndDate` と同じ「ゼロ値＝未指定」方式に揃え、repository では `nullString` / `nullInt32` と同型の `nullTime` で NULL に変換する。JSON の `null` と欠落を区別しないのは、どちらも「期限なし」で扱いが同じであり、区別を使う要件がないためである。
- **レスポンスの NULL 表現を `cancelledAt` に揃える**: `EventResponse` で NULL 許容の日時は `CancelledAt` だけであり、これは `*time.Time` + `omitempty` でキーごと省略する形をとっている。同じ「NULL 許容日時」に 2 つの流儀が混ざると、後から片方へ統一するときにレスポンス契約の破壊的変更になる。
- **一覧は共有型のまま出す**: `EventSummary` を一覧専用に分ければ露出を `GET /api/v1/events` だけに閉じられるが、`eventSummarySelect` と `scanEventSummaries` も分岐し、以後この型に項目を足すたびにどちらへ入れるかの判断とテストが増える。申込期限は単体取得で既に公開している情報であり、プロフィール一覧の公開範囲は ADR-0025 が別途制御しているため、共有型に足しても新たに秘匿情報が増えるわけではない。
- **「開催前まで」を強制したい場合はサービス層で行う**: 一次判定はサービス層、DB は最後の防衛線という ADR-0018 の型と一貫する。DB の `CHECK` はあくまで明らかに矛盾したデータ（終了後の締切）を止めるためのものとする。

## 影響（結果）

### 良い影響

- 「申込期限なし」を、番兵値や別フラグを使わずに表現できる。
- 終了日時より後という明らかに矛盾した期限は、DB が拒否する。
- 既存クエリは `SELECT *` を使っていないため、カラム追加で壊れる読み出しはない。既存の `INSERT INTO events (...)` はカラムを明示しているので、そのまま NULL が入る。
- 投稿時に申込期限を設定でき、「期限なし」は `applicationDeadline` を送らないことで表現できる。
- 一覧画面で締切を表示するのにイベントごとの詳細取得が不要になる。
- `CHECK` 違反になる入力はサービス層で 400 として止まるため、`pq` エラー由来の 500 にならない。

### トレードオフ・制約

- **読み出し側に NULL 分岐が増える**: 締切判定は `application_deadline IS NULL OR now() <= application_deadline` の形になる。この分岐を書き漏らすと、期限なしのイベントが「締切済み」に見える事故が起きうる。
- **DB は開催開始後の期限を許す**: 「申込は開催前まで」を強制したい場合、サービス層で `application_deadline <= event_date` を追加検証する必要がある。
- **既存環境は DB の再作成が必要**: マイグレーションファイルの直接編集で追加したため、適用済みの環境では goose が再実行しない。開発 DB は作り直す。適用済みの他環境には `ALTER TABLE events ADD COLUMN application_deadline TIMESTAMPTZ;` と対応する `ADD CONSTRAINT` を手当てする。
- **マイページ・プロフィールの一覧にも同時に出る**: `EventSummary` が共有型のため、`GET /api/v1/events` だけでなく `/api/v1/me/events` と `/api/v1/profiles/{id}/events` のレスポンスにも `applicationDeadline` が現れる。露出を片方だけに戻すことは後からできない（レスポンス契約の破壊的変更になる）。
- **クライアントはキーの欠落を「期限なし」と解釈する必要がある**: `omitempty` によりフィールド自体が JSON に現れない。`null` が返ることを前提に書かれたクライアントは、値の欠落を別扱いしないよう注意が要る。
- **検証を後から締めると破壊的変更になる**: サービス層の上限を `eventDate` に変えるのはコード変更だけで済むが、それまで通っていたリクエストが 400 になる。DB 制約と違い移行は不要な代わりに、クライアントへの影響が出る。

## 検討した代替案

- **`NOT NULL` にして「期限なし」を番兵値（遠い未来日時や `infinity`）で表す**:
  NULL 分岐が消え、`CHECK` を無条件に効かせられる。しかし「期限なし」を特定の日時で表すのは意味の詰め込みであり、番兵値を知らない表示側が遠い未来の締切をそのまま画面に出す事故を招く。`timestamptz` の `infinity` はドライバごとに扱いが異なり、Go の `time.Time` へマッピングする際に追加の考慮が要る点も避けたい。不採用。
- **申込設定を別テーブル（`event_application_settings` 等）に切り出す**:
  申込関連の設定が今後増えたときに拡張しやすい。しかし現時点で必要なのは 1 カラムであり、そのために 1:1 テーブルと JOIN を増やすのは早すぎる。設定項目が複数になった時点で再検討する。不採用。
- **`CHECK (application_deadline <= event_date)` にする**:
  「申込期限は開催前」という直感に合い、データの意味も締まる。しかし開催中の飛び入り受付を DB が禁じてしまい、その運用が必要になったときにマイグレーション編集と適用済み環境の手当てが要る。同じ判定はサービス層で表現できるため、DB 側は緩めに保つ。不採用。
- **`CHECK` を置かない**:
  終了日時より後の期限という明らかな矛盾を防げない。ADR-0018 の「DB を最後の防衛線として持つ」方針から外れる。制約を置いても通常運用のコストはゼロ。不採用。
- **リクエストを `*time.Time` にして JSON の `null` と欠落を区別する**:
  「期限なしを明示した」と「送らなかった」を区別できるが、保存結果はどちらも NULL で扱いが同じであり、区別を消費する要件がない。全層に nil チェックが増える割に得るものがない。不採用。
- **サービス層の上限を `eventDate` にする**:
  「申込は開催前まで」を API の契約として強制できる。しかし DB が許す範囲より狭くなり、二段の境界がずれる。開催中の受付という運用を最初から塞ぐ理由も現時点でない。必要になった時点でサービス層だけを締める（破壊的変更として扱う）。不採用。
- **レスポンスで `null` を明示する（`omitempty` を付けない）**:
  「期限なし」であることがキーの存在として明示され、値の欠落と取り違えにくい。しかし `cancelledAt` と流儀が分かれ、同じ型の項目でクライアントの分岐が 2 通りになる。OpenAPI から型を生成する限りどちらも optional 相当で、生成物の差もほとんど出ない。不採用。
- **一覧専用のサマリー型を分けて露出を絞る**:
  `GET /api/v1/events` にだけ申込期限を出せる。しかし共通の SELECT とスキャン関数も分岐させることになり、重複が確実に増える一方で、絞った先に守るべき秘匿情報があるわけではない。不採用。
- **相対表現（開催の N 日前）で持つ**:
  開催日時を変更したときに期限が自動で追従する利点がある。しかし「◯月◯日締切」という一般的な告知形式をそのまま保持できず、絶対日時への変換がすべての読み出し箇所に必要になる。不採用。
