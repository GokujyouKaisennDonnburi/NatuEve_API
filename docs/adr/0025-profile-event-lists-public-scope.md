# ADR-0025: プロフィールのイベント一覧は主催・参加済みのみ公開し、申し込み中は本人限定にする

- ステータス: Accepted
- 日付: 2026-08-18
- 関連: #173, ADR-0010, ADR-0022, ADR-0024

## コンテキストと課題

ADR-0024 で本人向けの `GET /api/v1/me/events` を追加した際、他人のプロフィールページ向けの
一覧は「URL を分けたうえで service / repository を共有する」と決め、実装は別 issue に送った。
本 ADR はその実装（#173）で確定させる残りの論点を扱う。

決めるべきことは3つある。

1. **公開する種別**: ADR-0024 は公開側を hosted / attended とし、applied（申し込み中）は
   本人限定と決めていた。この線引きを実装でどう強制するか。
2. **件数（counts）の公開範囲**: 一覧を返さなくても、件数を返せば「この人はいま何件申し込んで
   いるか」は伝わる。counts に applied を含めるかどうか。
3. **存在しないプロフィールの扱い**: 404 を返すか、空の一覧を 200 で返すか。また、
   プロフィール不在（404）と `type` 不正（400）が同時に起きたときどちらを返すか。

前提と制約:

- このエンドポイントは認証不要の公開エンドポイント（`GET /api/v1/profiles/{id}` と同じ位置づけ）。
- 返すイベントサマリー（`model.EventSummary`）は `GET /api/v1/events` と同じで、公開情報のみを含む
  （参加者の氏名・メールアドレスは含まない。ADR-0022）。
- 過去の参加履歴を第三者に見せること自体は、イベント集約サイトの性質上許容する
  （主催者・参加者の実績が信頼の材料になる）。

## 決定

`GET /api/v1/profiles/{id}/events?type=hosted|attended` を**認証不要の公開エンドポイント**として
追加する。`type=applied` は未知の値と同じく 400 で拒否し、本人が申し込み中を取得する経路は
認証必須の `GET /api/v1/me/events` に限る。

レスポンスの `counts` は `hosted` / `attended` の2種別のみを含む専用型
（`model.ProfileEventCounts`）とし、applied の件数も公開しない。

存在しないプロフィール ID は 404 を返す（`GET /api/v1/profiles/{id}` と揃える）。
ID が UUID として解釈できない場合は 400（パス由来のため。ADR-0010）。
検証の順序は「ID の形式（400）→ プロフィールの存在（404）→ `type` の妥当性（400）」とし、
存在しないプロフィールに不正な `type` を投げた場合は 404 を返す。

公開してよい種別の制限は handler ではなく service（`ListPublicByProfile`）で行う。
一覧の取得自体は本人向けの `ListByProfile` へ委譲し、公開対象外の件数を落とした
レスポンスへ詰め替える。

## 理由

**閲覧者を見ない設計にする**のが公開範囲を守る最も確実な方法である。1つの URL で本人と他人を
兼ね、`type=applied` のときだけ「閲覧者 == 対象者」を検証する設計も可能だが、その分岐を1つ
落とすだけで申し込み履歴が漏れる。公開エンドポイントが閲覧者の概念を一切持たなければ、
漏洩は分岐の正しさではなく構造で防がれる。クライアント側の負担もほぼ変わらない
（「自分のページか」の判定は、申し込み中タブを出すかどうかの判断で既に必要）。

**counts から applied を外す**のは、件数もまた申し込み状況の開示だからである。一覧を隠して
件数だけ返すと「今3件のイベントに申し込んでいる」ことが他人に分かる。`model.MyEventCounts`
（3種別）をそのまま返して applied をゼロで埋める案は、ゼロが「申し込みが無い」のか
「非公開」なのか区別できず、実装ミスで実数が入る余地も残る。型ごと分けて、公開できない
数値がレスポンス DTO に存在しない状態にする。

**404 を返す**のは、空配列だと「存在しないユーザー」と「イベントが1件も無いユーザー」を
区別できないためである。クライアントはプロフィール本体（`GET /api/v1/profiles/{id}`）も
取得するので、両者でステータスが食い違わないほうが扱いやすい。

**プロフィールの存在を `type` の妥当性より先に判定する**のは、`/profiles/{id}/events` が
プロフィールに従属するコレクションだからである。親リソースが存在しなければコレクション自体が
存在せず、その状態でクエリパラメータの当否を返しても、クライアントが直すべき本質的な誤り
（存在しない ID を指している）が伝わらない。

**種別の制限を service に置く**のは、そこが信頼の境界だからである（CLAUDE.md）。
ADR-0024 では「公開してよい種別の制限だけを handler 側で行う」と書いたが、実装時に
service 側へ寄せた。handler で弾く形にすると、将来この service メソッドを別の経路から
呼んだときに制限が外れる。取得処理は `ListByProfile` への委譲にして重複を持たない
（正規化やクエリ条件が片方だけ変わるドリフトを防ぐ）。

## 影響（結果）

### 良い影響

- 公開エンドポイントが認証情報を参照しないため、閲覧者判定の漏れによる情報漏洩が起こり得ない。
- repository は追加なしで済む（`myEventClauses` / `ListMySummaries` / `CountMyEventKinds` を再利用）。
  種別ごとの絞り込み条件が引き続き1箇所にあり、`/me` と `/profiles/{id}` で結果がずれない。
- 公開してよい数値だけを持つ DTO になり、「うっかり applied を含めた」がレビューで見つけやすい。

### トレードオフ・制約

- **自分のプロフィールページでも、申し込み中タブだけは `/me/events` を叩く**必要がある。
  クライアントは1画面で2つのエンドポイントを使う。
- 件数取得は `/me` と同じ `CountMyEventKinds`（applied を含む3種別を1クエリで数える）を使い、
  applied を捨てている。公開側では使わない集計を1つ余分に行うが、同一クエリ内の
  スカラーサブクエリ1本ぶんであり、条件定義を1箇所に保つ利点を優先した。
- 参加済みイベントの公開は、過去の行動履歴の公開でもある。将来プロフィールに公開設定を
  持たせる場合、本 ADR を置き換える。
- プロフィールの存在確認に1クエリ増える（handler で `ProfileService.GetByID` を呼ぶ）。
- 存在しないプロフィールに不正な `type` を投げると 400 ではなく 404 が返る。
  リクエストが2重に誤っている場合、より根本的な誤りだけが伝わる。
- 公開用レスポンスは本人向けレスポンス（applied を含む `MyEventCounts`）を組み立ててから
  公開対象だけを詰め替える。公開できない件数が一瞬メモリ上に存在するが、
  シリアライズされる DTO（`ProfileEventCounts`）には該当フィールドが無い。

## 検討した代替案

- **案A: 1つの URL で3種別を扱い、applied のときだけ本人判定する** / クライアントが1エンドポイント
  で済むが、公開エンドポイントに閲覧者の概念が入り、分岐の欠落が即座に漏洩になる。
  得られる利便性に対してリスクが釣り合わない。
- **案B: counts は `MyEventCounts` を使い回し、applied をゼロで埋める** / 型を増やさずに済むが、
  ゼロの意味が多義的になり、実数が漏れる経路も残る。
- **案C: `type` の妥当性をプロフィールの存在より先に判定する** / 形式だけで判定できる誤りを
  先に返せてクエリも節約できるが、そのために種別のホワイトリストを handler にも置くか、
  service のシグネチャを分解する必要がある。制限を1箇所（service）に保つことを優先した。
- **案D: 存在しないプロフィールでも空配列を 200 で返す** / 実装は単純だが、クライアントが
  「ユーザーが居ない」と「イベントが無い」を区別できず、プロフィール本体の 404 と挙動が食い違う。
- **案E: 参加済みも非公開にし、公開は主催イベントのみにする** / プライバシーは最も厚くなるが、
  参加実績はイベント集約サイトにおける利用者の信頼材料であり、公開の価値が上回ると判断した。
