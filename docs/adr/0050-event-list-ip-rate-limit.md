# ADR-0050: イベント一覧 API に API 側で IP レートリミットを掛け、他の公開 GET には今は掛けない

- ステータス: Accepted
- 日付: 2026-11-16
- 関連: #276, #215, #244, ADR-0034, ADR-0037, ADR-0043

## コンテキストと課題

`GET /api/v1/events` は認証不要の公開エンドポイントで、IP レートリミットが掛かっていなかった。
同一 IP からの連打で DB を占有されると、他の利用者がイベントを探せなくなる（PBI78 のゴール 3）。
決めることは、上限値（平均レートとバースト）、他の公開 GET にも掛けるか、API と Cloudflare のレート制限ルールのどちらで行うかの 3 つである。

制約と前提は次のとおり。

1. **一覧は公開 GET の中で最も重い**: キーワードは 5 項目に `normalize(col, NFKC) ILIKE` を掛け、地域は最大 200 件の OR 条件になり、
   総件数の `COUNT(*)` も行う（ADR-0008、ADR-0028、ADR-0030）。
2. **本番は Cloud Run 1 台・DB 接続に上限あり**（ADR-0037）。レートリミットはインスタンスのメモリ上で数え、台数が増えると緩む。
3. **フロントの呼び方**（NatuEve_Web_Frontend の 4605c25 時点）:
   - 一覧はクライアントコンポーネント（`useEventList`）からだけ呼ぶ。SSR からは呼ばない。
   - 呼び出しは画面操作 1 回につき 1 回（初期表示・ページ送り・並び替え・検索の確定・絞り込みの適用）。検索は入力中には呼ばない。
   - 失敗時は 200ms・400ms・600ms・800ms・1000ms の間隔で最大 5 回再試行する（初回から累計で約 3 秒）。
4. **SSR から呼ぶ公開 GET がある**: イベント詳細（`GET /api/v1/events/{id}`）は SSR から呼ぶ（`revalidate 60`）。
   SSR 経由のリクエストで API に届く利用者 IP は未検証である（#244）。
5. **IP を共有する利用者がいる**: 携帯回線の CGNAT、イベント会場や学校の Wi-Fi などでは、複数の利用者が同じ IP になる。
6. **ゾーンのレート制限ルールが Custom Domain の Worker 宛てのリクエストに効くかは未検証**（ADR-0034 の未検証の前提）。

## 決定

**`GET /api/v1/events` に、API 側で同一 IP あたり平均 2 回/秒・バースト 30 回の IP レートリミットを掛ける。他の公開 GET には今は掛けない。**

1. 実装: `middleware.NewIPRateLimiter` のこのルート専用のインスタンスを、ルートのミドルウェアとして付ける。超過時は 429（`rate_limited`）を返す。
2. 上限値: 平均 2 回/秒（0.5 秒ごとに 1 回分戻る）、バースト 30 回。
3. 対象外: `GET /api/v1/tags`・`/events/{id}`・`/profiles/{id}`・`/profiles/{id}/events`・`/events/{id}/report` には掛けない。
   sitemap は ADR-0043 のとおり別のインスタンスで制限する。
4. 見直す時期: #244 で SSR 経由の利用者 IP を確かめた後、または一覧以外の公開 GET で負荷の問題が見えたとき。

## 理由

- **API 側で行う**: 既存の `IPRateLimiter`（参加申込・sitemap）と同じ仕組みで、429 の形式が統一フォーマットになり、swag に記述でき、CI でテストできる。
  Cloudflare のルールはダッシュボードの設定でリポジトリに残らず、Custom Domain の Worker 宛てに効くかも未検証である（前提 6）。
- **平均 2 回/秒**: 1 人の画面操作は 1 回 1 リクエストで、1 回/秒を超え続けることはない。上限が効くのは主に IP を共有する場合で、
  1 人が 10 秒に 1 回操作するとして、2 回/秒なら同じ IP の 20 人まで枠が減り続けない。1 IP から毎分 120 回の一覧取得は、連打を止める目的には十分小さい。
- **バースト 30 回**: 429 になるのは t 秒間に 30 + 2t 回を超えたときで、10 秒なら 51 回目になる。ページ送りの連続クリックや検索のやり直しでは届かない。
  使い切っても 0.5 秒で 1 回分戻るため、同じ IP から他に送っていなければ、フロントの再試行（前提 3）は遅くとも累計 600ms の 2 回目で成功する。
- **一覧だけに掛ける**: 重い検索を伴う公開 GET は一覧だけである（前提 1）。イベント詳細は SSR から呼ぶため、SSR 経由の IP が利用者ごとに分かれない場合、
  掛けると全利用者が 1 つの枠を共有して 429 になる（前提 4）。残りは主キーでの取得や小さな結果で、軽い。
- **専用のインスタンスにする**: 一覧の枠を他の API と共有しないため、一覧を使い切っても参加申込や詳細には影響しない。

## 影響（結果）

### 良い影響

- 同一 IP からの一覧の連打は平均 2 回/秒に抑えられる（インスタンスが一時的に増えると、ADR-0037 のとおり最大 2 倍まで緩む）。
- 1 人の通常の画面操作では 429 にならない。

### トレードオフ・制約

- **分散したアクセスは止められない**: IP ごとに数えるため、多数の IP からの大量アクセスには効かない。
- **リクエストは Cloud Run に届く**: 拒否は API で行うため、Cloud Run のリクエスト数には数えられる。
- **IP を共有する呼び出し元は枠も共有する**: 同じ IP で同時に操作する人が多いと 429 になりうる。`CF-Connecting-IP` が入らない経路も同様（Deployment.md）。
- **SSR から一覧を呼ぶようになったら見直しが要る**: SSR 経由の IP が利用者ごとに分かれない場合、全利用者が 1 つの枠を共有する（#244）。
- **429 に `Retry-After` は付かない**: ADR-0043 と同じ。フロントは 429 を他の失敗と同じく再試行する。
- **不正なクエリは数えない**: クエリの検証（ADR-0021）が先に 400 を返すため、その分は枠を消費しない。DB には届かない。
- **他の公開 GET は無制限のまま**: 見直すまでは、詳細などへの連打は止まらない。

## 検討した代替案

- **Cloudflare のレート制限ルールで行う**: Cloud Run に届く前に止められる / ダッシュボードの設定でリポジトリに残らずテストできず、
  Custom Domain の Worker 宛てに効くかも未検証のため不採用。
- **平均 1 回/秒にする**: 1 人の操作には足りる / IP を共有する利用者の余裕が半分になり、負荷の面では 2 回/秒との差が小さいため不採用。
- **参加申込・sitemap と同じく分単位の厳しい値（平均 5 回/分など）にする**: 閲覧のたびに呼ぶ API のため、通常の操作で 429 になる。不採用。
- **全ての公開 GET に同じ制限を掛ける**: 一度に守れる / SSR から呼ぶ詳細で全利用者が枠を共有するおそれがあるため、#244 の検証まで不採用。
- **公開 GET 全体で 1 つの枠を共有する**: インスタンスが 1 つで済む / 一覧の利用で詳細などまで 429 になるため不採用。
