# ADR-0044: ゲストの参加申込は確認メールのトークンで確定する

- ステータス: Accepted
- 日付: 2026-11-12
- 関連: #273, #205, ADR-0016, ADR-0031, NatuEve_Web_Frontend#403

## コンテキストと課題

現状の参加申込は認証任意で、未ログインでも申し込める。申込済みのメールアドレスには
409 `already_joined` を返すため、応答の違いから第三者が申込の有無を判別できる。
また、他人のメールアドレスで未ログイン申込をすると、その行が `event_members` に残り、
本人のログイン申込を長期間ブロックできる（#205）。

PBI77 のゴール 1〜3 を満たすには、メールアドレスの所有者だけが申込を確定でき、
申込の有無を応答から判別できない必要がある。一方、確認メールと案内メールは Resend の
無料枠（1 日 100 通）を消費し、同期送信すると応答時間の差が申込の有無の手がかりになる。

決める必要があるのは、確認トークンの形式と有効期限、未確定の申込の保存方法と掃除、
申込済みアドレスへの応答、確定用エンドポイント、メールの送信方式である。

## 決定

**未ログインの参加申込は `event_members.status='pending'` として保存し、確認メールの
トークンで `confirmed` に遷移させる。確認・案内メールは ADR-0016 の outbox に予約し、
API の応答はメール送信に依存させない。**

1. `event_members` に次の列を追加する（ADR-0044）。
   - `status`（`pending` / `confirmed`、既定値 `confirmed`）
   - `confirmation_token_hash`（SHA-256 の hex。平文トークンは保存しない）
   - `confirmation_token_expires_at`
   - 既存行は `confirmed` として扱う。`pending` はトークン必須、`confirmed` は
     トークンなしという CHECK 制約を置く。
2. 確認トークンは `crypto/rand` の 32 バイトを base64url（パディングなし）で表した
   文字列とする。有効期限は発行から 24 時間で、確定に成功するとハッシュと期限を NULL に
   して単回使用を保証する。トークンはイベント ID と組み合わせて検索する。
3. 確認メールのリンクは
   `{WEB_BASE_URL}/events/{eventID}/join/confirm?token={token}` とし、Web の確認画面を
   経由させる。確定用 API は `POST /api/v1/events/{id}/join/confirm` で、
   リクエストボディは `{"token":"..."}`、成功時は `200` と
   `{eventId, confirmedAt}` を返す。
4. 未確定の申込は参加者一覧・参加人数・定員判定・通知宛先に含めない。
   `event_members` を参照する読み取り系と定員の集計に `status='confirmed'` を付ける。
5. 期限切れの `pending` は、同じイベントへの次回申込時に遅延削除する。イベントに
   アクセスが無い間は行が残るが、`pending` は読み取りから除外され、期限を過ぎた
   トークンでは確定できない。部分インデックスで検索と削除を補助する。
6. 未ログインで申込済みのアドレスからの再申込は 409 を返さない。新規申込と同じ 201 と
   本文の形で応答し、既存申込の内容（名前・人数など）は返さず、送信された内容から
   レスポンスを組み立てる。案内メールは「すでに申し込まれています」の文面で outbox に
   予約する。ログイン中の重複は、入力されたメールアドレスが JWT の email と一致することを
   確認したうえで、従来どおり 409 `already_joined` を返す（案内メールは送らない）。
7. 定員・申込期限・終了日時・カテゴリの判定は、新規申込と重複申込で同じ順序・同じ結果に
   する。定員超過なら重複申込でも新規と同じ `409 capacity_full` を返す。ただし案内メールは
   重複時に予約する。
8. 確認メールと案内メールは、参加申込の DB 更新と同一トランザクションで
   `event_notification_outbox` に INSERT する。outbox に `recipient_kind='email'` と
   `recipient_email` を追加し、既存ワーカーが1宛先1通で送信する。同期送信は行わない。
9. 確定時はイベント行をロックし、確定済みの申込だけを数えて定員を再確認する。
   申込期限は再確認しない（期限内に受け付けた申込をメール確認の遅れで失効させないため）。
   取消済み・終了済みイベントでは確定できない。
10. ログインしての申込は従来どおり即 `confirmed` とする。ただし、入力されたメールアドレスが
    JWT の email と一致することを必須とし、一致しない場合は 400 を返す。同じイベント・同じ
    メールの `pending` 行がある場合は、その行を破棄してログイン申込で置き換える。
11. #205 について、登録済みメールでのゲスト申込は引き続き受け付ける。ただし
    `pending` のままでは確定せず、メールアドレスの所有者が確認した場合だけ参加者に
    なる。ログイン申込は JWT の email と一致するメールだけを許可するため、第三者が
    他人のメールで即時確定することもできない。確定済みゲスト行をプロフィールへ
    自動で紐づける処理は行わない。入力されたメールアドレスだけではログイン中
    アカウントの所有証明にならず、他人の申込を引き継げてしまうため。紐づけは別の
    Issue で扱う。

## 理由

- 未確定を `status` で表すと、既存の `event_members` の一意制約（イベント×メール）を
  そのまま使い、確定時は同じ行を更新するだけで済む。別テーブルへの移し替えが不要。
- トークンをハッシュで保存すると、DB の内容が漏れても確認リンクを再利用できない。
  ランダムな不透明トークンは JWT のようにクレームを持つ必要がなく、失効も行の更新だけで
  完結する。
- 応答を送信内容から組み立てると、重複時にも既存申込の名前・人数を返さずに済む。
  定員や期限の判定を新規申込と同じにすることで、応答の違いから申込の有無を推測できない。
- outbox を使うと、応答時間がメール送信に依存せず、Resend の一時障害やレート制限にも
  既存のリトライで回復できる。参加申込の確定とメール予約が同一トランザクションになるため、
  「確定したのにメールが無い」状態を減らせる。
- ログイン申込で `pending` 行を置き換えると、第三者が先に作った未確定行で本人の
  ログイン申込がブロックされない。

## 影響（結果）

### 良い影響

- 未ログイン申込は、メールアドレスの所有者が確認するまで参加者として扱われない。
- 申込済みのアドレスに再申込しても、応答から申込の有無が分からない。
- 確認メールの送信失敗やレート制限は outbox のリトライで回復する。
- 未確定の申込が参加人数・定員・通知宛先に混ざらない。

### トレードオフ・制約

- `pending` 行は同じメールアドレスの再申込をトークン期限（24 時間）までブロックする。
  大量のメールアドレスで埋められる可能性は、join の IP レート制限と短い期限で抑える。
- 重複時の案内メールは確認リンクを再送しない。確認メールを紛失した場合は、トークンの
  期限切れ後に再申込する必要がある。
- 確認・案内メールも Resend の送信枠を消費する。outbox が最終失敗した場合はログで検知し、
  既存の手動再送手段で対応する。
- outbox の送信は非同期のため、確認メールの到着は数秒〜数分遅れることがある。
- メール本文には確認リンク（平文トークン）が入り、送信済みの outbox 行にも残る。
  トークンは 24 時間で失効するため、期限後の再利用はできない。
- 確定済みゲスト行はプロフィールに紐づかない。ゲストとして確定した参加者は、
  ログイン参加者向けの leave / absence API を使えない（従来の匿名参加と同じ）。
- 登録済みメールでログイン中に申し込んだ場合、既存の確定済みゲスト行とメールが一致すると
  新規の参加にはならず、案内メールだけが届く。本人がゲスト行を管理できない問題は残る。

## 検討した代替案

- **未確定専用のテーブルを新設する**: 既存の `event_members` の一意制約・内訳・通知宛先の
  クエリを二重に持つことになり、確定時の移し替えも必要。不採用。
- **JWT を確認トークンにする**: 署名鍵の管理とクレーム設計が必要で、失効・単回使用の
  管理は結局 DB の行更新になる。不透明なランダムトークンで十分。不採用。
- **参加申込 API 内で同期的に確認メールを送る**: 実装は小さいが、送信失敗時の応答と
  DB の状態がずれ、応答時間の差も申込の有無の手がかりになる。不採用。
- **登録済みメールのゲスト申込を 409 で拒否する**: アカウントの存在を外部から確認できる
  うえ、ゲスト参加の手軽さを失う。確認メールで所有者を確かめる方式を採用。
- **重複時は確認メールを再送する**: 確認メールを紛失した利用者には親切だが、AC の
  「すでに申し込まれています」の案内と異なり、第三者が案内メールを送り続けられる
  問題も変わらない。案内メールを送る。不採用。
