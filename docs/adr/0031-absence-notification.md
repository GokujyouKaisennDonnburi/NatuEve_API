# ADR-0031: 申込期限経過後の参加キャンセルは欠席連絡 API で行い主催者へ通知する

- ステータス: Accepted
- 日付: 2026-09-02
- 関連: ADR-0011, ADR-0016, ADR-0029

## コンテキストと課題

既存の参加キャンセル API `POST /api/v1/events/{id}/leave`（ADR-0011）は申込期限内の
キャンセルを想定しており、理由の記録も主催者への連絡も行わない。しかし申込期限
（`events.application_deadline`、ADR-0029）を過ぎた後も、体調不良・家庭の都合等で
参加できなくなる参加者は存在し、主催者は人数の増減を把握する必要がある。

決めるべきことは次の 5 点である。

1. 期限後のキャンセルを leave に任せるか、別 API にするか
2. 欠席した参加者の `event_members` 行（参加行）を削除するか残すか
3. 欠席理由をどう受け取り・どこに保存するか
4. 主催者へのメール通知をどう保証するか（既存 outbox は参加者全員宛が前提）
5. 欠席連絡を受け付ける期間の境界

## 決定

**期限経過後のキャンセルは専用 API `POST /api/v1/events/{id}/absence`（認証必須）
で行い、参加行削除・`action='absence'` ログ追記・主催者宛メールの outbox 予約を
1 トランザクションで実行する。あわせて leave を期限ありイベントの期限経過後は
409 で拒否する。**

1. **leave との境界**:
   - leave は「申込期限内のキャンセル」。期限ありイベントで `application_deadline`
     経過後の呼び出しは 409 `deadline_passed` を返し、欠席連絡 API へ誘導する。
   - 期限なし（`application_deadline IS NULL`）のイベントは従来どおり leave を
     常時利用できる（期限の概念がないため境界判定が成立しない）。
   - absence は期限前に呼ぶと 409 `before_deadline` を返す。
2. **参加行の扱い**: absence は leave と同じく `event_members` から該当行を
   DELETE する。欠席ステータス列の追加は行わない。欠席の事実は
   `event_participation_logs` と主催者へのメールで伝わる。
3. **欠席理由**: リクエストボディは `reason`（任意・指定する場合は `illness` /
   `family` / `weather_transport` / `other` の 4 値）と `detail`（任意・200 文字以内）。
   両方を `event_participation_logs` の新カラム（`reason`, `detail`）に保存し、
   主催者メールの本文にも記載する。DB 側にも CHECK 制約で `reason` の値域を縛る。
   `reason`・`detail` の未指定はフィールド省略・`null`・空文字のいずれも同じ扱いとし、
   DB には NULL で保存する。レスポンスでも `null` を返す（空文字にしない）。
   `reason` 未指定時は主催者メールの本文に「欠席理由：記載なし」と記す。
4. **主催者への通知**: `event_notification_outbox` に `recipient_kind`
   （`members` = 従来の参加者全員宛 / `organizer` = 主催者 1 人宛）を追加し、
   absence のトランザクション内で `organizer` 行を INSERT する（ADR-0016 の
   Outbox パターンを踏襲）。ワーカーは `recipient_kind` に応じて宛先を解決する
   （`organizer` は `events` JOIN `profiles` の `email` から取る）。件名・本文は
   サーバーが組み立て、クライアントからは送らない。
5. **受付期間**: 申込期限経過後（期限なしイベントは常時）〜 `end_date` まで。
   `end_date` 経過後の absence は 409 `event_ended`、取消済みイベントは
   409 `event_cancelled` を返す。

## 理由

- **leave をそのまま使わせない**: 期限後のキャンセルは主催者への連絡を伴う業務
  上必須の状態遷移であり、理由なしで黙って抜けられると主催者が人数を把握できなく
  なる。「キャンセルしたら主催者に通知する」という不変条件をサーバー側に集約する
  （CLAUDE.md「ドメインロジックの集約」）ためには、別エンドポイントで強制するのが
  最も単純である。
- **参加行の削除**: leave と同じ扱いにすることで、参加者一覧・参加人数・一斉送信の
  宛先から自然に外れ、既存の集計・送信ロジックへの影響がゼロになる。欠席者を一覧に
  残す案はステータス列追加と各所の除外ロジックを要求し、得られる利益（一覧上の
  欠席表示）に比べて変更範囲が大きい。欠席の事実は participation_logs で追跡できる。
- **欠席理由を任意にする**: 主催者にとって最も損失が大きいのは「理由が分からない
  こと」ではなく「欠席連絡自体がされないこと」であり、理由の入力を必須にして連絡の
  ハードルを上げるべきではない。未指定は空文字ではなく NULL で保存し、「未指定」の
  表現を DB・API の両方で 1 つに保つ（空文字を許すと未指定判定が
  `reason IS NULL OR reason = ''` に分岐する）。
- **outbox の種類拡張**: 主催者へのメールも送信保証・自動リトライの対象にする
  べきで、同期送信では「欠席処理成立・通知失敗」の穴が残る（ADR-0016 の議論と
  同型）。宛先が 1 人であることだけが既存 outbox と異なるため、宛先の解決方法を
  `recipient_kind` で表現するのが最小の拡張になる。
- **受付期間**: 終了済みイベントへの欠席連絡は誰の意思決定にも役立たず、誤操作
  （終了後のうっかりタップ等）による無意味な主催者メールを生むため `end_date` で
  打ち切る。期限なしイベントを常時受付にするのは、当日欠席（体調不良等）の連絡
  ユースケースが期限の有無に依存しないと考えられるため。

## 影響（結果）

### 良い影響

- 期限後の欠席が理由付きで記録され、主催者への通知が送信保証付きで自動的に行われる。
- leave・absence の役割分担が明確になり、クライアントは期限と end_date で
  使い分けるだけでよい（両方ともレスポンスで返っている）。
- outbox の `recipient_kind` 拡張により、今後の「主催者宛通知」系は同じ仕組みを
  再利用できる。

### トレードオフ・制約

- **leave の breaking change**: 期限ありイベントの期限経過後に leave を叩く
  クライアントは 409 を受け取る。フロントは `deadline_passed` を受け取ったら
  absence を呼ぶように修正する必要がある。
- 欠席理由はセンシティブな個人情報であり `event_participation_logs` に永続化される。
  閲覧手段は現状 DB 直参照のみで、API では公開しない（公開要件が出たら別 ADR）。
- 主催者メールの宛先は `profiles.email` に依存する。events.profile_id は FK だが
  NULL 可能であり、NULL の場合（または profiles 行不在・email 空）は送信できない。
  その場合の行は pending のまま 30 秒周期で再試行され続け、エラーログで検知する
  （一時障害と同一セマンティクス。恒久障害の区別は将来課題）。
- 匿名参加者は ADR-0011 と同じ理由（本人性・ログの NOT NULL）で対象外。

## 検討した代替案

- **leave を期限後もそのまま使わせ、理由を任意ボディで受け取る**:
  理由の記録と主催者通知を強制できず、期限前後で leave の意味論が曖昧になる。
  不採用。
- **参加行を欠席ステータス付きで残す**: 主催者の一覧で欠席者が見える利点はあるが、
  participantCount・ListRecipients・一斉送信の全てに除外ロジックが必要になり変更
  範囲が広い。欠席連絡はメールで足りるため不採用。
- **主催者へのメールを同期送信する**: 実装は最小だが「欠席処理成立・通知失敗」の穴
  が残り、Resend の一時障害でユーザーが欠席連絡自体を失敗扱いして再送し、無駄な
  再処理を誘発する。ADR-0016 と同じ結論のため不採用。
- **主催者宛通知専用の outbox テーブルを新設する**: テーブル・ワーカーが二重化し、
  リトライ・後始末のロジックも重複する。`recipient_kind` 1 カラムの追加で済む
  既存テーブル拡張を採る。不採用。
- **`event_ended` を 400/404 ではなく 409 にする**: リソースの状態（終了済み）と
  リクエストの意図（欠席連絡）の競合であり、join API の `event_cancelled` 409 と
  エラー体系が揃う 409 を採用。
