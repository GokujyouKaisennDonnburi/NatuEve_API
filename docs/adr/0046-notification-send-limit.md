# ADR-0046: 一斉送信の回数上限をイベントごと・24時間あたり5回とし、DB で数える

- ステータス: Accepted
- 日付: 2026-11-13
- 関連: ADR-0005, ADR-0007, ADR-0016, ADR-0031, ADR-0037
- 変更: ADR-0007 の決定（profileID / eventID 単位のレート制限・送信量カウンタを実装しない）を置き換える（Supersedes, 部分的）。ADR-0007 の「Resend 有料プランへの移行が必須」という前提と、1 リクエストあたりの宛先数上限（`maxNotificationRecipients` = 100）は有効のまま

## コンテキストと課題

ADR-0007 は、Resend 無料枠（100 通/日）が一斉送信機能に対して構造的に小さすぎることが主因であり、カウンタは「枠の枯渇」を「サーバーによる拒否」に言い換えるにすぎないとして、回数制限の導入を見送った。

その後、Resend の有料プラン移行が前提となり枠枯渇の主因は解消された。しかし ADR-0007 でトレードオフとして明記されていた「主催者が誤って複数回送信すると参加者へ重複メールが届く」問題が残る。参加者から見た実害は「同じイベントから短時間に大量のメールが届くこと」であり、これは送信枠の容量とは独立した被害である。一斉送信 API（`POST /api/v1/events/{id}/notifications`）の送信は DB に記録されないため、回数を数える手段も存在しなかった。

決めるべきことは「回数上限の単位・回数・期間」と「複数インスタンスでも正しく数えられる実装方式」である。

## 決定

一斉送信 API に、**イベントごと・直近 24 時間あたり 5 回**の送信回数上限を設ける。超過時は HTTP 429（`notification_limit_exceeded`）で拒否し、メールは 1 通も送信しない。

1. 上限の単位は **eventID**（`events.id`）とする。上限回数は 24 時間あたり **5 回**、期間は**スライディングウィンドウ**（現在時刻から過去 24 時間に予約された回数を数える）とする。
2. 送信回数は **DB（新テーブル `event_notification_send_log`）で数える**。1 回の送信につき 1 行を INSERT し、対象期間内の行数が上限を数える。メモリ上のカウンタは使わない。
3. カウントは**送信前の予約方式**とする。`Reserve`（同一トランザクション内で `pg_advisory_xact_lock(hashtextextended(event_id::text, 0))` によるイベント単位の直列化 + 期間内行数の SELECT + INSERT）で枠を確保してから送信する。送信成功時は予約行に `sent_at` を記録し、送信失敗時は予約行を DELETE して枠を返す。
4. 上限の対象は一斉送信 API のみ。イベントキャンセル通知（ADR-0016）と欠席連絡（ADR-0031）の outbox 送信は**対象外**とする。両者は参加者にとって必須連絡であり、回数上限で止めるべきでないため（ADR-0016 で宛先数上限を適用しないのと同じ判断）。
5. 上限値・期間はコード内定数とする（`maxNotificationSendsPerEvent = 5`、`notificationSendWindow = 24h`）。宛先数上限（`maxNotificationRecipients`）と同じく、運用で変更するものではないため環境変数にしない。

## 理由

- **単位をイベントごとにする**: 重複メールの被害は「同じイベントの参加者に何度届くか」で決まるため、被害の受け手に一致する単位がイベント。主催者単位では、複数イベントへ分散送信した場合に各イベントの参加者への反復送信を止められない。トークン漏洩時の総送信量は Resend 側の料金上限と監視に委ねる。
- **回数 5 回・期間 24 時間**: 正当な運用（前日リマインド・当日連絡・急な変更連絡）を妨げない上限であり、連打やダブルクリック（同時 2 回消費）を数回で吸収しきる。参加者に 1 日 6 通以上の同イベントメールが届く状況は、主催者の意図の有無にかかわらず拒否してよい量。
- **予約方式（送信前に枠確保）**: 送信後に記録する方式では、送信と記録の間に他リクエストが割り込み上限を超えて送信でき、複数インスタンス下で数え漏れる。予約なら「上限を超える送信は開始しない」ことが保証される。予約後にプロセスが死んだ場合、次のウィンドウまで 1 回分の枠が欠けるが、これも「過剰送信されない」方向の誤差であり許容する。
- **DB + advisory lock**: ADR-0037 により最大インスタンス数は 1 だが、同一インスタンス内の同時リクエストや、今後インスタンス数を変更しても数え方が壊れないようにする必要がある。`pg_advisory_xact_lock` によるイベント単位の直列化は PostgreSQL だけで完結し、外部ロック・外部キューを持ち込まずに済む。

## 影響（結果）

### 良い影響

- 参加者が同じイベントから受け取る一斉送信が 24 時間あたり 5 通までに収まる。
- 上限の判断（単位・回数・期間・対象外範囲）が ADR として明文化され、将来の変更時に議論の土台が残る。
- 送信履歴が `event_notification_send_log` に残り、運用調査が可能になる。

### トレードオフ・制約

- 主催者が短期間に 6 回以上の正当な連絡を送る必要が生じた場合、429 で止まり翌ウィンドウまで送れない。運用上は 1 日 5 回を超える全体連絡は発生しない前提。
- 送信成功後の `MarkSent` 失敗時は送信済みのまま予約行が `sent_at` 無しで残る（カウントには影響しない）。
- 予約後・送信前のプロセス死亡で枠が 1 回分欠ける（自己修復はウィンドウ経過後）。送信が「余分に行われる」方向の誤差ではないため、重複メールの観点では安全側。

## 検討した代替案

- **主催者（profileID）単位の上限**: トークン漏洩時に複数イベントへ散らばる送信を抑えられる利点があるが、イベントごとの参加者への反復送信を止められない。被害の受け手と単位が一致しないため不採用。将来、漏洩対策として追加する場合は別 ADR とする。
- **メモリ上のトークンバケット**: 実装が最小だが、再起動で消え、複数インスタンスで数えが分断される。AC で複数インスタンスでの正確性が要求されているため不採用。
- **固定 1 日分のカウンタテーブル（UPSERT + RETURNING で原子的加算）**: 単一 UPDATE 文で成立する利点があるが、送信失敗時の返却（減算）とウィンドウのリセット処理が文面複雑になり、送信履歴も残らない。可読性と監査性を優先し不採用。
- **冪等キーによる重複送信抑止**: ADR-0007 も指摘した方式だが、「同じ内容の意図しない二重送信」を消すものであって「上限回数を超えた意図的な送信」を止められない。本 AC の要件と目的が異なるため不採用（将来の別課題として残す）。
- **上限を設けない（ADR-0007 の維持）**: 重複メールの実害が残る。ADR-0007 が想定していた「枠枯渇が主因」の構図は有料プラン移行で解消済みのため、回数上限の費用対効果は再評価の余地があると判断し不採用。
